# 第二部分：知识点

## ⭐ A. 只有"真运行"才能发现的问题（静态审查的死角）

**这三个是本次最有价值的发现，因为前面 7 个阶段的所有静态检查都放过了它们。**

### A-1. 上游库的 `isinstance` 检查 → 适配器必须在装配点解包

```
Invalid checkpointer provided. Expected an instance of `BaseCheckpointSaver`,
`True`, `False`, or `None`. Received SqliteCheckpointStore.
```

**背景**：我们的架构是"业务代码依赖 `CheckpointStore` **协议**，不依赖具体 saver"
（为了 web/desktop 各用 PG/SQLite）。但 LangGraph 的 `compile(checkpointer=...)`
**做类型检查**，不接受适配器。

**解法（是分工，不是妥协）**：

```
业务层（routers / services）  → 用协议，可替换
装配层（build_graph）        → 解包出真 saver 交给 LangGraph
```

**教训**：适配器模式遇到"上游要 isinstance"时，**必须有明确的解包点**。
而且这个解包点应该**只有一个**（我们放在 `build_graph`）。

### A-2. `getattr(obj, "name", None)` = 静默失败

**现象**：我加了 `_unwrap_checkpointer` **之后仍然报完全相同的错**。

**原因**：store 把 saver 存成**私有的 `_saver`**，而解包函数找的是 `.saver`：

```python
getattr(obj, "saver", None)   # 名字对不上 → 返回 None（不报错！）
```

**教训**：**带默认值的 `getattr` 是"静默失败"的经典来源**。
错误不在现场炸，而是在很远的下游以完全不同的形式出现（"Invalid checkpointer provided"）。

**判据**：如果你写 `getattr(x, "y", None)`，问一句"**拿不到时会发生什么？**"
—— 如果答案是"很久以后报一个看不懂的错"，那就别用默认值，让它当场炸。

### A-3. 表结构：PG 版与 SQLite 版**不一样**

| | PostgreSQL saver | **SQLite saver** |
|---|---|---|
| 表 | `checkpoints` + `checkpoint_blobs` + **`checkpoint_writes`**（3 张） | `checkpoints` + **`writes`**（2 张） |

**原因**：SQLite 能把 blob 直接存在行里，不需要拆表。

**教训**：**同名库的不同后端，可能有不同的 schema**。
写断言时要**从源码/实测取表名**，不能从"另一个后端"的记忆里搬。

## ⭐ B. 一个反复复发的病根：「对象 vs 字典 / 类 vs 实例」

**今天它在四个地方出现，都是同一个病：**

```python
ReadFileTool.name                      # ❌ 类 vs 实例
ReadFileTool().name                    # ✅
ReadFileTool.model_fields["name"].default  # ✅ 确实要在类上取值时

tool.args.key()                        # ❌ dict vs 对象（.key() 是 Java 写法）
{arg for t in TOOLS for arg in t.args} # ✅ 迭代 dict 得到的是键

getattr(back.checkpoint, "id", None)   # ❌ back.checkpoint 是 dict
back.checkpoint.get("id")              # ✅

latest["tool_calls"]                   # ❌ AIMessage 是 Pydantic 模型不是 dict
latest.tool_calls                      # ✅
```

**排查口诀**：
> 报错说某个名字不对时，先问 **"它说的那个名字在哪一侧？"**
> —— 类 vs 实例？dict vs 对象？

**为什么它反复出现**：因为**静态看不出来**。`getattr(dict, "id", None)` 语法完全合法。

## ⭐ C. asyncio 下的"无锁"：判据是「临界区里有没有 await」

**先破除误区**：**无锁 ≠ 没有临界区**。

| | 多线程 | asyncio |
|---|---|---|
| 谁打断你 | **线程调度**（随时） | **只有 `await`** |
| 要锁吗 | 要 | **只在临界区里有 await 时才要** |

**推论**：**一段没有 await 的同步代码，本身就构成原子临界区。**

| | `LocalTokenBucket`（令牌桶） | `CircuitBreaker`（熔断器） |
|---|---|---|
| 临界区里有 await 吗 | ❌ 没有 | ✅ **必须有**（要先 await 下游） |
| 要锁吗 | **不要** | **要** |
| 硬加锁的后果 | 把临界区**切开**，反而制造竞态 | —— |

**熔断器不加锁的真实后果**（原 `RedisFuse` 的缺陷）：

```
协程1: 读 _fail_count = 0   ...
协程2: 读 _fail_count = 0   ...   ← 两个都读到 0
协程1: _fail_count = 1
协程2: _fail_count = 1            ← 两次失败只记了 1 次
```

配"连续失败 5 次跳闸"，实际要失败 8 次。**只让熔断变慢，不报错。**

**加锁姿势**：锁要包住**读-改-写整段**，不是只包写。

```python
async with lock: 读状态; 判断; 改状态     # ✅
读状态; async with lock: 改状态           # ❌ 读和写之间仍可被插入
```

## ⭐ D. 路径安全：必须"两道门"，且**第二道才是真门**

```python
if Path(p).is_absolute(): raise ...        # ① 意图检查（挡不全）
target = (root / p).resolve()              # ② 拼接 + 解析
if not target.is_relative_to(root): raise  # ③ 结果校验 ★ 唯一不可绕过的
```

**①挡不全的具体漏网输入**（实测）：

```
PureWindowsPath('/etc/passwd').is_absolute()  =  False   ← 放行了！
而 (root / '/etc/passwd')  =  C:\etc\passwd              ← root 被替换掉了
```

**两个原因叠加**：
- Windows 的"绝对路径"需要盘符，只有根斜杠**不算**
- `pathlib` 的规则是"**右侧绝对路径会替换左侧**"

**③为什么接得住**：`.resolve()` 展开符号链接 → 比对的是**解析后的真实路径**，不是输入字符串。

**另外两条**：
- `root` 自己也要 `.resolve()`，否则比对基准是假的，整道防线失效
- **不要用 `startswith`**：`"/sandbox-evil".startswith("/sandbox")` 为真 → 错误放行

## ⭐ E. Pydantic v2 禁止"类级访问字段"

```python
ReadFileTool.name                          # ❌ AttributeError: name
ReadFileTool().name                        # ✅ 'read_file_tool'
ReadFileTool.model_fields["name"].default  # ✅ 确实要在类上取值时
```

**机制**：`ModelMetaclass.__getattr__` 把"在类上访问字段"判为错误用法。

## F. 依赖管理的三条硬规则

### F-1. 参数名变了，全局搜索必须先跑

**今天两次踩同一个坑**：
- 删 `AsyncPostgresSaver` 的 import → 漏了**类型标注**`saver:AsyncPostgresSaver`
- 加 `load_prompt` 的 import → **anchor 字符串不匹配，静默失败**

**教训**：改一个符号的用法时，**先全局搜所有出现位置**（不只 import 行，
还有类型标注、字符串、注释里的引用）。

### F-2. 谁用谁声明（不要靠传递依赖）

今天的表现：我把框架依赖从 `furina_core` 收窄 → `furina_web` 立刻
`ModuleNotFoundError: No module named 'sqlmodel'` ——
因为它**从来没声明过**，原来是被 core "顺带"带进来的。

**判据**：`pyproject.toml` 的 dependencies 应该等于"这个包自己 import 的东西"，
不多不少。

### F-3. uv workspace 的机制

| 要点 | 说明 |
|---|---|
| 核心价值 | 每成员**各有 pyproject + 各自 dependencies**，但**共享一个 `.venv` 和 `uv.lock`** |
| 根变成"纯声明" | 业务依赖全部下移 → **默认 `uv sync` 只装根工程的**（所以要 `--all-packages`） |
| `[tool.uv.sources]` 必须写 | `furina-core = { workspace = true }` —— uv 0.12.5 **不会**自动推断成员依赖 |
| 包名 ≠ import 名 | `furina-core`（PyPI 用横线）→ `import furina_core`（标识符用下划线） |
| **必须用 `src/` 布局** | 只有真正安装进环境的包才 import 得到 —— **这正是验证依赖分离的前提** |

## G. 架构方法：从"能跑"到"bug 藏不住"

### G-1. 好的结构能让 bug 自己浮出来

| 调整前 | 调整后 |
|---|---|
| `prevalidate_node` 没被 `add_node` → 藏在 179 行里 | 提示词路径集中到 `loader.py` → **一处改，且只有一处** |
| `storage/` 依赖 `agent/` → 藏在 import 行里 | 加一条红线后，**反向依赖不可能再出现** |
| 空 `models/` 目录 → 看着像"还没写" | 删掉 → **不再误导** |
| "工具"散在 5 处 → 加新工具要想半天 | 全在 `agent/tools/` → **位置没有歧义** |

**判据**：如果一个 bug 需要"通读才能发现"，那是**结构的失败**，不是你的疏忽。

### G-2. 什么时候该分层，什么时候该合并

**反例（今天删掉的）**：桌面版的 `services/` + `repositories/` 两层。

**那一层的存在理由是**："多个 service 复用同一份数据访问"。
**桌面版只有一个消费者** → 成立条件不存在 → 分层变成纯粹的绕路。

**合并后的保留**：数据访问函数加 `db_` 前缀（`db_get_thread`），
**读代码时仍能区分"直接读写库的"与"做业务判断的"**。

**判据**：分层要有**成立条件**。条件不成立时的分层 = 负债。

### G-3. 生命周期 ≠ 组装（把反向依赖解开）

原 `storage/agent_graph.py` 一个文件干两件事：

```
① init_pg_saver / close_pg_saver    → 连接的开关      → 存储层
② build_graph(saver) + app.state.graph → 组装主管图   → 编排层
```

而且①里 `from furina_desktop.agent.graph import build_graph` ——
**存储层反向依赖编排层**。

**这个依赖的恶果不只是难看**：想换存储（PG→SQLite）就必须动 `storage/`，
而动 `storage/` 又会牵到 `agent/` —— **两件不相关的事被绑在一起**。

### G-4. 红线必须可机械检查

**我犯的错**：最初给 core 定"**零框架依赖**"，搬运后实测**不成立**
（`models.py` 要 sqlmodel、`storage/session.py` 要 fastapi、`config.py` 要 openai）。

**我的处理**：**改红线**（从"零框架"改成"**零存储后端**"），而不是把文件赶出 core ——
因为这几样**两边都要**。

| | 原红线 | 现红线 |
|---|---|---|
| 内容 | 零框架依赖 | 零存储后端（不出现 `asyncpg`/`psycopg`/`redis`/`lancedb`） |
| 能否机械检查 | ❌ "不依赖框架"没法验 | ✅ 一条 grep 验完 |

**教训**：**留一条无法验证的红线，比改掉它更危险** —— 下一个读代码的人会以为它成立。

## H. 工程习惯

### H-1. 区分"它崩了"和"它错了"

| | 特征 | 例子（今天） |
|---|---|---|
| **崩了** | 能被运行抓到 | `AttributeError: name` / `ImportError: ToolMessagefrom` |
| **错了** | **静默**，不报错 | `create_all` 漏表 / `getattr` 拿到 `None` / 字段名差个 `s` |

**后者更危险，而且只有"读代码 + 想语义"才能发现。**

### H-2. 环境问题 vs 代码问题（别改错东西）

**今天的实例**：SQLite 报 `unable to open database file`。

**我先做的**：用裸 `sqlite3` / `aiosqlite` / 绝对路径**三种方式交叉验证** →
证明代码没问题，是**沙箱不让我往 `%TEMP%\dsh-*` 写**。

**教训**：报错先问"**这是我的代码，还是我的环境？**"
—— 如果是环境，**不要为了迁就它去改代码**。

### H-3. 临时脚本用文件，不用 `-c`

`python -c "..."` 在 PowerShell 里要处理**三层引号**（PS 字符串 / Python 字符串 / 正则），
今天因此失败**两次**。改用"写临时脚本文件 → 跑 → 删"。

### H-4. 脚本化批量修改的纪律

| 纪律 | 今天的反例 |
|---|---|
| 替换规则**有序**（长在前） | `agent.node` 在 `agent.node.coder` 之前替换 → 产出 `nodess` |
| 处理**空文件**（`-Raw` 返回 null） | 空 `__init__.py` 让脚本抛异常 |
| 改完**立刻重跑验证** | 漏改的 import 藏了一整个阶段 |
| **脚本本身也要读** | 我的合并脚本产出过 `import X import Y` 这种语法错误 |

# 第五部分：一句话总结

> **今天做的事，本质上是把"一份混在一起、跑不起来的代码"拆成"三个边界清晰、
> 各自能跑的包"，并在过程中发现：真正难的不是重构，而是"判断哪些改动是
> 消除耦合、哪些只是换个地方放代码"。**
>
> **最大的收获有三条**：
> 1. **只有真运行才能发现某些问题**（适配器的类型检查、私有属性名不匹配）
> 2. **红线必须可机械检查**（"零框架依赖"是理想，"零存储后端"才是约束）
> 3. **好的结构能让 bug 藏不住**（这才是调架构的目的，不是好看）
