# 9.8 HITL 调研记录：六个高星 agent 项目的人机审批设计对照

> 调研时间：2026-09-07 ｜ 方式：6 个并行调研 agent 抓取真实 GitHub 源码/官方文档（raw.githubusercontent.com 直链），非二手结论
> 一句话：把 OpenAI Agents SDK / AutoGen / CrewAI / OpenHands / Cherry Studio / LangGraph 官方 的 HITL 拆成「审批粒度 × 介入形态 × 暂停恢复」三条轴做对照，结论收敛出三条铁共识，并映射回 furina 单图 LangGraph 的六步落地清单。
> 目的：给「代码 agent 改文件前需人工审批」的 gate 设计定参照系（对应 PLAN 十二节的 human-in-the-loop 落地点）。

## 一、HITL 设计三轴坐标系

所有框架的差异可压缩到三条轴上，每个设计决策都是各取一档：

| 轴 | 左极端 | 右极端 | 两端代表 |
|---|---|---|---|
| **A. 审批粒度** | 动作级（拦单个 file-write） | 任务收尾级（审整份 diff/总结） | OpenAI / OpenHands ↔ CrewAI |
| **B. 介入形态** | 结构化二元（approve/reject(+reason)） | 自由文本（人是对话参与者） | OpenAI / Cherry / OpenHands ↔ AutoGen / CrewAI |
| **C. 暂停与恢复** | interrupt 可序列化暂停 | 终止-重启（save_state 再续） | OpenAI / LangGraph ↔ AutoGen 慢速路径 |

## 二、六项目定位速查

| 项目 | 审批粒度 | 人介入 | 暂停恢复 | 最值得抄的一个设计 |
|---|---|---|---|---|
| **OpenHands** | 每步**整批** all-or-nothing | 状态机 + 按钮（可带 reason） | 再次 run() 即放行 | 「动作先入历史 → 未匹配 observation 即 pending → 批准=再次 run」，**不用独立消息类型** |
| **AutoGen** | 代码执行前 `approval_func` | 人是团队参与者，自由文本 | in-run 阻塞（慎用）或 终止+save_state | `UserInputRequestedEvent`(事件)与 `TextMessage`(对话消息) **分离**——审批噪音不进 LLM 历史 |
| **CrewAI** | 任务收尾级（human_input=True） | 自由文本，空串=认可 | 同步 kickoff 自然阻塞 | 对"人工把关整份 diff"场景有用；工具调用点无能为力 |
| **OpenAI SDK** | 工具声明 `needs_approval`(静态/动态) | 结构化 approve/reject | `RunState.to_json/from_json` 可序列化暂停 | `ApplyPatchTool` 审批函数拿 `{type,path,diff}`——**审批对象=路径+diff 而非工具名** |
| **Cherry Studio** | 每工具调用（PreToolUse 钩子） | 主进程注册表 respond(approved/reason/updatedInput) | 挂起态在主进程，abort 按拒绝结算 | per-tool auto/ask/deny + per-agent 权限档 + **不可穿透守卫**（bypass 也拦 sqlite 写库/全局安装） |
| **LangGraph 官方** | middleware 批量打包一次 interrupt | 四决策 approve/edit/reject/respond | interrupt+checkpointer（我们已有） | `graph.stream_events(version="v3")` 才是官方推荐观测姿势 |

## 三、各项目深度要点（源码锚点 + 可抄点）

### 3.1 OpenHands（对我们价值最大的真代码 agent）

**风险分 4 级**：`SecurityRisk.UNKNOWN/LOW/MEDIUM/HIGH`（risk.py）。
**定级与"要不要问"两轴解耦**：`SecurityAnalyzerBase.security_risk(action)`（可插拔：LLM 分析器读工具参数里自评的 `security_risk` / 规则系 Pattern/PolicyRail / 组合防御）决定风险等级；`ConfirmationPolicy.should_confirm(risk)`（AlwaysConfirm / NeverConfirm / `ConfirmRisky(threshold=HIGH, confirm_unknown=True)`）决定是否该问。异常一律回退 HIGH（fail-closed）。只读工具（schema `readOnlyHint`）强制 UNKNOWN 天然免问。
`Finish/Think` 单动作永远免问。

**核心机制（最值得搬的整套模板）**：
1. LLM 产出 tool_calls → 逐个建 `ActionEvent` 进事件历史（**带 tool_name/tool_call_id/security_risk/summary，此时尚未执行**）。
2. 需要确认时，动作只进历史不执行，`ConversationState.execution_status` 置 `WAITING_FOR_CONFIRMATION`，run 主循环 break。
3. **批准 = 再次 run()（隐式确认）**：`agent.step/astep` 头部先查 `get_unmatched_actions()`，有则执行这批动作再返回。
4. **拒绝 = `reject_pending_actions(reason)`**：对每条 pending 生成 `UserRejectObservation(action_id, tool_call_id, reason)` 以 **tool 角色消息写回 LLM 历史**，状态回 IDLE。
5. 竞态兜底：等待确认期间新用户消息到达 → 自动拒绝 pending（"Superseded by a new user message"），防止残留 pending 下次 run 被隐式静默执行。

**前端协议**：没有专门的 "ConfirmationAction" 事件类型——「需要人决策」= 状态机状态叠在已流出的 ActionEvent 上。UI 判定 `curAgentState === AWAITING_USER_CONFIRMATION` 且最后一个 agent 事件存在 → 渲染成审批卡（`conversation-confirmation-buttons.tsx`），内容就是动作的 `summary`+`security_risk`（HIGH 显示 RiskAlert 红条）。批准/拒绝走**独立 API**（`POST /api/conversations/{id}/events/respond_to_confirmation {accept, reason}`），不走聊天事件通道。

**"免重复问"的记忆 = 会话级策略降级**（AlwaysAsk → Risky(HIGH) → Never 三级），不是精确命令 allow-list；细粒度规则放规则分析器里，不混在审批流程。

> 对 furina 的可抄点：把"需要人决策"建模为状态机位而不是新消息类型；拒绝对称回喂 LLM 且理由走历史通道；「批准=再次 run」让 CLI/Web 共用同一状态机。
> 源码路径：`software-agent-sdk/openhands-sdk/openhands/sdk/security/{risk,analyzer,confirmation_policy}.py`、`sdk/agent/agent.py`（_requires_user_confirmation ~L1025、_get_action_event、astep 头部）、`sdk/conversation/impl/local_conversation.py`（run 循环 break ~L1985、reject_pending_actions ~L2606、竞态兜底 ~L2265-2310）。最清晰闭环看 `software-agent-sdk/examples/01_standalone_sdk/04_confirmation_mode_example.py` + `tests/sdk/conversation/local/test_confirmation_mode.py`。

### 3.2 OpenAI Agents SDK（结构化派参考）

**声明**：`FunctionTool/function_tool/ShellTool/ApplyPatchTool/CustomTool/Agent.as_tool` 都有 `needs_approval: bool | Callable`。
**fail-closed**：动态审批函数在参数无法安全解析时（畸形 JSON / NaN / Infinity / 解析非对象）→ **强制人工审批**，不调用审批函数（`parse_function_tool_arguments` 返回 None → return True）。文件工具尤其该抄：参数解析失败宁可多审，别放行去写盘。
**中断契约**：`ToolApprovalItem`（agent + tool_name + arguments + call_id，tool.py/items.py）进 `RunResult.interruptions` 后整局暂停；**刻意不以流事件投递**（stream_events 白名单没有 approval，实现里 `ToolApprovalItem → event=None`，注释 "approvals represent interruptions, not streamed items"）。UI 感知方式：流正常结束 + `result.interruptions` 非空 → 弹卡。
**审批 API**：`RunState.approve(item, always_approve=False)` / `reject(item, always_reject=False, rejection_message=...)`；实现是 RunContextWrapper 上的决策注册表（per-call_id 或 always 永久，带 fingerprint/scope 防嵌套歧义），随 `RunState.to_json()/from_json()` 序列化落库——**审批卡天然可跨进程**。没有独立 edit/respond 类决策（只有二值 approve/reject + always 粘性）。
**拒绝回灌模型**：`resolve_approval_rejection_message` 把一句拒绝文案包成普通 `ToolCallOutputItem` 喂回模型（自定义文案 > RunConfig.tool_error_formatter(kind="approval_rejected") > 默认常量）。
**代码/文件编辑类（与我们最贴）**：
- `ApplyPatchTool`（tool.py L1440 / editor.py）：模型请求改文件（unified diff），宿主实现 `ApplyPatchEditor` 协议（create/update/delete，入参 `ApplyPatchOperation{type, path, diff, move_to}`）。审批函数签名 `(ctx, operation, call_id)`——**能看到完整 path + diff**，天然支持"展示 diff 给人工"。另有 `on_approval` 程序化审批回调（不暂停）。
- `ShellTool`：本地模式（配 executor）才支持审批钩子；hosted 模式直接 UserError 拒绝。
- MCP：本地 server `require_approval=`；Hosted MCP `tool_config={"require_approval":"always"|"never"} + on_approval_request`。
**嵌套冒泡**：`Agent.as_tool()` 内部产生的审批中断仍然出现在**外层 run** 的 interruptions/RunState 上，在外层 approve/reject 后恢复；决策经 `_find_nested_approval_state` 定位回嵌套 run 自己的 state。

### 3.3 AutoGen（自由文本派参考 + 代码审批新特性）

**现役 HITL = UserProxyAgent**：把人做成团队里的普通参与者（RoundRobin/SelectorGroupChat），`input_func: Callable[[prompt, CancellationToken?], str]`，回复作为 `TextMessage`/`HandoffMessage` 注入同一次对话流。
**两种介入时机（关键设计）**：
1. in-run 阻塞——官方**明确警告**这会让团队处于"不可保存/恢复的临时阻塞态"，只适合按钮式秒级交互；
2. **终止后重启**——`HandoffTermination`/`SourceMatchTermination` 先让团队停下，`team.save_state()/load_state()`，人回复后下次 `run_stream(task=人话)` 续跑。慢速人类响应推荐此路。
**事件/消息分离**：轮到人时流上发 `UserInputRequestedEvent`（属 AgentEvent，官方声明"仅向用户/应用通知，不做 agent 间通信、不进历史"），随后 input_func 被 await 停顿；人话才是进上下文的 ChatMessage。官方 FastAPI 示例把 `run_stream` 喂给 websocket，遇 `UserInputRequestedEvent` 启用输入框，input_func `await websocket.receive_json()` 阻塞等浏览器。
**代码执行审批（最新 main 已合入，commit #6886）**：`CodeExecutorAgent`/`MagenticOne` 加 `approval_func`，每次执行代码块前回调：`ApprovalRequest{code, context} → ApprovalResponse{approved: bool, reason}`，支持 sync/async，默认不设=自动放行。**注意：设了 approval_func 后 agent 不可再 dump_component 序列化**——审批属运行时策略，不是声明式配置。
**低层兜底**：autogen-core `DefaultInterventionHandler.on_send` 可拦截任意 agent→agent 消息（cookbook《User Approval for Tool Execution》对 FunctionCall 弹 y/n，拒绝抛 ToolException）。

### 3.4 CrewAI（任务收尾把关派，别指望它拦工具调用）

**内置门闩 = task 级 `human_input=True`**：agent 思考完、给 final answer 之前阻塞等人；`input()` 同步拿自由文本，经 `_format_feedback_message` 写回 context.messages 后重启 agent 循环；**空串=认可结束**（"loop until satisfied"）。最新 main 抽象成可插拔 `HumanInputProvider/SyncHumanInputProvider`（core/providers/human_input.py），executor 经 get_provider() 取用；已加入异步路径（commit f6fa045，AsyncExecutorContext + 非阻塞输入 + 把 HumanFeedbackResult 抛给 listeners）。
**无 Crew 级"批准开跑"门、无工具调用点门**。"工具主动问人"= 社区把 HumanApprovalTool 写成 BaseTool 子类、`_run` 里阻塞人机往返（"use before any irreversible action"）。
> 结论：要"写文件前批准"别指望内置，得把审批做成工具调用点自己阻塞一轮。

### 3.5 Cherry Studio（工具审批的工程纵深派——宿主现场解剖）

**它不自己写 agent step-loop**，把 Claude Code SDK / Pi / DeepSeek Harness 当可插拔驱动接入；哲学 = "权限门槛 + 连续自主"，不是教科书 interrupt/resume。
**审批 = 主进程注册表 + IPC respond**（`src/main/ai/toolApproval/ToolApprovalRegistry.ts`）：driver 把工具调用按 toolCallId 挂起为 PendingApproval，等渲染端 `ai.tool.respond_approval {approved, reason?, updatedInput?}` 才 dispatch 放行；注册被 abort 自动按拒绝结算。
**三层策略而非逐次弹窗**：① per-tool 声明式（auto/required/runtime + bypass lift/enforce，`builtinToolPolicy.ts`）；② per-agent 权限模式（产品层 5 档：逐次确认/自动接受编辑/智能批准/仅规划/完全访问）；③ **不可穿透自动拒守卫**——`userDataSqliteGuard.ts`（拦用户数据目录 SQLite 写入）、dependencyGuard（拦全局安装）、toolGuards.ts（注释明确 "bypassPermissions only skips interactive-effect"，headless denials 每档生效）。
**steer 而非插话**：官方注释 "No mid-stream message injection — steering handled by queueing a steer, yielding at a step boundary"。
> 它没确认有真正的 diff 预览后批准——这是它没做好的点，恰是我们该做得更强的地方（获批前出 diff 视图）。
> 源码：`src/main/ai/toolApproval/{ToolApprovalRegistry,builtinToolPolicy,userDataSqliteGuard,toolGuards}.ts`、`src/main/ai/runtime/claudeCode/{guardRules,settingsBuilder}.ts`、`.../pi/approvalExtension.ts`、`src/renderer/components/composer/variants/PermissionRequestComposer.tsx`。

### 3.6 LangGraph 官方（对照——两条旧结论已被 2026 版本更新）

**结论一：`messages` 模式漏中断 = 按设计，不是 bug，别去修它。** 中断永远挂在 state/values 类投影（v1 `__interrupt__` key → v2 `values` 流的 `interrupts` 字段），从不出现在 LLM token 的 messages 投影。**当前主推姿势 = `graph.stream_events(..., version="v3")`**：同一底层事件流多投影并发消费，`stream.messages` 收 token、`stream.interrupts`/`stream.interrupted` 收中断、`stream.output` 拿终态，互不消耗（event-streaming.md）。
**结论二：supervisor 三铁律被官方重写**（`langgraph-supervisor` 包已停维护，迁移到"主管 create_agent + 子代理包成 @tool"模式，migrate/langgraph-supervisor.md）：
| 旧（9.7 记的） | 新（2026 官方） |
|---|---|
| 共享同一 saver 实例 | **只给最外层图编译 checkpointer，子 agent 一律不传** → per-invocation 持久化（单次调用内继承父级、支持 interrupt） |
| 工具内 get_config() 透传 | **已自动化**（tool 包装子代理自动继承），官方文档该词 0 次出现 |
| 主管层统一 resume | 仍成立且明文：恢复永远在最外层 + 原 thread_id + `Command(resume=...)` |

**HumanInTheLoopMiddleware 现状**：不在 langgraph 包，canonical 位置 = langchain v1 的 `libs/langchain_v1/langchain/agents/middleware/human_in_the_loop.py`（包发行名 `langchain`，抓取时 1.4.0）。机制：`after_model` 把一次 AI 消息里所有需审 tool_calls 批量打包进**一次** `interrupt(hitl_request)`；resume 校验 decisions 数量 = 被打断数，按序处理（approve=原样执行 / edit=改 name/args / reject=合成 status="error" ToolMessage / respond=合成 status="success" ToolMessage 跳过）。`when` 谓词需 langchain>=1.3.3。middleware 只能在 `create_agent` 编译的 runtime 生效，不能直接挂手搓 StateGraph 节点。
**恢复语义（langgraph/types.py interrupt docstring）**：resume 必须 Command；被中断节点**从头重跑**（之前代码再执行一遍，须幂等）；同节点多 interrupt 按 index 匹配 resume 值；多中断可 `Command(resume={i.id: value})`。需 checkpointer。

## 四、跨项目收敛的三条铁共识

1. **拒绝必须对称回喂给 LLM，且走历史通道**。OpenHands `UserRejectObservation`（tool 消息 + tool_call_id + reason）、OpenAI 把"未获批准"包成工具输出回灌、LangGraph middleware 合成 status="error" ToolMessage。共同点：agent 看到"哪个动作被拒、为什么"→ 自我纠错。静默不执行 = 最差实现。
2. **审批请求不要混进模型上下文/对话历史**。AutoGen 明说事件不进历史；OpenAI `to_input_item()` 主动抛异常防回灌；OpenHands pending 是事件层状态。
3. **竞态兜底是隐藏大坑**：等待确认期间新用户消息到达 → 自动拒绝 pending（OpenHands "Superseded by a new user message"），否则残留 pending 会在下次 run 被"隐式放行"静默执行。SSE 实现几乎必然踩。

## 五、映射回 furina 的落地决策

**核心判断：选 LangGraph 在轴 C 上占大便宜。** checkpointer + interrupt 已替你实现"暂停/恢复"，OpenAI 要自己造 RunState 序列化、AutoGen 要 save_state/load_state、OpenHands 要再次 run() 才有。你只需在轴 A/B 做决定 + 把状态暴露到 SSE 层。

**技术栈现状（2026-09-07）**：单智能体 ReAct（graph.py，furina 节点 + 全量 tools）；checkpointer = AsyncPostgresSaver；agent_stream 走 `stream_mode="messages"`；事件契约还是 status 魔法串（9.7 遗留：要改 type 封闭集）；PLAN 十二目标是 supervisor（子代理=工具，tool-as-agent）。

**落地六步（按依赖序，均为待办钩子）**：

- [ ] **1. 观测通道先换**：`agent_stream` 从 `stream_mode="messages"` → `graph.stream_events(version="v3")`（或 async `astream_events` + asyncio.gather 并发消费 messages/interrupts/output）。一并解决 messages 模式漏 `__interrupt__` 老大难。
- [ ] **2. 事件契约升级**（9.7 遗留项）：`status` 魔法串 → `type` 封闭事件集，加入 `approval_required`（及终态 `done`/`error`）。前端收到 `approval_required` 才弹审批卡。参考 9.7 三流派；LangGraph 系保留"错误是事件不是断流"。
- [ ] **3. 审批粒度（轴 A）选方案①起步**：把 `interrupt()` 内嵌进会改文件的 `@tool`。审批上下文 = `{path, diff, tool_call_id, reason}`；resume payload 支持 approve/reject（+可选 reason）。理由：贴合"写操作集中在工具层"现状 + 将来 tool-as-agent 复用。铁律：interrupt() 不包 try/except；resume 后节点从头重跑 → gate 前不得有副作用。
- [ ] **4. 决策契约（轴 B）**：单图阶段 = 结构化 approve/reject + 可选 reason（OpenAI/OpenHands 派），UI 是按钮卡而非聊天介入，不引入 AutoGen 自由文本。
- [ ] **5. 拒绝回喂**：reject 的 resume 返回后，节点合成一条 `ToolMessage(status="error")` 回 LLM 说明理由（铁共识 1）。
- [ ] **6. 竞态兜底**：审批挂起期间用户又发新消息 → 作废旧 pending（铁共识 3），agent_stream 内处理。

**待拍板的开放问题**（写代码前定）：
- 审批粒度要不要"整批"（一次 LLM 响应多个 file-write 打包成一次 interrupt，OpenHands/middleware 派）还是"逐工具"（每次 interrupt，OpenAI 单工具派）？→ 建议起步整批打包，减少打断次数。
- 是否需要 edit（改参/改 diff 再执行）？LangGraph middleware 支持、OpenAI SDK 不支持、OpenHands 不能直接改（reject+重出）。若 MVP 只要 approve/reject，先砍 edit。
- diff 预览放哪层：`interrupt()` payload 里带 unified diff，UI 渲染 diff 视图（OpenHands/Cherry 都没做好的点，是我们的差异化）。

## 七、一句话沉淀

HITL 的门道不在"要不要 interrupt"，而在三件事：**审批对象长什么样（路径+diff 而非工具名）、拒绝怎么对称回喂给模型、挂起期间来了新消息怎么办**。框架的暂停/恢复机制只是地基，且 LangGraph 已经把地基给我们铺好了。
