## 1. 现状结论（压缩版）

### 1.1 三句话

1. **链路断在入口**：coder 子图第一个节点读不到 `subagent_task`，实测 `AttributeError`。
2. **审批门不在图上**：`prevalidate_node` 未注册、`pending_reviews` 永远为空、`execute_node` 未注册且为空。
3. **没有审批持久化**：无表、无状态、无幂等键、无唯一约束、无执行记录。

### 1.2 当前数据流（实际）

```text
HTTP → get_session（desktop 未接业务库）→ agent_stream（NotImplementedError）
图   → prepare_node（AttributeError）
即便绕过 → model → review_node（pending_reviews=None）→ model（热循环）
```

### 1.3 约束 → 设计落点

| 任务书约束 | 本文落点 |
|---|---|
| 审批状态与执行状态分离 | §3 两列独立枚举 + §4 状态机 |
| 高风险操作必须经过统一执行器 | §6 唯一入口 `execute_approved` |
| 审批绑定工具及关键参数 | §3 `tool_name + args_json + args_hash + target_path` |
| 重复提交不重复创建 | §5 幂等键 |
| 不能只靠"先查再写" | §5 DB `UNIQUE` + `IntegrityError` |
| 唯一冲突必须正确处理 | §5 savepoint + rollback + 语义校验 |
| 只有有效批准才授权执行 | §4 / §6 条件 UPDATE |
| 执行前查有效性 + 内容一致 | §6 `args_hash` / `old_hash` / 路径复检 |
| 结果不确定不盲目重试 | §4 `unknown` 终态 + §6 不自动重试 |

## 2. 目标架构

### 2.1 分层

```text
packages/core/furina_core/approval/
    enums.py       审批/执行状态（纯枚举，无依赖）
    models.py      SQLModel 表（web/desktop 共用）
    repository.py  数据访问 + 幂等插入 + 条件更新
    service.py     业务规则（创建、决策、执行认领）

apps/desktop/
    storage/database.py      SQLite 引擎 + session（新增）
    services/approval.py     审批业务 + 执行器
    api/agent.py             决定 / 列表 / resume
    agent/...                图与工具接线
```

### 2.2 单一事实来源

**数据库是审批状态的唯一事实来源。**

- LangGraph checkpoint 只负责"图停在哪"；
- `pending_reviews` 只是给 UI 的展示快照；
- **执行参数只从数据库的 `args_json` 读取**，绝不从 resume 载荷读取。

这条决定了三件事：

1. 客户端无法通过修改 resume 载荷篡改参数；
2. 进程重启后仍能查询/决策；
3. checkpoint 丢失时，审批记录仍可审计。

### 2.3 执行边界

```text
安全工具 → ToolNode（现状保留）
高风险工具 → 只能由 execute_approved() 调用
```

**硬约束：`ToolNode` 的 tool 列表里不能再出现高风险工具。**
否则存在"批准后走执行器"与"直接走 ToolNode"两条写盘路径，审批可被绕过。

## 3. 数据模型

### 3.1 粒度

**一行 = 一个工具调用。**

不是"一次 interrupt 一行"。理由：

- 约束要求"绑定具体工具及关键参数"，逐行天然满足；
- 现有 `ItemDecision` 就是逐条决策；
- 不需要 `batch` 主表 + `items` 子表；
- 同一批用 `batch_id` 分组即可。

### 3.2 表：`approval_request`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | UUID PK | 审批记录 id |
| `thread_id` | str(64)，索引 | LangGraph thread |
| `batch_id` | str(64)，索引 | 同一次 interrupt 的批次 |
| `scope` | str(32) | 固定 `"coder"`，为将来多子代理预留 |
| `tool_call_id` | str(128) | LLM 给出的调用 id |
| `tool_name` | str(128) | 必填 |
| `args_json` | Text | **完整参数快照**（执行时唯一来源） |
| `args_hash` | str(64) | `sha256(args_json)` |
| `target_path` | str(512) nullable | 沙箱相对路径 |
| `old_hash` | str(64) nullable | 审批时文件内容哈希（乐观锁） |
| `idempotency_key` | str(64) **UNIQUE** | 见 §5 |
| `approval_status` | str(16) | pending/approved/rejected/expired/cancelled |
| `execution_status` | str(16) | not_started/running/succeeded/failed（+ 建议扩展 `unknown`） |
| `decided_by` | str(128) nullable | 审批人（desktop 固定 `"local"`） |
| `decided_at` | datetime(tz) nullable | |
| `decision_reason` | Text nullable | |
| `execution_started_at` | datetime(tz) nullable | |
| `execution_finished_at` | datetime(tz) nullable | |
| `execution_result` | Text nullable | 成功摘要（如写入字节数/hash） |
| `execution_error` | Text nullable | 失败/未知原因 |
| `created_at` / `updated_at` | datetime(tz) | UTC |

> **与草案的差异（需确认）**：草案 §5 的执行状态只有四种
> `NOT_STARTED / RUNNING / SUCCEEDED / FAILED`。
> 本文额外使用 `unknown` 表达"可能已执行、但响应丢失"（草案 §8 明确要求不能把它
> 当失败盲目重试）。若严格按草案，可改成 `FAILED` + 单独的 `outcome_uncertain` 标记。
> **这一条在实施阶段 3 前必须定下来。**

### 3.3 索引与约束

```text
PRIMARY KEY (id)
UNIQUE (idempotency_key)
INDEX (thread_id, approval_status)
INDEX (batch_id)
CHECK (approval_status IN (...))
CHECK (execution_status IN (...))
```

- `UNIQUE` 是幂等的**真正保证**，不是辅助。
- `CHECK` 可选但建议加：PG 与 SQLite 都支持，能在数据库层挡住非法状态。
- 不建 `UNIQUE(batch_id, tool_call_id)`：`idempotency_key` 已覆盖，重复约束只会增加冲突处理分支。

### 3.4 为什么不用原生 ENUM

- PG 原生 enum 改值需要 `ALTER TYPE`，SQLite 不支持；
- 用 `VARCHAR + CHECK` 跨库一致，且迁移简单；
- 应用层仍用 `str, Enum`（JSON 可序列化，`interrupt()` 载荷需要）。

## 4. 状态机

### 4.1 审批状态

```text
pending ──approve──▶ approved
pending ──reject───▶ rejected
pending ──超时─────▶ expired
pending ──新请求/文件已变──▶ cancelled

approved / rejected / expired / cancelled 为终态
```

### 4.2 执行状态

```text
not_started ──执行器原子认领──▶ running
running ──成功────▶ succeeded
running ──确定失败──▶ failed
running ──结果不明──▶ unknown
```

### 4.3 两条铁律

1. **`approved` 只代表授权，不代表执行。**
   批准后 `execution_status` 仍是 `not_started`。
2. **只有 `approved + not_started` 才能进入 `running`。**
   这是条件 UPDATE 的 WHERE 子句，不是应用层 if。

### 4.4 终态不自动重试

- `failed`：确定没有产生副作用，或已确定失败。要重试必须重新审批。
- `unknown`：可能已产生副作用。**禁止自动重试**，等人工确认。
- 不引入"自动回滚"：文件写入无法可靠回滚，假装能回滚比不做好。

## 5. 幂等设计

### 5.1 幂等键

```text
idempotency_key = sha256(
    canonical_json({
        "thread_id": thread_id,
        "scope": "coder",
        "tool_call_id": tool_call_id,
        "tool_name": tool_name,
        "args": args
    })
)
```

`canonical_json`：

```python
json.dumps(obj, ensure_ascii=False, sort_keys=True, separators=(",", ":"))
```

然后 utf-8 编码再 sha256，输出 64 位 hex。

**为什么包含 `tool_call_id`：**

- 它在 resume 后仍稳定存在于 state 的 `AIMessage` 中（待阶段 2 实测确认）；
- 同一逻辑请求的重复投递会得到同一个 key；
- 新的一轮对话会生成新的 `tool_call_id`，不会误伤"用户真的想再写一次同样内容"。

**为什么不包含 `checkpoint_id`：**

- checkpoint id 是图内部实现细节，升级 LangGraph 可能变化；
- 它不表达"这是哪个操作"。

### 5.2 创建：create-or-get

```python
async def create_or_get(session, *, row_fields) -> tuple[ApprovalRequest, bool]:
    key = row_fields["idempotency_key"]
    try:
        async with session.begin_nested():   # SAVEPOINT
            row = ApprovalRequest(**row_fields)
            session.add(row)
            await session.flush()            # 在这里触发唯一冲突
        return row, True
    except IntegrityError:
        # savepoint 已回滚，外层事务仍可用
        existing = await session.scalar(
            select(ApprovalRequest).where(
                ApprovalRequest.idempotency_key == key
            )
        )
        if existing is None:
            raise                            # 不是我们认识的冲突
        if existing.args_hash != row_fields["args_hash"]:
            raise ApprovalKeyCollision(...)  # key 相同但语义不同 → 409
        return existing, False
```

关键点：

- **不能先 SELECT 再 INSERT** 作为正确性保证（任务书明确禁止）。
- 用 `begin_nested()`（SAVEPOINT）而不是整段 `rollback()`：
  只回滚插入，不波及调用方同一事务里的其他写入。
- PG 在唯一冲突后事务会 abort；savepoint 回滚后外层事务仍可继续。
- 冲突后必须做**语义校验**：同 key 但 `args_hash` 不同，说明逻辑错误或碰撞，不能静默复用。

### 5.3 决策：条件 UPDATE

```sql
UPDATE approval_request
SET approval_status = :action,
    decided_at = :now,
    decided_by = :who,
    decision_reason = :reason,
    updated_at = :now
WHERE id = :id
  AND approval_status = 'pending'
```

结果处理：

| rowcount | 再读到的状态 | 返回 |
|---|---|---|
| 1 | — | `APPLIED` |
| 0 | 不存在 | 404 `NOT_FOUND` |
| 0 | 与本次动作相同 | 200 `IDEMPOTENT`（重复点击/重试） |
| 0 | 与本次动作不同 | 409 `CONFLICT`（先批后拒 / 先拒后批） |

原子性由 `WHERE ... AND approval_status='pending'` 保证，不依赖应用层锁。

### 5.4 执行认领：条件 UPDATE

```sql
UPDATE approval_request
SET execution_status = 'running',
    execution_started_at = :now,
    updated_at = :now
WHERE id = :id
  AND approval_status = 'approved'
  AND execution_status = 'not_started'
```

`rowcount == 0` → 拒绝执行（未批准 / 已执行 / 正在执行）。

### 5.5 并发结果

| 场景 | 结果 |
|---|---|
| 两个请求同时创建同一审批 | 一个成功，一个走冲突分支返回同一行 |
| 两个请求同时批准/拒绝 | 一个 `APPLIED`，一个 `IDEMPOTENT` 或 `CONFLICT` |
| 两个执行器同时认领 | 只有一个 `rowcount==1`，另一个被拒 |
| 批准与执行同时发生 | 执行认领要求 `approved`，未批准时 `rowcount==0` |

## 6. 统一执行器

### 6.1 入口

```text
execute_approved(approval_id) -> ExecutionOutcome
```

**全项目只允许这一个函数调用高风险工具。**

### 6.2 顺序（重要：事务要短）

```text
1. 短事务 A：
   - 读取审批行
   - 校验 approval_status == approved
   - 校验 execution_status == not_started
   - 校验 args_hash == sha256(args_json)
   - 原子认领 → running
   - commit
2. 事务外：
   - 重新解析 target_path，确认仍在 sandbox 内
   - 文件类：
       old_hash 非空 → 当前文件 hash 必须相等
       old_hash 为空 → 目标文件必须仍不存在
   - 执行工具
   - 文件类：读回并比对写入内容 hash
3. 短事务 B：
   - succeeded / failed / unknown
   - 写 execution_result / execution_error / finished_at
```

**不要在事务里做文件 I/O 或调 LLM。** 否则锁持有时间不可控。

### 6.3 失败分类

| 情况 | 结果 |
|---|---|
| 认领失败（未批准/已执行） | 拒绝，不写文件 |
| `args_hash` 不一致 | `failed`，记 `error="args tampered"` |
| 路径越界 | `failed`，不执行 |
| `old_hash` 不匹配 | `failed` + 审批置 `cancelled`，要求重新审批 |
| 工具明确抛错且未写盘 | `failed` |
| 写盘后读回不一致 / 超时 | `unknown`，**不重试** |

### 6.4 旧的整批拒绝语义

当前 `handle_review_fn` 的逻辑是"同批有一个拒绝 → 整批不执行"。
新模型支持逐条决策，建议改成**逐条执行**：批准的执行，拒绝的回填拒绝消息。
这是语义变更，需要确认（见 §12 Q4）。

## 7. 图流程改造

### 7.1 目标结构

```text
START
 └─▶ prepare_node
      └─▶ model_node
           ├─(无 tool_calls)─▶ END
           └─(有 tool_calls)─▶ prevalidate_node
                                  ├─(未知工具)──────▶ 回填错误消息 → model_node
                                  ├─(全安全)────────▶ tools_node ──▶ model_node
                                  └─(含高风险)──────▶ 建/取审批记录 → review_node
review_node
 └─ interrupt({type, batch_id, approvals:[...]})
      └─(resume)─▶ execute_node
                     ├─ 逐条读 DB
                     ├─ approved → execute_approved()
                     ├─ rejected → 回填 ToolMessage
                     └─▶ model_node
```

### 7.2 关键语义

- `prevalidate_node` **必须注册**，它是唯一写 `pending_reviews` 的地方。
- `should_continue` 不再直接送 `review_node`；它只决定"结束 / 去 prevalidate"。
- `review_node` 只做两件事：把载荷交给 `interrupt()`；把 resume 值写入 `decision_reviews`。
- `execute_node` 不信任 `decision_reviews` 的内容，只把它当作"恢复信号"；
  真正的决策从数据库读。
- 混合批次（安全 + 高风险）：**整批等审批**，批准后由 `execute_node` 统一执行
  安全工具（直接调用）与高风险工具（走执行器），并为每个 `tool_call` 回填 `ToolMessage`。
- 全安全批次：仍走 `ToolNode`，保持现有行为。

### 7.3 interrupt 载荷

```json
{
  "type": "review_request",
  "batch_id": "uuid",
  "approvals": [
    {
      "approval_id": "uuid",
      "tool_call_id": "call_xxx",
      "tool_name": "write_file_tool",
      "path": "notes/demo.txt",
      "is_new_file": false,
      "old_hash": "abc...",
      "added": 3,
      "removed": 1,
      "diff": "--- a/...\n+++ b/..."
    }
  ]
}
```

- 载荷**只用于展示**，不用于执行。
- `approval_id` 是前端决策的唯一句柄。

### 7.4 resume 载荷

```json
{"batch_id": "uuid"}
```

- 不带参数、不带工具名、不带决定。
- 决定通过 `POST /agent/approvals/{id}/decision` 先落到数据库。
- resume 只负责"让图继续跑"。

### 7.5 恢复前置校验

`POST /agent/resume` 必须：

1. 校验 thread 归属；
2. 校验图当前确实处于 interrupt（`aget_state(config).interrupts` 非空）；
3. 校验该 `batch_id` 下**没有 `pending` 记录**；
4. 校验提交的 `batch_id` 与当前中断载荷一致；
5. 再 `astream(Command(resume=...))`。

任一条不满足 → 409，不恢复。

## 8. API

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/agent/approvals?thread_id=&status=` | 查询审批记录 |
| POST | `/agent/approvals/{approval_id}/decision` | 批准/拒绝 |
| POST | `/agent/resume` | 恢复被中断的图 |

决策请求体：

```json
{"action": "approve", "reason": null}
```

- 只允许 `approve` / `reject`（V1 不支持 edit）。
- 不接受 `args`、`tool_name`、`path` 等字段；出现即 422。
- 重复相同决策 → 200（幂等）；相反决策 → 409。

### 8.1 新消息与挂起审批

当线程处于 interrupt 且仍有 `pending`：

- **方案 A（推荐，V1）**：`POST /agent` 直接返回 409，提示先处理审批。
  简单、不会静默放行。
- 方案 B：自动把旧 `pending` 置 `cancelled` 再开新轮。
  更"顺滑"，但要额外处理旧 checkpoint。

V1 建议 A；B 留到有 UI 之后再评估。

### 9.2 阶段 3：幂等与执行安全

| 步骤 | 内容 | 验收 |
|---|---|---|
| 3-1 | 稳定幂等键 + 规范化 JSON | 同请求重复投递 key 一致 |
| 3-2 | savepoint + IntegrityError + 语义校验 | 并发创建只留一行，无异常冒泡 |

| 3-4 | 执行认领条件 UPDATE | 并发只执行一次 |
| 3-5 | `args_hash` / `old_hash` / 路径复检 | 参数篡改、文件变更被拦截 |
| 3-6 | `unknown` 状态 + 禁止自动重试 | 不确定结果不被二次执行 |
| 3-7 | 新消息/挂起策略 | 不出现静默放行 |

## 11. 风险与未验证

### 11.1 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| `backend/` 与 `apps/desktop/` 双份代码 | 修一处漏一处 | 冻结 backend，只改 desktop |
| 先接 `tools_node` 后加校验 | 出现无审批写盘窗口 | 先拆高风险工具，再接审批 |
| 客户端篡改参数 | 批准内容与执行内容不一致 | resume 不带参数；执行只读 DB |
| `args_json` 过大 | 写入文件的全文进 DB | 设置单参数长度上限；后续可拆分 |
| SQLite 并发写 | `database is locked` | WAL + 短事务 + 单实例锁 |
| PG 冲突后事务 abort | 后续查询全失败 | savepoint 回滚 |
| checkpoint 与 DB 不一致 | 有记录但无法恢复 | DB 为准；提供按 thread 查询 |
| 无迁移工具 | 表结构变更难 | 本轮只新增表；后续再引入 Alembic |

### 11.2 未验证（施工时必须先验）

1. `tool_call_id` 在 resume 前后是否稳定（决定幂等键是否成立）。
2. `interrupt()` 在编译子图中冒泡到主管图（`docs/9.11` 记录为已验证，需复验）。
3. `rowcount` 在 aiosqlite / asyncpg 下对条件 UPDATE 的返回值。
4. SQLite `SAVEPOINT` + `IntegrityError` 的实际行为。
5. PG 与 SQLite 的类型/时间精度差异（若将来做 web）。
6. 真实 PG / Redis 连通性（阶段 1 未连接）。

## 14. 施工顺序的理由

1. **先修链路，再建表。**
   如果先建表，所有审批测试都只能直接调 service 层"模拟通过"，
   无法证明真实链路可用——这正是任务书禁止的。
2. **先拆高风险工具，再加审批。**
   否则在接线的一瞬间会出现"无审批写盘"的窗口。
3. **先加唯一约束，再写冲突处理。**
   约束是正确性的地板；先有地板，再谈地板上怎么走路。
4. **一次只修一个雷，每修一次立刻重跑。**
   沿用 `docs/NOTES.md` §五的纪律。
