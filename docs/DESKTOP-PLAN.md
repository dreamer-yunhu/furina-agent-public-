## §0 产品定义

### 一句话

> **一个装在 Windows 上、双击即用的 AI 桌面助手。第一版做「芙宁娜角色扮演对话 + 代码 agent（带人工审批）」双模式。**

### 三类目标（按优先级）

| 优先级 | 目标 | 判据 |
|---|---|---|
| **1** | **自用** | 你自己每天愿意打开它 |
| 2 | 求职作品 | 能讲清架构取舍、有可演示的东西 |
| 3 | 开源 | 别人能装上并跑起来 |

### 明确的【不是目标】（本节比上面重要）

不写这一节，后面所有取舍都没有依据。

| 不做 | 理由 |
|---|---|
| **不做本地模型兜底** | 用户首次进入**必须配置一个大模型密钥**。打包模型会让安装包变成几个 GB，且要解决 GPU 兼容 —— 那是另一个项目的工作量 |
| **不做服务端托管密钥** | 用户自带密钥（BYOK）。服务端不碰 token、不承担成本、不需要计费系统 |
| **一阶段不支持非 OpenAI 兼容格式** | 只支持 `base_url` + `api_key` + `/v1/chat/completions` 的服务商 |
| **不做多用户** | 单机应用。没有注册/登录/顶号/黑名单的语义 |
| **不做 Docker / 不让用户装任何服务** | 这是"开箱即用"的定义 |
| **不做 RAG 的独立进程（第一版）** | 见 §4 决策表 |
| **不做 Web 版（本阶段）** | Web 版是副产品，`furina-core` 会为它保留共用能力，但本阶段不投精力 |

### 三个验收锚点

**每个都是可执行的，不是形容词。** 这是全文唯一能判断"做完了没有"的东西。

| 锚点 | 判据（可执行） | 上次验证 |
|---|---|---|
| **A. 骨架贯通** | 在一台**没装 Python、没装任何数据库**的 Windows 机器上，双击安装包 → 打开窗口 → 填入密钥 → 校验通过 → 说一句话并得到回复 | ❌ 未验证 |
| **B. 芙宁娜可对话** | 连续对话 3 轮，她**能引用 1 条来自语料的世界观知识**（而不是泛泛而谈） | ❌ 未验证 |
| **C. 审批闭环** | agent 提出写文件 → 弹出 diff 预览 → 批准后**文件真的出现在沙箱目录**；拒绝后**真的没出现**且模型收到打回 | ❌ 未验证 |

> ⚠️ **B 和 C 是产品的核心价值。A 是它们能否交付的前提。**

## §2 三个未验证的假设（按"不成立时的破坏力"排序）

> **这三个假设决定了整个产品形态能不能成立，而它们一个都没验过。**

### 假设 A：Python 后端能被打成可执行文件，并在**没装 Python 的机器**上跑

| | |
|---|---|
| **怎么验** | 最小 FastAPI 服务 → PyInstaller/Nuitka 打包 → 在无 Python 环境的机器上运行 |
| **不成立时** | ❌ **整个"开箱即用"形态要重新设计**（退回"本地 Web 应用"：用户装一次、浏览器打开） |
| 破坏力 | ⭐⭐⭐ **最高** |
| 状态 | ❌ 未验证 |

### 假设 B：Tauri 能可靠地管理 Python 子进程

| | |
|---|---|
| **怎么验** | Tauri 拉起 Python → 探活 → 正常退出回收 → 强杀后无僵尸 → 启动时清理上次残留 |
| **不成立时** | 用户体验崩坏（关不掉、重复启动、端口冲突） |
| 破坏力 | ⭐⭐ |
| 状态 | ❌ 未验证 |

### 假设 C：密钥校验与安全存储

| | |
|---|---|
| **怎么验** | 保存前发一次最小请求校验 → 失败给可操作提示 → `grep sk-` 日志零命中 |
| **不成立时** | 用户首次体验失败、或密钥泄漏 |
| 破坏力 | ⭐⭐ |
| 状态 | ❌ 未验证 |

> **C 是"防呆"的核心**：把"密钥错误"的发现时机从**用户第一次提问时**提前到**保存那一刻**。
> 不校验 → 用户填完点开始 → 聊第一句 → 报 `AuthenticationError` → **他不知道是密钥错还是软件坏**。

> **每个里程碑必须有可执行判据。判据是形容词的，一律不合格。**
> 顺序原则：**先消除破坏力最大的未知，再堆功能。**

| 里程碑 | 内容 | 可执行判据 | 状态 |
|---|---|---|---|
| **M0 骨架贯通** | Python 打包 + Tauri 拉起 + 首次配置页 + 密钥校验 + 日志脱敏 + 单实例锁 + 三层防护骨架 | **锚点 A**：无 Python 机器上装完 → 填密钥 → 校验通过 → 说一句话得到回复（agent 图可以只有一个 echo 节点） | ❌ |
| **M1 芙宁娜可对话** | roleplay 模式打通：人设注入 + 流式输出 + 本地历史落盘（SQLite） | 浏览器/窗口里连续聊 3 轮，历史重开后还在 | ❌ |
| **M2 RAG** | 那 125 KB 语料接通：切块 → embedding → LanceDB → 检索 → 拼进 prompt | **锚点 B**：她能引用 1 条世界观知识 | ❌ |
| **M3 审批闭环** | HITL 全链路：修 `execute_node` → 接 `handle_review_fn` → 恢复入口 → 前端 diff 预览 | **锚点 C**：批准后文件真出现；拒绝后真没有 | ❌ |
| **M4 存储本地化收尾** | checkpoint 抽成自家仓储接口，SQLite 实现落地，去掉 PG 依赖 | desktop 依赖里**没有 psycopg**，且 `import psycopg` 失败 | ❌ |
| **M5 分发** | 安装包 + auto-update + 首次运行引导 | 陌生机器按 README 走一遍能通 | ❌ |

### 关于顺序的两个说明

**① 为什么 M0 在最前**：它验证的三个假设是**后五个里程碑的交付前提**。若 A 不成立，M1-M5 全部无法交付给用户。

**② 为什么 M1 排在 M3（审批）之前**：M1 交付的是"**一个真的能用的产品**"（能聊天、数据存本地），它自身就是完整价值。而 M3 是"给能用的产品加能力" —— 更复杂（中断/恢复/审批 UI），但没有它产品依然可用。
**且 M3 是你求职故事里最值钱的一块，值得单独一轮专注，而不是夹在别的活里做一半。**

## §5 技术选型要点

### 5.1 RAG（第一版）

**结论：Python 进程内嵌 LanceDB，不做独立进程。**

| 项 | 决定 |
|---|---|
| 检索引擎 | **LanceDB**（嵌入式，自带向量 + 全文检索/BT 语义） |
| 形态 | **进程内**，不独立成 Rust 服务 |
| embedding（起步） | 走 API（语料 125 KB，一次性入库） |
| embedding（最终） | 推迟到 M0 打包验证之后 —— **别污染"能不能打包"这个实验** |
| 语料 | `backend/knowledge/`，**32 文件 / 125 KB** |

**为什么不做独立进程**：

| 理由 | 说明 |
|---|---|
| 性能不是瓶颈 | 桌面端检索频率≈0，且 LLM 调用要 2 秒，检索只占 0.5% |
| **RAG 的质量瓶颈不在引擎** | 在**切块策略**——而那个只能靠跑起来调 |
| 独立进程的代价不划算 | 第二个子进程生命周期 + IPC + 跨进程错误传播 + CI 多一条 Rust 构建线 |

**⚠️ 唯一现在要做的准备工作**（10 分钟）：

```
agent 节点 → 一层接口 retrieve(query, domain) → 实现（LanceDB）
```

**不要 `import lancedb` 散进 agent 节点。** 将来换 Rust 服务时，改的是这一个文件。

**⚠️ 发布期的验收标准（现在定，免得到时返工）**：

准备 **10~20 个"问题 → 期望检索到的段落"的快照**。每次改切块参数跑一遍看命中率。
**没有它，你会陷入"感觉答得不好 → 改 prompt → 还是不好 → 改切块 → 说不清哪个起作用"。**

### 5.2 三层防护与防呆

> **BYOK 之后，"限流"保护的对象从"你"变成了"用户自己"和"这台机器"。**
> 它是**防呆**，不是**入口防御**。

```
层1  并发上限     asyncio.Semaphore        保护本机（内存/连接/CPU）     超限 → 排队
层2  速率限流     LocalTokenBucket          保护额度（防手抖与重试风暴）  超限 → 拒绝/等待
层3  成本软提示   本地累计 token 计数       到阈值 → 只提示，不硬拦
```

**为什么第 3 层只提示不硬拦**：那是**用户自己的钱**，你没权力替他决定"今天不能再用了"。
硬拦会让他觉得"这软件坏了"。

**⚠️ 多实例陷阱**：`LocalTokenBucket` 是进程内状态。用户双击两次 → **两个桶 → 速率翻倍**。
→ **必须做单实例锁**（检测到已有实例则激活窗口并退出新进程）。它顺带解决"用户开两个窗口以为是一个"。

**⚠️ 重试必须走同一个令牌桶**（每次重试也取令牌 + 指数退避）。
否则"我加了限流"会被自己的重试逻辑绕过 —— 很隐蔽的一类。

**防呆清单**：

| # | 场景 | 处理 |
|---|---|---|
| 1 | 空消息 / 超长输入 | 前端拦 + 后端也拦 |
| 2 | 连续点发送 | 请求进行中禁用按钮 |
| 3 | **密钥 401** | 说"密钥无效，请到设置检查" + 一键跳设置。**不说 `AuthenticationError`** |
| 4 | **429（撞供应商限速）** | 指数退避重试 + 提示"请求太频繁，稍后自动重试" |
| 5 | 网络断开 | 明确说"网络不可用"，不说"未知错误" |
| 6 | 重复实例 | 单实例锁 |
| 7 | 重试风暴 | 重试计入令牌桶 |
| 8 | 成本 | 累计 token，超阈值提示（不拦） |

### 5.3 配置与密钥

**配置项（全部用户可填，无智能默认）**：

```
base_url   [ https://api.deepseek.com/v1   ]
api_key    [ sk-...                        ]
model      [                                ]  ← ★ 不给默认值，各服务商命名不同
```

> **补一个"从服务商拉取模型列表"按钮**（`GET /v1/models` 是 OpenAI 兼容标准端点）。
> 猜错模型名产生的报错很难懂，宁可让用户选。

**密钥存储**：本地配置文件（`%APPDATA%\furina-agent\config.json`，权限仅当前用户）。
**先用文件，不做 OS 密钥链** —— 后者要引依赖、要处理不可用回退，对本地应用收益有限。

**⚠️ 密钥泄漏的三个入口**：

| 入口 | 防护 |
|---|---|
| **日志**（最大风险） | 现状是全局 `DEBUG` + `httpx`/`openai` 在 DEBUG 下会打印 `Authorization` 头。**必须**：降级为 `INFO` + 第三方库静默。**判据：装完后 `grep sk- 日志文件` 零命中** |
| 报错消息 | 只说"密钥无效"，不回显密钥内容 |
| 打包 | **别把仓库根 `.env` 一起打进安装包**（"打包整个目录"是常见做法，`.env` 会跟着走） |

**能力探测**：校验密钥的同时，顺手发一个**带 `tools` 的最小请求**。
若失败 → 明确告知"该服务商不支持工具调用，agent 模式不可用，但可以正常聊天"。

> **为什么值得做**：`tools` / function calling 是 OpenAI 兼容格式里**最可能不兼容的一项**。
> 这比让用户在 agent 里撞一堆莫名错误好得多。

### 5.4 只支持 OpenAI 兼容格式 —— "兼容"的定义

| 能力 | 用在哪 | 必需？ |
|---|---|---|
| `POST /v1/chat/completions` | 对话 | ✅ 必需 |
| `stream: true` + SSE `delta` | 流式 | ✅ 必需 |
| **`tools` / function calling** | **agent 工具调用** | ⚠️ **agent 模式必需，roleplay 不需要** |
| `POST /v1/embeddings` | RAG | ⚠️ 可选（见 §5.1） |
| `GET /v1/models` | 模型列表按钮 | ⭕ 锦上添花 |

> **代码层面几乎不用改** —— `langchain_openai.ChatOpenAI` 本来就是 OpenAI 兼容。
> **真正的工作量在配置界面和错误处理。**

## §6 风险与退出条件

> 原 `PLAN.md` 的路线图**只有成功路径**（5 个阶段，0 个停止条件）。本节补上。

| # | 风险 | 触发条件 | 怎么发现 | 应对 |
|---|---|---|---|---|
| 1 | **打包方案走不通** | M0 假设 A 失败 | 换机器实测 | **换形态**：退回"本地 Web 应用"（用户装一次、浏览器打开） |
| 2 | Python 进程变僵尸 | Tauri 崩溃/强杀 | 任务管理器 | 进程守护 + 启动时清理残留 |
| 3 | 多实例 → 限流失效 | 用户双击两次 | 单实例锁生效 | 单实例锁 |
| 4 | 密钥泄漏进日志 | 日志里有 `sk-` | `grep sk-` | 脱敏 + 降级日志级别 |
| 5 | **Tauri 前端工作量被低估** | 仓库前端是零 | —— | **前端是独立主线，不能当附属**（见下） |
| 6 | LangGraph SQLite saver 不可用 | M4 实测 | 跑一次中断恢复 | 换自管存储（触发 §4.4 元决策③的重新评估） |

### ⚠️ 风险 5 要单独强调

**仓库里前端是零**（无 `package.json` / 无 `src/` / 无 `Cargo.toml` / 无 `tauri.conf.json`）。

做桌面版等于**同时开两条主线**：**Python agent + Tauri UI**。

**这个工作量可能比 agent 那一半还大**，而在 `PLAN.md` 里它被写成"阶段 3"的一行字。

**M0 的应对**：**用最简 HTML 顶住**（复用仓库根已有的 `agent_demo.html`，它已能跑 SSE），
**把 Tauri UI 推迟到 M1 之后** —— 因为 M0 要验的是"打包 + 进程管理"，不是"UI 好不好看"。

## §7 与当前项目的差距（分阶段）

> 这一节回答："**现在离第一版差在什么地方**"。

| 前端 | ❌ 零 | M0 用 `agent_demo.html` 顶住 |

**M0 的结论**：**三个假设全部未验证，打包与进程管理是从零开始。这是全项目最大的未知。**

### M1 差距（芙宁娜可对话）

### M3 差距（审批闭环）

| 要做的 | 现状 |
|---|---|
| `execute_node` 实现 | ❌ **空函数体，且从未 `add_node`** |

| 修 `handle_review_fn` 的三处裸 `raise` | ❌ 现存 bug（裸 raise → `RuntimeError`，后面的回代逻辑不可达） |
| 恢复入口 `POST /agent/resume` | ❌ 是 `pass` |
| 修 `decision_review` vs `decision_reviews` 拼写 | ❌ 现存 bug（**静默不共享**） |
| 修 `classify_tool_calls` 的 `set(dict)` | ❌ 现存 bug（`TypeError: unhashable`） |
| 修 prompt 硬编码路径 | ❌ 实测 1 处 |
| 前端 diff 预览 | ❌ 零 |

**M3 的结论**：**契约和逻辑骨架都在，但链路断了 4 个地方，且前端要从零做。**

### M4 差距（存储本地化）

| 要做的 | 现状 |
|---|---|
| checkpoint 仓储接口 | ❌ 零（**saver 调用已散在 4 个文件里**） |
| SQLite saver 实现 | ❌ 零 |
| 去掉 psycopg 依赖 | ❌ 现在 desktop 显式依赖它 |
| 表结构与迁移 | ❌ 现在靠 `SQLModel.metadata.create_all`，且**拆表后会静默漏表** |

### 总结：差距的三个层次

| 层次 | 内容 | 性质 |
|---|---|---|
| **① 从零开始的** | 打包、进程管理、配置页、前端、RAG、SQLite 存储 | **新工作量，占大头** |
| **② 链路断的** | HITL 的 4 处断点、SSE 桥、6 个占位节点 | 修补 + 接线 |
| **③ 已有的** | `furina-core`（797 行已验证）、coder 子图 ReAct 循环、审批契约 | **可直接复用** |

> **一句话**：**第 ③ 层比你以为的多（core 是实打实验证过的），但第 ① 层比 `PLAN.md` 里写的多得多 —— 而那才是"开箱即用"的成败所在。**
