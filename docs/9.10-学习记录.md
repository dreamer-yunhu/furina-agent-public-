## 二、调研结论（对齐过 GitHub + 官方文档）

### 2.1 Agent「写本地文件」的三派主流方案

| 派系 | 代表 | 本质 | 评价 |
|---|---|---|---|
| A. 全量写回 | `langchain-community` FileManagementToolkit | 模型给整个文件内容，工具原子覆盖 | 官方范本，适合小文件 |
| B. 结构差分包 | OpenAI `apply_patch`（ApplyPatchOperation） | 模型只吐「create/update/delete 操作 + diff」，宿主引擎落盘 | **2026 事实标准**，对应契约第三刀 |
| C. Shell 执行 | LangChain 1.x `ShellToolMiddleware` | agent 自己跑命令/sed/git | 灵活但风险最高；默认 `HostExecutionPolicy` 裸跑无沙盒 |

**关键结论**：契约 §八 第三刀选 B 派方向正确；A 派只当验证期脚手架，最终要过渡到自写工具。

### 2.2 `langchain-community` 已 sunset（重要决策依据）

- 官方 issue #674（2026-05）：`langchain-community` **停维护**，不再接新集成/新特性。
- 官方迁移指引：**coding agent 直接在应用代码里实现工具更简单**，或走 MCP。
- 本地实证：`langchain` 1.3.18 / `langchain-core` 1.6.1 **均无 file_management 模块**，只有 community 提供 → 但 community 迟早要弃。
- **今日拍板**：弃用 toolkit 包装，自写 BaseTool 子类文件工具（与官方迁移方向一致）。

## 三、概念突破（今天真正学会的）

> 卡点本质：**非科班，OOP「类 vs 实例」没立起来**，导致 args_schema、说明书、继承全糊在一起。

1. **工具的本质**：大模型是嘴不是手。工具 = 一句话（模型说）+ 一段代码（机器做）。模型喊工具名 → LangChain 翻译 → 调 `_run` → 结果回喂模型。
2. **说明书写给模型、代码写给机器，两半要分开**。说明书（args_schema + description）最终转 JSON 给模型；`_run` 是真 Python 逻辑。
3. **类 vs 实例 / type[X] 语义**：类是「空白表单模板」，实例是「填好的某张表」。`args_schema` 要的是**类**（要字段定义生成 schema），不是实例（只有具体值）。注解装类用 `type[BaseModel]`（BaseModel 家族的类），装实例才直接写 `BaseModel`。
4. **`type[BaseModel]` 是「BaseModel 或其子类的类」** → 多态：ReadFileInput 是 BaseModel 子类也能放进去。
5. **不抛异常、返回字符串**：工具 `_run` 错误必须转字符串返回给模型（让模型自己纠错），抛异常会崩 agent —— 与 HITL 铁律「interrupt 不包 try/except」一致。
6. **继承 = 规矩写一遍**：基类统一权限边界，儿子动手前先问爸爸（调基类裁判方法）。

## 六、给自己的提醒

1. **最小可执行版铁律**：砍掉黑名单、HITL、多余工具、为「将来的第二个使用者」做的抽象。等真遇到再重构（重构成本低，预判成本高）。
2. **每次只引入一个变量**：别让「验证自写工具能否跑通」和「安全做全」两个问题搅在一起。
3. 安全分级直觉正确：读可放宽、写/删必严；破坏力越大门槛越高。最小版连 delete 都不写（能力即边界）。
4. 今天从「报错 → 雾水 → 能自己设计 Input 和基类字段」已是实打实进步，卡在路径解析是正常台阶，不是退步。
