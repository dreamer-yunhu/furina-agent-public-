## 一、核心机制（两句话）

1. **中断靠"谁接住"定归属** → 所以**只能有一个 checkpointer**（最外层）。子图自己编译 checkpointer，中断就被它自己接住，主管永远看不见。
2. **消息隔离靠"字段名不同"** → **不靠独立线程**。

> 依据：官方迁移指南 —— `compile only the outermost graph with a checkpointer, leave subagents without their own checkpointer`
> 你的 `coder.py:76` 注释已经写对了第 1 条。

⚠️ **已更正**：上一轮说"官方 supervisor 用 uuid5 给子代理派生独立 thread_id"——那是**旧库** `langgraph-supervisor` 的做法，该库已不维护。新规则相反。

## 二、图结构

```
        主管 State                         coder 子图 State
   ┌────────────────────┐            ┌──────────────────────┐
   │ messages  ●●●●●●●  │            │ internal_messages ●●●│  ← 私有
   │ user_profile       │            │                      │
   │ retrieved          │            │                      │
   │ route              │            │                      │
   │                    │            │                      │
   │ subagent_task   ───┼────────────┼──▶ subagent_task     │  ← 共享·入
   │ subagent_result ◀──┼────────────┼─── subagent_result   │  ← 共享·出
   └────────────────────┘            └──────────────────────┘
```

**依据**：官方 subgraph 文档 —— 只要子图**接口（输入/输出 schema）**被遵守，父图不需要知道子图内部细节。

**⚠️ 关键前提**：这个设计**建立在"父图声明、子图没声明的 key，子图看不见"之上**。若不成立 → 整套方案推翻。**这就是实验 A-6。**

## 三、主管 State（参考骨架，非定稿）

| 字段 | 类型方向 | 谁写 | 谁读 | 说明 |
|---|---|---|---|---|
| `messages` | `Annotated[list, add_messages]` | 入口 / 生成节点 | 生成节点 / 持久化 | **唯一的对话真相** |
| `user_profile` | `UserProfile \| None` | 画像节点 | 生成节点 | ⚠️ 序列化安全，**不能塞 ORM 对象** |
| `retrieved` | `list[RetrievedChunk]` | 检索节点 | 生成节点 | 每 chunk **带 id**——为化学 Agent 引用溯源留路 |
| `route` | `Literal[...] \| None` | 路由节点 | 条件边 | 与 `mode` 的关系待判 |
| `subagent_task` | `str \| None` | 调度节点 | coder 子图 | 共享通道·入 |
| `subagent_result` | `str \| None` | coder 子图 | 调度节点 | 共享通道·出 |

**三个刻意选择：**

- **`mode` 故意不放进来**。会话级定死 → 它是 `config.configurable` 的东西；每轮可变 → 它和 `route` 是同一个东西。放进来 = 默认两个都要 = 浪费。
- **`subagent_task` / `subagent_result` 是通用一对，不是每个子代理一对**。等真出现第二个子代理**且需要并行**时再拆。
- **两个都先用 `str`**。还没写出 coder，不知道它该汇报什么结构，**让接口先粗**。

## 四、coder 子图 State（参考骨架，非定稿）

| 字段 | 类型方向 | 谁写 | 谁读 | 说明 |
|---|---|---|---|---|
| `subagent_task` | `str \| None` | 继承自主管 | 起始节点 | **名字必须与主管逐字一致**才共享 |
| `subagent_result` | `str \| None` | 收尾节点 | 回传主管 | 同上 |
| `internal_messages` | `Annotated[list, add_messages]` | model / tools 节点 | model 节点 | **私有**，⚠️ 与主管 `messages` 不串待 A-6 确认 |

**⚠️ 为什么故意不叫 `messages`**：若父子两边都声明 `messages`，按官方文档二者会**共享同一 channel**。**名字不同是零成本保险，别赌框架行为。**

**⚠️ `internal_messages` 的残留坑**：`add_messages` 的语义是**追加 / 按 id 合并**，不是替换。子图 channel 按 namespace 存在你父图**同一个 thread** 下 → **第二次调用 coder 时，上一轮的消息还在**。
→ 需要"进入子图先清空"的机制。**去 `langgraph/graph/message.py` 里找删除消息的机制（`RemoveMessage` 及相关哨兵常量）**，自己确认。

## 六、坑（精简版）

**坑 1 · "节点重跑"≠"工具重跑"**
langgraph 的 resume 是**节点级重跑**，不是从断点精确续执行。`tools_node` 里若一轮有 3 个工具调用、只有第 2 个被中断，重跑时**第 1 个会再执行一遍**。
→ 非科班陷阱：直觉是"暂停/继续"，实际是"回滚到节点开头/重放"。
→ 副作用检查：**`model_node` 重跑会再调一次 LLM，重复计费。**

**坑 2 · "静默通过"传染到前端**
A-3 的失败形态是"图正常跑完，只是没中断"——**和"确实没有需要审批的操作"长得一模一样**。
→ `[流-3]` 的"run 结束"事件必须带字段说明：**正常结束** 还是 **带 pending 中断结束**。否则前端区分不出来，你会调一周。

**坑 3 · 开源分发灾难（核心痛点）**
整套设计的调试成本全压在"能连 PG checkpointer + 能 dump thread 状态"上。穷哥们 clone 仓库只跑 `uv run`，**连"图挂在哪个中断上"都看不到**。
→ **建议**：先写一个最小 **thread 状态转储脚本**（读 thread_id → 打印挂起状态）。**既是你的调试工具，也是给开源用户的自白书**，成本极低、价值极高。**比先做前端 UI 省钱。**

### 8.1 向量量化四旋钮

| 旋钮 | 何时生效 | 说明 |
|---|---|---|
| `num_bits` | **建索引时** | ⚠️ **建完固定，不可在线改，改需重建** |
| `nprobes` | 查询时 | 代价近似线性；过拐点后收益递减 |
| `refine_factor` | 查询时（默认关） | 回表读原始向量重排；**随机 IO，与检索串行，延迟直接叠加** |
| `approx_mode` | 查询时 | **Fast / Normal / Accurate**，三档**即时切换，索引无需改动** |

**数字锚点**（LAION 10M×768d，nprobes=64，并发 32，cosine）：

| 索引 | recall@10 | QPS | p99 (ms) |
|---|---|---|---|
| IVF_RQ · 5 bit | **0.963** | 1,522 | 31.9 |
| IVF_RQ · 1 bit | 0.763 | 1,524 | 31.1 |
| IVF_PQ · 96×8 | 0.690 | 1,075 | 40.7 |
| IVF_SQ · 8 bit | 0.956 | 653 | 78.5 |

**可用结论**：1 bit → 5 bit，召回 +20pp，p99 只多 2.3%，QPS 基本持平；代价在存储（32× → 6.4× 压缩）。
→ **默认起点取 5 bit**；`approx_mode` 先 Normal，出问题再调。

### 8.2 Q7 向量库选型 —— 判据

| 维度 | Serving-first（向量数据库） | Cost-first（向量湖） |
|---|---|---|
| 检索触发 | 持续在线 | 按需 |
| 资源成本 | 容量按峰值规划，常驻计费 | 用时付费，空闲近零 |
| I/O 路径 | 内存 / 本地盘 | 对象存储冷路径 |
| 查询 / SLA | 小 TopK · 高 QPS · 毫秒 p99 | 大 TopK · Batch · 秒~分钟 |
| 典型场景 | **RAG · 语义搜索** | 去重 · Hard Negative · 语料筛选 |

**判断：我们是 RAG + Small TopK → Serving-first。**
→ 向量湖那一整套（分布式建索引、segmentation、ZoneMap、Lance Namespace）**与需求无关，不要引入**。
→ Q7 尚需回答的仍是：**ChromaDB vs pgvector vs 本地 LanceDB**（三者都属 Serving-first，比的是运维成本，不是架构类别）。

### 8.3 两条排除项

1. **Intel AMX 相关优化全部不适用** —— AMX 是 Xeon 专属指令集，本机是 **AMD Strix Halo**。会上的 3.89× / 3.46× 一个都搬不过来。
2. ⚠️ **会上的 "Lance" ≠ 你用的 "LanceDB"**
   - 会上：**Lance 格式**用于数据湖，配 Spark/Ray/对象存储，管 PB 级
   - 我们：**LanceDB 库**，`pip install lancedb`，本地目录，管几万~几百万条
   → **不要因为"我在用同一个技术栈"就往上加分布式能力。**
