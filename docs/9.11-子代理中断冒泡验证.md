# 9.11 子代理中断冒泡验证

> 写这一页的原因：supervisor 架构（`coder.as_tool()` 包成工具给主管）里，**coder 内部的 HITL 审批请求能不能传到主管那一层**，是一个**没被验证过的假设**。
> 这个假设如果错了，9.8 记录里的「主管层统一 resume」就不成立，整个 tool-as-agent 的 HITL 设计要退回子图节点路线。
> **在写 supervisor 接线代码之前，先把它验掉。** 预期成本：半天。

---

## 〇、这个实验在回答什么

用装修比方：

| 角色 | 对应 |
|---|---|
| 业主 | 用户（你） |
| 包工头 | 主管 supervisor 图 |
| 电工师傅 | coder 子代理 |
| 打洞 | `write_file` 工具 |
| 电工问"能不能打" | `interrupt()` |
| 你手上唯一那台对讲机 | 主管图的 SSE 流 / checkpointer |

**问题**：电工发出的问题，能不能通过包工头，传到业主唯一那台对讲机上？业主回话能不能只对着包工头说，就传到电工耳朵里？

技术表述：

```
主管 = create_agent(model, tools=[coder.as_tool()], checkpointer=saver)
coder = create_agent(model, tools=[...], middleware=[HITL])   ← 不传 checkpointer
```

→ coder 内部的 interrupt，出现在**主管图**的 `stream` / `get_state()` 里吗？能从**主管** resume 吗？

**为什么必须先做**：这是整个 supervisor + HITL 的地基。地基错了，上面写的每一行都白写。

## 一、开工前的三个前提检查

动手前先把这三条确认掉，否则实验失败你分不清是谁的锅。

- [ ] **前提 1：coder 子图没有自己的 checkpointer**
      官方铁律（9.8 已记录）：只给最外层编译 checkpointer，子 agent 一律不传。
      子图一旦自己编译 checkpointer → 中断不冒泡，变成独立 run。

- [ ] **前提 2：主管是唯一编译 checkpointer 的图**，且 `thread_id` 从最外层传下去。

- [ ] **前提 3：你知道 `as_tool` 是 beta**
      源码：`langgraph/graph/state.py` 上挂着 `@beta_decorator.beta(...)`。
      不影响实验，但影响你对"这条路稳不稳"的判断。

## 四、诊断表（看不到现象 → 怀疑谁）

> 这张表是这个实验最值钱的部分。**失败时对照它，别瞎试。**

| # | 症状 | 最可能的原因 | 先查哪里 |
|---|---|---|---|
| 1 | 图跑完了，`interrupts` 空 | ① `interrupt_on` 里工具名拼错 → **静默放行**（源码 `human_in_the_loop.py` L435 是 `if self.interrupt_on.get(name) is not None`，没 entry 就当自动批准）<br>② middleware 没挂上<br>③ `when` 谓词恒返回 False | `build_graph` 里 middleware 的实参；把它 print 出来 |
| 2 | 中断出现了，但 `Command(resume=...)` 恢复不动 | ① 恢复时用的不是最外层图<br>② `thread_id` 不一致<br>③ resume 载荷形状不对（应是 `{"decisions": [...]}`，源码 L456）<br>④ 用了单值形态而去撞上了多个中断 | resume 那两个参数（graph 对象、thread_id） |
| 3 | `GraphInterrupt` 异常穿到我的 `except` 里 | 中断没被主管图接管 → **极可能是 coder 自己编译了 checkpointer**，或 coder 不是作为子图/工具被调用而是被当普通函数调 | coder 的 `create_agent(...)` 有没有 `checkpointer=` |
| 4 | 卡住了，但 `get_state()` 看不到中断 | 观测位置错了（你在看 `messages` 流，但中断挂 `values` 流） | 原始帧 print 出来对比 |
| 5 | decisions 数量报 `ValueError` | 一次 `AIMessage` 里有 N 个被 gate 的工具 → middleware **打包成一次中断要 N 个 decisions**（源码 L459-464） | 中断里 `action_requests` 的长度 |
| 6 | 前端一直收不到审批请求，但图确实停了 | SSE 桥接层只消费了 `messages`，没消费 `values` | `agent_stream.py` 的 `stream_mode` |

## 五、判定与分支

### ✅ 全绿 → 继续原计划

- 主管层**不需要**为了"能拿到中断"而加 gate（冒泡跟 gate 无关，别绑一起）
- 按 9.8 的落地六步推进
- 补一条**回归测试**：任何给子图加 `checkpointer=` 的改动都必须让这条测试变红

### ❌ 实验 A 失败（机制不通）→ 退回 Plan B

`as_tool` 这条路的冒泡如果不成立，按 9.8 记录的备选路线走：

> 何时切 B（子代理 = 子图节点）：出现"主管必须看子代理内部状态 / 打断它"的需求时再局部切。

**现在就是那个"需求出现"的时刻。** 把 coder 从「工具」改成「主管图里的一级节点/子图」，namespace 自然嵌套，中断天然冒泡。

⚠️ 注意：这会**同时改变 supervisor 的架构选型**（A 路线 → B 路线），需要回到 PLAN §十二 重新拍板。

### ⚠️ A 通、B 不通 → 变量在 middleware 层

说明问题出在 `HumanInTheLoopMiddleware` 而不是 `as_tool`。回实验 A 的骨架，把 interrupt 换成"由 middleware 触发"，逐步逼近。
