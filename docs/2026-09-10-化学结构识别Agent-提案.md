## 〇、一句话定位

**把教材/论文里的化学结构图，变成"可信、可溯源、可人工纠正"的结构化知识。**

用户本人有真实痛点（这是关键——不是编出来的需求）。

技术链路：`图片 → 键线式识别 → RDKit 验证 → 一致性仲裁 → 教材 RAG → 带引用的解释`

## 一、技术选型（已核实）

| 层 | 选型 | 状态 | 证据 / 备注 |
|---|---|---|---|
| 后端 | FastAPI | 🟢 | 复用 furina-agent 技术栈 |
| 单分子识别 | **MolScribe**（主引擎） | 🟢 | `pip install MolScribe`，v1.1.1，PyTorch，Swin-Base 骨干（checkpoint `swin_base_char_aux_1m.pth`） |
| 反应式识别 | **RxnScribe** | 🟢 | 同作者；`predict_image_file(f, molscribe=True, ocr=True)` **内部已调 MolScribe** |
| 副引擎 | **DECIMER 2.0** | 🟡 | `pip install decimer` v2.8.0，**TensorFlow/TPU 栈** → 本机只能 CPU |
| 化学验证 | **RDKit** | 🟢 | 生产级，文档已到 2026.03.4 |
| 结构标准化 | **chembl_structure_pipeline** | 🟢 | MIT，ChEMBL 26 起在用；**入参是 molblock 不是 SMILES** |
| 教材 RAG | ChromaDB + **BGE-M3** | 🟡 | BGE-M3 = 568M 参数（fp16 ≈1.2GB 权重） |
| 前端 | Tauri v2 + React | 🟡 | Python 打包（sidecar）是后期摩擦点 |
| MCP | 后续阶段 | — | — |

### 关键选型结论

1. **MolScribe 为主引擎、DECIMER 为副引擎**——MolScribe 是 PyTorch，能吃本机 ROCm torch；DECIMER 是 TF，上不了这张卡。
2. **RxnScribe 可能让"双引擎编排"变得多余**——它内部已调 MolScribe，且返回 `bbox` + `conditions`(OCR 文本)。先跑通它，再决定是否单独编排。
3. **RAG 必须拆两条正交通道**：
   - 文本语义 → BGE-M3 + ChromaDB（查教材段落）
   - 结构相似 → 分子指纹（Morgan/ECFP4），**不进向量库**
   - ⚠️ **SMILES 不能当文本 embedding**（`CCO` 与 `OCC` 是同一分子，语义距离却很远）

## 二、核心架构判断（三根支柱）

### 支柱 1：OCSR 是感知任务，不是生成任务
LLM **全程不碰"看图出 SMILES"**——那是 MolScribe/DECIMER 的活。
LLM 只负责语义层：命名校对、性质解释、教材条款比对、引用溯源。
→ **模型负责模糊，工具负责精确**（与 furina-agent coder 子图同一思路）

### 支柱 2：RDKit 通过 ≠ 识别正确
`sanitize` 只证明"这是一张合法的分子图"，不证明"它就是图上画的那个分子"。
苯环上少一个甲基，SMILES 一样合法。
→ **必须引入第二个独立信号**（见 §3 钩子4）

### 支柱 3：验证要有确定性兜底
`chembl_structure_pipeline` 做**盐剥离 / 电荷中和 / 互变异构规范化**。
论文里的化合物常是盐酸盐、钠盐形式，不标准化会导致同一分子被当成两个。

## 三、契约设计

### 领域对象（取代 furina-agent 当前的 `State{messages}` 单字段模型）

```
MoleculeCandidate:
    smiles: str                    # 引擎原始输出，未规范化
    molfile: str | None            # ← 标准化通路的输入，别丢
    source: Enum[DECIMER, MOLSCRIBE, HUMAN]
    engine_confidence: float|None
    bbox: tuple | None             # ← HITL 交互 + 多分子区分
    role: Enum[REACTANT, PRODUCT, SOLVENT, UNKNOWN]   # ← 反应式场景
    canonical_smiles: str | None
    inchikey: str | None

ValidationReport:
    is_valid: bool
    failures: list[ValenceError | SanitizeError | ParseError]
    # 注意：只回答"合法吗"，不回答"对吗"

ConsensusResult:
    verdict: Enum[AGREE, CONFLICT, SINGLE_SOURCE]
    agreed_smiles: str | None
    disagreement_metric: float
    needs_human: bool

RetrievedContext:
    chunk_id / doc_id / text / page / score
    channel: Enum[TEXT_CHUNK, STRUCTURE_NEIGHBOR]     # ← 两条通道

GroundedClaim:
    text: str
    cited_chunk_ids: list[str]     # 空列表 = 无依据，前端必须标红
```

### API 端点（窄闭环）

```
POST /v1/ocsr/recognize          # 图 → 候选 + 验证 + 仲裁
POST /v1/ocsr/{task_id}/confirm  # HITL 回填修正
GET  /v1/ocsr/{task_id}/status   # 长任务轮询 / SSE
```

### DDL 骨架

```
recognition_task(id, image_uri, status, created_at, model_versions JSONB)
molecule_candidate(id, task_id FK, source, raw_smiles, molfile, bbox,
                   canonical_smiles, inchikey, confidence, created_at)
validation_record(id, candidate_id FK, is_valid, failures JSONB)
consensus_record(id, task_id FK, verdict, metric, needs_human, resolved_by)
corpus_chunk(id, doc_id, page, text, chroma_id, embedding_model)
citation(id, answer_id FK, chunk_id FK, span_start, span_end)
```

> ⚠️ **`molecule_candidate` 保留全部原始输出，永不 upsert 覆盖**——eval、badcase 复盘、模型版本对比全靠这张表。

### 钩子4：一致性仲裁（核心技术点）

问题：DECIMER 给 `CC(=O)Oc1ccccc1C(=O)O`，MolScribe 给 `CC(=O)Oc1ccccc1C(=O)[O-]`，哪个对？

候选信号：
- InChIKey 精确比对（最简单，但只能抓"全同/全不同"）
- Tanimoto 相似度（连续分歧度，但非权威）
- **反向渲染比对**：候选 SMILES 用 RDKit 画回图像，与原图做感知相似度 ← **最强独立信号**，绕开"两模型犯同一个错"的相关性

**苏格拉底式自问**：*如果两个引擎都错了、且错得一模一样，仲裁机制会怎样？*
→ 这决定了"多模型投票"是否靠得住。

## 五、显存需求（N 卡场景）

### 权重账（按参数量自算，不信二手站点的 VRAM 数字）

| 组件 | 参数量 | fp32 | fp16 |
|---|---|---|---|
| MolScribe | ~120-150M（Swin-Base + decoder） | ~500-600MB | ~250-300MB |
| RxnScribe | ~120-150M（同架构） | ~500-600MB | ~250-300MB |
| DECIMER 2.0 | ~30-80M（**估算，待实测**） | ~120-320MB | ~60-160MB |
| BGE-M3 | 568M | ~2.3GB | ~1.2GB |
| **合计** | | **~3.4-3.8GB** | **~1.8-2.0GB** |

### 场景总表

| 场景 | 推荐显存 | 卡 |
|---|---|---|
| 单引擎调试 | 2-3GB | 4GB+ |
| **全化学栈（本地）** | **4-5GB** | **8GB 卡足够** |
| 全化学栈 + batch 16 | 6-8GB | 12GB |
| + 7B LLM (4bit) | 12-14GB | 16GB |
| **+ 14B LLM (4bit)** | **16-20GB** | **24GB（3090/4090）** |

### ⚠️ 关键结论
**OCSR 侧不需要借卡。** 找搭档/借学校算力的理由应该是**"跑 LLM 和批量评测集"**，不是"跑 OCSR"。优先级搞反会白欠人情。

### 显存核算模型
```
总显存 ≈ 权重 + 激活 + CUDA context + 碎片余量
权重     = n_params × bytes_per_param    # fp32=4, fp16=2, int8=1
激活     ≈ batch × resolution² × 常数
CUDA ctx ≈ 300-600 MB / 进程
碎片余量 ≈ 峰值 × 1.2
```

### 进程隔离粒度（已修正）
```
✅ 进程 A（PyTorch）：MolScribe + RxnScribe + BGE-M3   ← 共享 1 份 CUDA context
✅ 进程 B（TF）：DECIMER                                ← 框架冲突无法调和
❌ 每引擎一进程                                          ← 浪费 1.5GB context
```

## 六、Strix Halo 环境坑（本机专属）

### 🔴 致命层

**坑 1：`total_memory` 报的是 VRAM + GTT 之和**
- ROCm issue #6004：*"ROCm reports VRAM + GTT as total available memory on APU, but pools have different allocation semantics — causes downstream overcounting"*
- **后果**：按这个数算 batch size → overcount → OOM
- **推论**：`max_batch_size` 不能靠计算，只能**二分探测**

**坑 2："48GB UMA" 是误导的**
- 官方文档：Strix Halo 走 **GPUVM**，是**按进程的虚拟地址空间（VMID）**，**不是独立的物理 VRAM**
- **GART / GTT 描述的是"能映射多少系统内存进 GPU 地址空间"的上限，不是两种物理内存**
- ROCm issue #6022：*"librocdxg fails to map Dedicated VRAM in WSL2; **ROCm pool size is limited by .wslconfig memory setting**"*
- **后果**：能用的"显存"上限 = **`.wslconfig` 分配的内存**，不是物理 48GB

### 🟠 架构级

**坑 3：UMA → CPU 和 GPU 抢同一条内存总线**
- 内存是**映射的，不是物理划分的**
- **推论**：DECIMER(CPU) 与 MolScribe(GPU) **并行可能比串行更慢**
- **直接质疑"双引擎并行"策略** → 必须实测

**坑 4：DECIMER 上不了本机 GPU（三重不利）**
- ROCm TF 版本矩阵停在 **ROCm 6.1.x → TF 2.13-2.15**，本机是 ROCm 7.2
- 且那是**原生 Linux** 文档，本机是 **WSL2 + DXG** 路径
- 再叠 issue #6022
- → **DECIMER 只能 CPU，别再尝试**

### 🟡 工具链层

| 坑 | 症状 | 处置 |
|---|---|---|
| `pip install MolScribe` 顶掉 ROCm torch | torch 变 CUDA 版 | 检查 `torch.__version__` 含 `+rocm` |
| 子进程丢 `HSA_ENABLE_DXG_DETECTION` | 子进程 `cuda.is_available()` = False | **worker 启动时显式传 env** |
| 子进程丢 `HF_ENDPOINT` | `hf_hub_download` 挂起 | 同上（MolScribe 用 hf_hub_download 拉权重） |
| 跨文件系统 I/O | 遍历图库极慢 | 数据放 WSL 内部 `~/`，不放 `/mnt/c` |
| `wsl --update` 破坏 rocr4wsl | 某天 GPU 突然消失 | **固定内核版本，禁自动更新** |
| OpenCV 无 X11 | `cv2.imshow` 崩 | `opencv-python-headless` |
| PDF 转图缺 poppler | `pdf2image` 报错 | `apt install poppler-utils` |

### 环境不变量（写代码前必须为真）

```
INV-1  WSL2 内存上限 ≥ 想用的 GPU pool        （由 .wslconfig memory= 决定）
INV-2  HSA_ENABLE_DXG_DETECTION=1 在 worker 进程环境里
INV-3  torch 是 +rocm 版且未被 MolScribe 依赖覆盖
INV-4  HF_ENDPOINT=https://hf-mirror.com 在下载进程里可见
INV-5  数据在 WSL 内部文件系统，不在 /mnt/c/
```

## 八、评测设计

- [ ] **Q1**：RxnScribe 已内置 MolScribe，还需要单独编排 MolScribe 吗？若不需要，"双引擎一致性仲裁"还成立吗？

- [ ] **Q5**：HITL 修正后的结果要不要回写成 eval 数据？若要，`molecule_candidate` 表设计够用吗？
- [ ] **Q6**：BGE-M3 走 CPU 的吞吐够不够批量入库几万条 chunk？若不够 → 入库用 GPU、查询用 CPU（同模型两套部署）？
- [ ] **Q7**：向量库用 ChromaDB 还是 **pgvector**（服务器已有 PG16，可少一个组件）？建议：先用 Chroma 跑通，留 `VectorStore` 抽象接口。
- [ ] **Q8**：教材语料版权问题——中文有机化学教材（邢其毅等）PDF 的合规边界？
- [ ] **Q9**：学校机器断连时演示能否降级？是否需要保留纯本地通路？

### ChromaDB 已知坑
- 官方压测：16GB RAM → ~360万条，查询 ~4ms，基准正是 **1024 维**（与 BGE-M3 输出吻合）
- ⚠️ **持久化目录不能被两个进程同时打开** → 离线入库与在线服务并存会挂起 10+ 分钟（issue #7040）
