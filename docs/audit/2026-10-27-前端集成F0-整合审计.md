## 3. 三条主链路

### 3.1 主管图：从用户输入到结果

```text
POST /agent
  │  body: {user_input, chat_thread_id, [model 未使用]}
  ▼
get_owned_threads() ── 不存在/非本人 → 404
  ▼
runtime.start_run()
  ├─ 已有活动 Execution（CREATED/RUNNING/WAITING_APPROVAL/SUSPENDED）→ 409 thread_busy
  ├─ create Task (QUEUED) → RUNNING
  ├─ create Execution (CREATED) → RUNNING;  graph_thread_id = execution_id
  └─ 返回 RunContext{thread_id, task_id, execution_id, graph_thread_id}
  ▼
agent_stream(graph_input = {messages, task_input, task_id, execution_id})
  ▼
┌──────────── 主管图（根 namespace）────────────┐
│ START                                          │
│  ▼                                             │
│ begin_turn_node   清 run 级字段（intent/error/ │
│                   result/subagent_task 等）    │
│  ▼                                             │
│ intent_node       LLM(disable_streaming)       │
│                   → intent_raw, attempts+1     │
│  ▼                                             │
│ validate_intent_node  _parse_intent:           │
│   ├─ 非 JSON/缺字段 ── attempts<2 → 回 intent_node（带 intent_error）
│   │                    attempts≥2 → route_failed_node
│   ├─ 合法但不支持 ───────────────→ route_failed_node
│   └─ CHAT/CODE ──────────────────→ _GOTO[intent]
│  ▼                                             │
│ chat_graph：prepare→model→END  （不挂工具）    │
│ coder_graph：prepare→model→should_continue     │
│              ├─无 tool_calls→finish→END        │
│              └─有 tool_calls→prevalidate→...   │
│ route_failed_node → END                        │
└────────────────────────────────────────────────┘
  ▼
SSE 帧（token / tool_start / tool_end / approval_required / error / done）
  ▼
流结束后 graph.aget_state:
  ├─ interrupts 非空 → done status=interrupted（DB 已是 WAITING_APPROVAL）
  ├─ route_status=="failed" → error route_failed + done failed（Task/Exec→FAILED）
  └─ 其它 → done completed（Task/Exec→COMPLETED）
```

**关键语义**

- 意图由模型产出（`intent_raw`），由程序校验后写入 `intent`；条件边只认 `intent`，通过 `Command(goto=...)` 路由，不存在 `add_conditional_edges` 的字符串映射表。
- 格式非法最多重试 1 次（总调用上限 2）；合法但不支持的意图立即失败，不重试。
- Task/Execution 在 HTTP 层创建，图内不建；图只接收 `task_id/execution_id`。
- 子图结果通过同名 `result` 字段映射回主管；SSE 只发 token，不发最终 `result` 帧。
- 主管自身节点（意图识别）产生的 token 被屏蔽，不下发给前端。

### 3.2 T23 审批：从送审到执行

```text
model_node 产出 tool_calls
   ▼
prevalidate_node
   ├─ 未知工具 → 回填 ToolMessage → model_node（整批拦下）
   ├─ 全安全   → tools_node → 执行 → model_node
   └─ 含高风险
        ├─ build_write_review：路径越界/目录/读文件失败 → 回填错误 → model_node
        ├─ runtime.ensure_approvals()
        │    ├─ create_or_get_approval（幂等键 = hash(execution_id:tool_call_id)）
        │    └─ Task/Execution RUNNING → WAITING_APPROVAL（成对 CAS）
        │    失败 → ApprovalSetupError → 回填错误 → model_node（不 interrupt）
        └─ pending_reviews = ReviewRequest.model_dump()
             ▼
          review_node → interrupt(snapshot)
             ▼  SSE approval_required {interrupt_id, review.requests[*].approval_id}
        ┌──────────── 用户决定 ────────────┐
        │ 可选：POST /agent/decisions      │  T20 落库，不恢复
        │ 必须：POST /agent/resume         │
        └──────────────────────────────────┘
             ▼
      /agent/resume
        ① 线程归属（404）
        ② active_execution（无 → 409）
        ③ 图是否 interrupt（否 → 409 state_mismatch）
        ④ check_decision_matches（集合完全一致，否则 409）
        ⑤ submit_decisions（APPLIED/IDEMPOTENT 通过；冲突 409；不存在 404）
        ⑥ runtime.prepare_resume
             ├─ preflight_resume：图 interrupts ↔ DB 行 ↔ tool_call 配对 ↔ args_hash
             │   失败 → 404/409/503，不恢复
             └─ validate_and_resume：状态对、无 PENDING、无 REVOKED、
                  NOT_STARTED、args 内部一致、目标文件 old_hash → RUNNING
        ⑦ Command(resume=decisions) → execute_node
             ├─ 载荷非法 → 回填 → model_node（不执行）
             ├─ 有拒绝   → 整批回填 → model_node（不执行）
             ├─ 文件已变 → 整批作废 → model_node（不执行）
             └─ 全批准   → approved_approvals（approval_id↔tool_call_id）
                  ▼
             guarded_tools_node
               ├─ claim_batch 失败 → 回填"执行权已被占用"（不执行）
               ├─ ToolNode 执行整批 tool_calls
               ├─ 异常 → 全部 UNKNOWN
               └─ finish_batch：SUCCEEDED/FAILED/UNKNOWN
                  ▼
             model_node → … → finish_node → END
                  ▼
             done completed → Task/Execution COMPLETED
```

### 3.3 Tauri / Python 生命周期

**现状（代码实证）**

```text
用户双击 / npm run tauri:dev
   ▼
Tauri main 窗口（1420 devUrl / dist 产物）
   ▼
React 模板页面（无 fetch、无 invoke）
   X  （无任何 Python 启动代码）
Python 需另开终端：
   uv run --package furina-desktop python -m furina_desktop
   ▼
uvicorn 127.0.0.1:8001 → /healthz
```

- 生命周期责任人：**无人**。Tauri 不启动、不探活、不回收 Python。
- 窗口：只有一个 `main`。无角色窗口、无"打开工作台"逻辑、无窗口复用/聚焦。
- 退出：Tauri 退出不影响 Python；Python 退出 Tauri 不知道。
- 端口：8001 固定；冲突时 uvicorn 启动失败，前端无提示。
- 单实例：Python 有文件锁，但路径相对 CWD（见 §5）。

**目标（F4 建议）**

```text
Tauri setup
  ├─ 解析资源路径 / 数据目录（绝对路径）
  ├─ 启动 Python（Rust Command 或 sidecar）
  ├─ 轮询 GET /healthz（退避重试）
  ├─ 就绪 → 创建 main 工作台窗口
  └─ 失败 → 窗口显示"后端未启动" + 重试按钮
Tauri on_window_event(CloseRequested/Destroyed)
  └─ 终止并等待 Python 子进程
角色窗口 → emit("open-workbench") → Rust 聚焦或创建唯一 main
两窗口 → 各自 HTTP 快照 + 各自订阅（不共享 React 状态）
```

## 5. 缺口与缺陷清单

### 5.1 P0 · 阻塞前端工作台

- 现象：`POST /agent` 的 SSE 帧只有 `token/tool_start/tool_end/approval_required/error/done`，没有 `task_id`/`execution_id`。

**P0-3 审批待办只存在于当次 SSE 流里**

- 现象：`approval_required.review.requests[]` 是唯一获取审批内容的通道；`/agent/resume` 又要求决定与待审项**逐条完全一致**。

**P0-4 客户端断连可能让 Execution 永久停在 RUNNING（推断，未实测）**

- 现象：`_stream_graph` 只捕获 `Exception`（`stream.py:207`）；`asyncio.CancelledError` 属于 `BaseException`，SSE 被 Starlette 取消时不会调用 `on_finished`，`finalize_run` 不执行。

### 6.3 现有接口细节

**`POST /agent`**

```json
// 请求
{
  "user_input": "帮我写一个 hello.txt",
  "chat_thread_id": "uuid",
  "model": "deepseek-v4-flash"   // 可选；后端忽略
}
```

响应为 SSE，帧示例：

```text
data: {"type":"token","agent":"coder","content":"好"}
data: {"type":"tool_start","agent":"coder","id":"call_w1","name":"write_file_tool","args":{...}}
data: {"type":"approval_required","agent":"coder","interrupt_id":"...","review":{...}}
data: {"type":"done","status":"interrupted"}
```

错误：404 线程不存在/非本人；409 `{"code":"thread_busy","execution_id":...,"status":...}`；422 校验失败；500 runtime 未初始化。

**`POST /agent/decisions`**

- 语义：只落库，不恢复图；单条决定必须至少有 `approval_id` 或 `tool_call_id`。
- 返回 `outcome`：`APPLIED` / `IDEMPOTENT` 为 200；`CONFLICT`/`ILLEGAL_STATE` → 409；`NOT_FOUND`/`SCOPE_MISMATCH` → 404。

**`POST /agent/resume`**

- 请求里的 `review.decisions` 必须与当前待审批**完全一致**（不多、不少、不重复）。
- 前置校验顺序：线程归属 → 活动 Execution → 图 interrupt → 决定集合 → 决定落库 → DB↔图↔args 预检 → 状态迁移 → 恢复。
- 失败语义：404（线程/审批不存在、越权）；409（未挂起、决定不匹配、冲突、预检失败）；503（checkpoint 不可读）。

**线程接口**

- `POST /agent/threads`：`{title}` → `{id, title, created_at}`；标题必填、最大 255、无最小长度。
- `GET /agent/threads?page&size` → `{items:[...], total, page, size}`；item 为 ORM 行（含 `user_id`）。
- `DELETE /agent/threads/{id}` → `{"ok":true}`；**注意 P1-1 的 checkpoint 孤儿问题**。
- `PATCH /agent/threads/{id}`：`{title}` → `{"ok":true}`。

- **输入**：`user_input`（必填，1–255，去空白后非空）、`chat_thread_id`（必填 UUID）、`model`（可选，后端忽略）。

## 7. 事件与状态同步评审

### 7.1 当前事件集（VERIFIED）

`EVENT_TYPES = token | tool_start | tool_end | approval_required | error | done`（`stream.py:42`）。

| 事件 | 载荷 | 发布时机 | 是否先持久化 |
|---|---|---|---|
| `token` | `{agent, content}` | 子图模型流式 chunk | 不涉及 |
| `tool_start` | `{agent, id, name, args}` | 模型产出 tool_calls | 不涉及 |
| `tool_end` | `{agent, id, name, status, content}` | ToolMessage | 工具已执行，终态稍后写 |
| `approval_required` | `{agent, interrupt_id, review}` | 图 interrupt | **是**（审批行与状态已提交） |
| `error` | `{code, message, ...}` | 异常/路由失败/挂起/决定不匹配 | 视情况 |
| `done` | `{status: completed\|failed\|interrupted}` | 流结束 | **是**（`finalize_run` 先执行） |

`agent` 取值：`supervisor`（token 被屏蔽）、`coder`、`chat`。

### 7.2 结论

- **没有状态变更事件**：`task.created`、`task.status_changed`、`execution.*`、`approval.decided`、`approval.invalidated` 全部不存在。
- **没有事件信封**：无 `event_id/occurred_at/thread_id/task_id/execution_id`，无法去重、排序、重放、跨窗口关联。
- **没有断线恢复**：无 `Last-Event-ID`，无快照 API；刷新后只能拿到会话标题。
- **多窗口不可能共享**：每条 SSE 绑定发起它的请求；第二个窗口无法接入正在运行的流。
- **发布顺序基本正确**：审批/完成事件都在 DB 提交之后；但用户动作产生的 `approval.decided` 完全不发。

### 7.3 建议的最小契约

**第一步：先做快照（F1）**

```text
GET /agent/threads/{thread_id}/state
{
  "thread_id": "...",
  "active_task": {"task_id","status","instruction","created_at"} | null,
  "active_execution": {"execution_id","status","graph_thread_id","created_at","finished_at"} | null,
  "pending_approvals": [{
    "approval_id","task_id","execution_id","tool_call_id","tool_name","args",
    "risk_level","target_path","old_hash","creates_dirs","diff",
    "approval_status","tool_execution_status","deadline_at","created_at"
  }],
  "last_error": {"code","message","at"} | null
}
```

**第二步（仅在双窗口需要实时时）：`GET /agent/events?thread_id=`**

```json
{
  "event_id": "uuid",
  "event_type": "task.created|task.status_changed|execution.started|execution.status_changed|execution.completed|execution.failed|approval.requested|approval.decided|approval.invalidated",
  "occurred_at": "RFC3339",
  "thread_id": "uuid",
  "task_id": "uuid|null",
  "execution_id": "uuid|null",
  "data": {}
}
```

**发布规则**：只在 DB 提交后发布；断线重连先用快照对齐，再用 `event_id` 去重；不假设事件可重放。

### 8.1 A 组 · F1 前必须定

---

#### D1. 提交任务后，怎么把 `task_id / execution_id` 给前端？

**代码现状**

- `agent_stream` 只产出六种帧，没有任何标识（`stream.py:42,258-312`）。
- `runtime.start_run` 已经拿到 `RunContext{task_id, execution_id, graph_thread_id}`（`runtime.py:90-96,232-237`），但没有序列化给调用方。
- 前端若自己生成临时 id，后端无法识别；重启/刷新后无法与任务对应。

**为什么现在定**

这决定 F2 的 `TaskComposer` 能否在提交后立即打开任务详情、能否把后续事件归到某个任务上；也决定 F3 列表/详情的路由参数。

**选项**

| 选项 | 做法 | 代价 | 风险 |
|---|---|---|---|
| **A. SSE 首帧 `meta`（推荐）** | 在第一个 token 前发 `{"type":"meta","thread_id","task_id","execution_id"}` | 后端 ~0.5 天；前端多认一种帧 | 前端必须忽略非渲染帧 |
| B. 响应头 | `X-Task-Id` / `X-Execution-Id` | ~0.5 天 | 需要 CORS `Access-Control-Expose-Headers`；扩展性差 |
| C. 两段式 | 先 `POST` 返回 JSON，再单独开流 | 2–3 天，改动最大 | 与"一个生成器跑完图"的结构冲突 |

**推荐 A**：改动最小、向后兼容、以后还能在 meta 里塞 `event_id`。
**不定的后果**：F2 只能用前端临时 id，刷新/重启后任务对不上。
**回答形式**：`D1 = A / B / C`。

---

#### D2. 关掉/刷新工作台时，正在跑的任务怎么办？

**代码现状（重要）**

- 一次 run 的生命周期绑死在发起它的 HTTP/SSE 请求上：`agent_chat` 直接返回 `StreamingResponse(agent_stream(...))`（`api/agent.py:168-176`）。
- `_stream_graph` 只捕获 `Exception`（`stream.py:207`），`asyncio.CancelledError` 不被捕获；SSE 被 Starlette 取消时 `on_finished` 不执行。
- `finalize_run` 只处理 RUNNING，且只在 `_notify_finished` 里被调用（`runtime.py:698-771`）。
- 超时扫描只处理 `WAITING_APPROVAL`（`timeout_scanner.py:83-113`），不处理 `RUNNING`。
- 结果：**刷新页面 ≈ 这条线程永久 busy**，之后每次 `POST /agent` 都 409 `thread_busy`，重启应用也不恢复（DB 持久化）。

**为什么现在定**

这是本轮最重要的产品+架构决策。它决定 F2 的提交流是"窗口生命周期的子资源"还是"后端独立任务"；也决定 F3 的刷新恢复能否成立。

**选项**

| 选项 | 行为 | 改动量 | 体验 |
|---|---|---|---|
| **A. 最小止血（推荐先做）** | 断连即收尾：捕获 `CancelledError` → `finalize_run(status="failed", reason="client_disconnected")`；若审批尚未开始可退 SUSPENDED | 0.5 天 + 1 个冒烟测试 | 刷新后任务显示失败，回答丢失；但线程能继续用 |
| B. 后台运行 + 可重连 | run 放后台 `asyncio.Task`，SSE 变成订阅者；刷新后可重新挂上看结果 | 3–5 天，需事件缓冲/订阅者管理 | 最好，但 F2/F3 会被拖住 |
| C. 显式取消 | 提供"停止任务"接口，取消即终止 | A + 0.5 天 | 用户可控，但不解决"刷新后想看结果" |

**推荐**：**F2 之前做 A，F4 之前再评估 B**。A 是正确性修复（现在会卡死），B 是体验升级；不要为了 B 把前端开工时间往后推两周。

**不定的后果**：测试会偶发"线程卡住"；用户刷新一次就得重启后端；F3 的"刷新恢复"无法验收。

**需要你回答**：你接受 V1"刷新/关闭 = 当前任务失败、回答丢失"吗？
- 接受 → `D2 = A`
- 不接受，要求"关掉窗口任务继续跑、回来还能看结果" → `D2 = B`（请明确，我会把 F1 范围扩大）

#### D3. 状态同步：快照轮询，还是全局事件流？

**代码现状**

- 没有任何"当前状态"查询接口；`GET /agent/threads` 只返回会话标题。
- 没有跨请求事件总线；每条 SSE 只服务发起它的请求。
- 双窗口若各自持 React 状态，天然不共享（React 全局状态不跨 WebView）。

**为什么现在定**

这决定 F1 要新增哪些接口、F3 刷新恢复怎么实现、F4 双窗口怎么共享。

**选项**

| 选项 | 做法 | 代价 | 适用 |
|---|---|---|---|
| **A. 快照 + 轮询（推荐 V1）** | 新增 `GET /agent/threads/{id}/state`；任务进行中 1–2s 轮询，空闲按需拉 | 1–2 天 | 单/双窗口都够用，实现最稳 |
| B. 事件总线 + `GET /events` | 进程内 pub/sub，每条 SSE 独立订阅 | 3 天 + 并发/重连处理 | 双窗口实时、断线重连才真正需要 |

**推荐 A**：双窗口各自轮询同一快照就能"看到同一业务状态"，不需要跨窗口通信。
**与 D2 的关系**：D2=A 时刷新后快照显示"任务已失败"；D2=B 时快照能看到 RUNNING 并可继续订阅。
**不定的后果**：F3 的"刷新恢复"无法验收；F4 的双窗口只能靠"各开各的"。
**回答形式**：`D3 = A / B`。

#### D4. 本地 API 要不要加认证？

**代码现状**

- `auth.py:48-75` 返回固定 UUID 的 `User`，不查库、不校验；桌面版没有登录动作。
- 服务只绑回环（`main.py:346-354`），CORS 只放 Tauri/1420 源（`main.py:283-294`）。

**为什么现在定**

| C. OS 级鉴权 | 不现实 | — |

**推荐**：**V1 选 A 并在文档里明确记录**；F4 做进程托管时顺手选 B（Rust 生成 token → 环境变量传给 Python → IPC 给前端），成本最低。
**不定的后果**：安全边界说不清；评审时是个漏洞。
**回答形式**：`D4 = A / B`。

#### D5. V1 要不要支持"同一个 Task 重新执行"？

**代码现状**

- 表结构支持一个 Task 多个 Execution（`task/models.py:103-122`）。
- 生产代码只有一条创建路径：`runtime.start_run` 每次都新建 Task（`runtime.py:176-237`）。
- `parent_task_id` / `redelegation_key` 只有字段，无写入方（grep 验证）。
- 因此 **Task:Execution 在实际数据里恒为 1:1**。
- F3 验收里的"历史 Execution 可区分"在当前实现下**无法产生真实数据**。

**为什么现在定**

这直接改写 F3 的验收标准和 UI 结构（是否显示"重跑"、是否显示执行历史时间线）。schema 已预留，现在不做将来也不需要迁移，所以这是一个**可逆的范围决策**。

**选项**

| 选项 | 做法 | 代价 |
|---|---|---|
| **A. V1 不做（推荐）** | 一次提交 = 一个 Task；UI 不提供"重跑"；F3 验收改为"当前执行可查" | 0 后端改动；需修改验收表述 |
| B. 最小重跑 | 新增 `POST /agent/tasks/{id}/executions`：复用 Task，新建 Execution + graph key | 1–2 天后端 + 状态机测试 |

**推荐 A**：没有真实需求支撑时，多一个执行入口就多一套状态机暴露面。
**不定的后果**：F3 范围模糊；你可能按"列表里每个 Task 只有一次执行"设计 UI，却又不确定产品是否接受。
**回答形式**：`D5 = A / B`。

#### D6. 审批粒度：整批全决，还是允许"部分批准"？

**代码现状**

**选项**

|---|---|---|
| **A. 整批全决（推荐）** | 0 | UI 可对每项给 approve/reject 开关，但提交必须覆盖全部 |
| B. 部分批准、其余保持待审 | 3–5 天，需改图恢复语义 + 决定匹配 | 会引入多次 resume 同一 interrupt |
| C. 逐条执行 | 更大 | 与当前 ToolNode 整批执行结构冲突 |

**推荐 A**。
**不定的后果**：前端可能做出"只提交一项"的交互，后端直接 409。
**回答形式**：`D6 = A / B / C`。

#### D7. 用户拒绝 / 工具失败时 Task 仍显示 COMPLETED，接受吗？
