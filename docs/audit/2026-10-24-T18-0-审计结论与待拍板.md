## 三、问题清单

### P0（阻塞 T18 / T20）

**P0-1 时间语义**
- 触发：`deadline_at = datetime.now(UTC) + 5min` 写入 → 读出 `tzinfo=None` → `now(UTC) > deadline_at` → `TypeError`
- 影响：T20 决定服务、T21 超时扫描全部阻塞
- 根因：SQLite 无时区类型，`DateTime(timezone=True)` 只影响 DDL 声明

**P0-2 幂等创建不可用直觉实现**
- 触发：重复 key → `IntegrityError` → 若不 `rollback` 直接查 → `PendingRollbackError`
- 影响：T18 若写成 `try: insert except IntegrityError: select`，会在“ID 冲突”路径上再抛一个 500
- 已验证可行路径：`begin_nested()` + `flush`（SAVEPOINT）

### P1（T18 范围内应处理）

- **P1-1 跨任务错配**：`create_approval` 不校验 `execution.task_id == task_id`
- **P1-2 幂等键语义未定**：是否包含 `args_hash` 决定“参数被篡改”是**检出冲突**还是**新建一条待审**
- **P1-3 无状态机**：`transition_*` 只保证抢到一次，不保证迁移合法（T19）
- **P1-4 缺 `INVALIDATED`**：MCP 阶段要标记旧审批失效，当前枚举没有（按规范延后）
- **P1-5 每个 repository 方法自己 commit**：无法组合多表事务（T19 会撞）

### P2（记录，暂不处理）

- `finish_tool_execution` 无返回值，调用方无法区分“成功”与“条件不满足”
- `max_length` 在 SQLite 不强制，PG 会报 → 两后端行为不一致
- `target_path` / `old_hash` 与 `tool_name` 无关联约束
- `updated_at` 只在 repository 的 UPDATE 中维护

## 四、需要你拍板（回一行即可）

格式建议：`Q1=A, Q2=A, Q3=A, Q4=A, Q5=A, Q6=A`

### Q1 · `idempotency_key` 怎么算？

| 选项 | 公式 | 后果 |
|---|---|---|
| **A（推荐）** | `sha256("{execution_id}:{tool_call_id}")` | 参数被篡改时，同 key 但 `args_hash` 不同 → **能检出冲突并拒绝** |
| B | 含 `args_hash` | 参数一改就变成“新建一条待审”，篡改被洗白成正常请求，**危险** |
| C | 含工具定义哈希 | 面向 MCP 阶段；现在没有工具指纹来源，做不了 |

> 建议理由：幂等键回答“这是不是同一个请求”，参数哈希回答“参数有没有变”。两者混在一起会丢掉“变”这个信号。

### Q2 · 幂等命中、但字段不一致时怎么办？

| 选项 | 行为 | 后果 |
|---|---|---|
| **A（推荐）** | 抛领域异常 `ApprovalConflict` | 调用方必须处理；不会静默放行 |
| B | 返回旧行 | 参数篡改被静默忽略，**不要** |
| C | 返回旧行 + `mismatch=True` 标记 | 灵活，但调用方容易忘记检查 |

### Q3 · 时间怎么存、怎么比？

| 选项 | 做法 | 后果 |
|---|---|---|
| **A（推荐）** | 存储仍是 UTC；读出一律 `as_utc()` 归一化，比较只用它 | 需要所有消费点记得调用，但不动 schema |
| B | 全项目改用 naive UTC | 开发时不易出错，但一旦有人传 aware 就埋雷 |
| C | 改存 epoch 整数 | 最稳，但要改列 → 需要迁移，本轮不建议 |

### Q4 · 现在是否加 `(execution_id, tool_call_id)` 唯一索引？

| 选项 | 后果 |
|---|---|
| **A（推荐）** | 暂不加。等 `INVALIDATED` 方案定了再加，否则“失效后重建审批”会撞唯一约束 |
| B | 现在加。数据最干净，但 MCP 阶段必须做迁移 |
| C | 加**部分唯一索引**（仅 `approval_status='PENDING'`）。兼顾历史与唯一，但语义复杂，SQLite/PG 行为需分别验证 |

### Q5 · 是否给 repository 加 `commit=False`？

| 选项 | 后果 |
|---|---|
| **A（推荐）** | 本轮不做，T19 做生命周期时再一起改 |
| B | 现在加。T19 多表事务能立刻组合，但会改动已通过 21/21 的代码 |

### Q6 · 跨任务错配校验放哪？

| 选项 | 后果 |
|---|---|
| **A（推荐）** | service 层先查 execution 再建 | 简单、跨库一致；多一次查询 |
| B | DB 复合外键 `(execution_id, task_id) → agent_execution(id, task_id)` | 结构性最强，但 SQLite 复合外键与现有模型改动大 |
