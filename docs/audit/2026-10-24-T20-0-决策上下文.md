## 2. Q1 · 决策记录放哪？

### 选项

| 选项 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A（推荐）** | **内联**：复用 `approval_request` 的 `approval_status / decided_by / decided_at / decision_reason` | 零 Schema 变更；与 T18 一致；单行原子 | **重复/冲突提交不留审计轨迹** |
| B | 新增 `approval_decision` 表（每次提交一行） | 完整审计；可记录“谁在什么时候又提交了什么” | 新表 + 仓储 + 事务改造；无 Alembic，只能 `create_all` 新建表；T20 范围显著变大 |
| C | 内联 + 追加 JSON 日志字段 | 折中 | 仍要改列；查询/索引差 |

### 影响

- 选 A：T20 只新增一个 service 文件 + 测试；`decide_approval` 不用改
- 选 B：要新增模型、仓储、`decide_approval(commit=False)`、事务编排；建议单独一轮做

### 补充：A 的审计缺口怎么补

A 方案下，重复提交/冲突提交**不会留痕**，但服务会返回 `IDEMPOTENT` / `CONFLICT`。如果将来需要审计，可在 T23 统一执行器时再加表，不影响现在。

## 3. Q2 · 什么算“同一个决定”？

### 背景

同一个 `approval_id` 已经有终态后，又来一次提交：

- 相同决定 → 应幂等返回
- 相反决定 → 应冲突

问题：比较哪些字段？

### 选项

| 选项 | 判定 | 后果 |
|---|---|---|
| **A（推荐）** | 只比 `approval_status` | 同一请求只有一个有效决定；不同人重复批准视为幂等 |
| B | `approval_status` + `decision_reason` | 同一决定换个理由就变成冲突，容易误报 |
| C | `approval_status` + `decided_by` | 换个人再批准算冲突 —— 对单机单用户没意义，对多用户语义也偏怪 |

### 影响

选 A 后，`IDEMPOTENT` 返回既有行（含原 `decided_by` / `decided_at`），**不覆盖**。

## 4. Q3 · 终态任务收到决定怎么办？

### 背景

审计确认：`decide_approval` 不检查 Task 状态。一个已 `COMPLETED/FAILED/CANCELLED` 的任务，其审批请求仍可被写成 `APPROVED`。

规范要求“终态任务不得被迟到批准复活”。问题是：**连决定本身要不要写？**

### 选项

| 选项 | 行为 | 后果 |
|---|---|---|
| **A（推荐）** | 拒绝：返回 `ILLEGAL_STATE`，不写决定 | 数据最干净；但审计上“用户确实点了批准”没有记录（Q1=A 时无处可记） |
| B | 写入决定，但永不恢复 | 保留用户意图；风险是看表的人误以为“已批准=会执行” |
| C | 写入并标记 `REVOKED` | 语义拧巴，不推荐 |

### 影响

选 A：T20 需要在写之前读 Task 状态（一次查询），并接受“这次点击没有留下痕迹”。
选 B：返回值仍是 `APPLIED`，但必须在文档里强调“批准 ≠ 执行”。

## 5. Q4 · 迟到决定允许保存吗？

### 选项

| 选项 | 行为 | 后果 |
|---|---|---|
| **A（推荐）** | 允许保存；T20 只落决定，不恢复任务 | 与规范一致（超时不使审批失效）；恢复校验在 T22 |
| B | 拒绝迟到决定（返回 `ILLEGAL_STATE`） | 与“超时不自动拒绝”的既定语义冲突，不建议 |
| C | 自动改成 `REVOKED` | 等于超时自动拒绝，违反规范 |

### 影响

选 A：`decided_at` 可能晚于 `deadline_at`。是否“迟到”可通过 `as_utc(decided_at) > as_utc(deadline_at)` 推导，**不需要新增字段**。

---

## 6. Q5 · “过期”用什么判？

### 背景

T21（超时扫描）还没实现，所以任务不会被自动置 `SUSPENDED`。如果 T20 用“状态是否为 SUSPENDED”判断迟到，**永远不会触发**。

### 选项

| 选项 | 判定 | 后果 |
|---|---|---|
| **A（推荐）** | 看 `deadline_at` 与服务端时间，仅用于“迟到”分类，不拒绝 | T20 可独立工作；T21 接入后再结合状态 |
| B | 看 Task/Execution 是否 `SUSPENDED` | 现在恒为假；要等 T21 才有意义 |
| C | 两者都看，任一满足即迟到 | 最完整，但当前状态分支是死代码 |

### 影响

选 A：T20 只做“时间上的迟到”，不改变任务状态；T22 负责恢复前校验。

## 7. Q6 · `decided_by` 从哪来？

| 选项 | 做法 | 后果 |
|---|---|---|
| **A（推荐）** | 调用方传字符串（本地固定用户） | 与现状一致；不引入认证改造 |
| B | 从 `task.thread.user_id` 反查 | 多用户才有意义；本地单用户是绕路 |

### 影响

选 A 时，T20 不校验“这个人有没有资格决定”。桌面版单用户、只监听回环，风险可接受；Web 版接 T20 时需要补。

## 8. Q7 · 要不要给 `decide_approval` 加 `commit=False`？

| 前提 | 是否需要 |
|---|---|
| Q1=A 内联 | **不需要**：单行 UPDATE 本身就原子 |
| Q1=B 独立表 | **需要**：决定行 + 审批状态必须同事务 |

> 这是 Q1 的派生问题，选了 A 就自动是“不需要”。
