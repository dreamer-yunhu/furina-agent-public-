## 2. 决策摘要

| 决策点 | 结论 |
|---|---|
| 决策记录载体 | `approval_request` 内联字段，不新增表 |
| 幂等判定 | 只比 `approval_status` |
| 冲突判定 | 已有终态不同 → `CONFLICT`，不覆盖 |
| 终态任务 | `ILLEGAL_STATE`，不写决定 |
| 迟到决定 | 允许写入；仅标注 `late`，不拒绝、不恢复 |
| 事务 | 单行条件 UPDATE；不为 T20 改 Repository 接口 |
| 并发 | 以 CAS 结果为准；失败后重读分类 |
| T19 调用 | **不调用**；决定不改变 Task/Execution 状态 |

## 3. 结果类型

```python
class DecisionOutcome(str, Enum):
    APPLIED = "APPLIED"              # 首次成功写入
    IDEMPOTENT = "IDEMPOTENT"        # 已有相同决定，返回原记录
    CONFLICT = "CONFLICT"            # 已有相反决定
    NOT_FOUND = "NOT_FOUND"          # 审批请求（或所属任务）不存在
    SCOPE_MISMATCH = "SCOPE_MISMATCH"# 请求与 task/execution 关联不符
    ILLEGAL_STATE = "ILLEGAL_STATE"  # 当前不允许（终态任务）

@dataclass(frozen=True)
class DecisionResult:
    outcome: DecisionOutcome
    approval: ApprovalRequest | None   # APPLIED/IDEMPOTENT/CONFLICT/ILLEGAL_STATE 时返回
    late: bool = False                 # 仅用于分类，不参与拒绝
```

**为什么用 dataclass 而不是 tuple**：需要携带 `approval` 与 `late`，且字段名要在调用方可见。
**为什么不用 Pydantic**：这是进程内结果对象，不跨 HTTP 边界；Pydantic 留给契约层。

**数据库异常不映射成 outcome**：`IntegrityError`、连接失败等**原样抛出**，由调用方感知持久化故障（符合“不得吞掉数据库故障”）。

## 4. 判定顺序（关键）

```
1. 按 approval_id 读取
      不存在 → NOT_FOUND
2. 校验归属
      approval.task_id != task_id 或 approval.execution_id != execution_id
      → SCOPE_MISMATCH（approval 返回 None，不回传别家的数据）
3. 已有决定（approval_status != PENDING）
      == 本次决定 → IDEMPOTENT（返回原记录，不覆盖 decided_by/decided_at）
      != 本次决定 → CONFLICT（返回原记录）
4. 读取 Task
      不存在 → NOT_FOUND
5. Task 已处于终态（COMPLETED/FAILED/CANCELLED）
      → ILLEGAL_STATE（不写决定）
6. 计算服务端时间与 late
      now = as_utc(now_param or datetime.now(UTC))
      late = now > as_utc(approval.deadline_at)
7. 条件 UPDATE（PENDING → 决定）
      命中 → APPLIED
8. 未命中（并发被抢）→ 重读 approval
      不存在 → NOT_FOUND
      与本次相同 → IDEMPOTENT
      与本次相反 → CONFLICT
```

### 为什么第 3 步在终态任务校验之前

如果顺序反过来：一个任务先完成、用户重放同一个批准，会被判成 `ILLEGAL_STATE`，破坏幂等。
正确语义是：**已经成功落过的决定，无论任务后来怎样，重放都必须返回 `IDEMPOTENT`**。

### 边界情形

| 情形 | 结果 |
|---|---|
| 审批 `APPROVED`，任务后来 `COMPLETED`，重放 `APPROVED` | `IDEMPOTENT` |
| 审批 `APPROVED`，重放 `REJECTED` | `CONFLICT` |
| 审批 `PENDING`，任务 `FAILED` | `ILLEGAL_STATE` |
| 审批 `PENDING`，`deadline_at` 已过 | `APPLIED`，`late=True` |
| 两个 Session 同时提交相反决定 | 一个 `APPLIED`，另一个 `CONFLICT`（重读得出） |

---

## 5. 幂等与冲突语义

- **幂等边界 = 同一个 `approval_id`**（一行一个有效决定）。
- 比较字段**只有** `approval_status`（Q2=A）；`decided_by`、`decision_reason` 不参与。
- `IDEMPOTENT` 返回**原记录**，不更新任何字段（包括 `updated_at`）。
- `REVOKED` 是终态：对 `REVOKED` 提交 `APPROVED` → `CONFLICT`。
- **T20 的用户决定只接受 `APPROVED` / `REJECTED`**；`REVOKED` 属于取消/失效流程（T21/T23），不在本服务入口暴露。若传入 `REVOKED` 或 `PENDING`，抛 `ValueError`（与 `decide_approval` 的防御一致）。

---

## 6. 事务边界

| 操作 | 事务 |
|---|---|
| 读取 approval / task | 无写入，自动事务 |
| 条件 UPDATE | 单条 SQL，天然原子 |
| 重读分类 | 独立读；不改变结果（CAS 已判定胜负） |

- **不需要** `decide_approval(commit=False)`（Q7）。
- **不新增**独立 decision 表，因此没有“决定行 + 审批状态”的跨表事务。
- 数据库故障直接抛出，调用方负责回滚/重试；服务不会伪装成某个 outcome。

> 如果将来 Q1 改成独立表，这里必须升级为 `session.begin()` 包住两条写入 —— 届时再改。

---

## 7. 并发控制

- 唯一写操作是 CAS：`UPDATE ... WHERE id=:id AND approval_status='PENDING'`。
- 不采用“先 SELECT 判断再 UPDATE”作为决策依据；SELECT 只用于**分类**，不用于放行。
- 失败后的重读是**结果解释**，不是重试写入。
- 已验证（T18/T19 同款机制）：顺序重复第二次 rowcount=0。
- 限制：SQLite 写锁串行化；**跨进程与 PostgreSQL 未验证**，测试只用同进程两个独立 Session。

## 8. 与 T19 的关系

- T20 **不调用** `lifecycle_service`（Q8）。
- 决定写入后 Task/Execution 状态保持不变；恢复与校验属于 T22。
- 若将来 T22 在决定后迁移状态，必须走 `transition_pair`，不得直接 UPDATE。

## 11. 已知依赖：运行接线不在 T20

当前“图内的 interrupt → approval_request 行”本身也**没有接线**（T18 的 `create_or_get_approval` 同样只有测试调用）。
因此 T20 交付的是**服务层能力**，不是端到端落库：

| 环节 | 负责阶段 |
|---|---|
| 创建审批行（interrupt 时） | 未接线；属于 T23 统一执行器 |
| 提交决定（resume 时） | T20 提供 `submit_decision`；接线建议随 T23 |
| 恢复前校验 | T22 |
| 执行获批工具 | T23 |

**这意味着验收口径**：T20 的“合法决定可以被正确持久化”由服务测试证明；**端到端**要等 T23。这一点需要在确认 ADR 时一并接受。
