## 二、三个 ID 的语义与使用位置

| 标识 | 定义 | 生成 | 运行时使用 | 当前问题 |
|---|---|---|---|---|
| `chat_thread_id` | 业务会话 ID | 创建会话时由业务库生成 | `/agent`、`/agent/resume` 的归属校验；**被直接当作 LangGraph `configurable.thread_id`**（`stream.py:_config`） | 与 `models.py:10` 的设计约定相反 |
| `execution_id` | 一次执行的业务 ID | `create_execution` 中 `uuid4()`（`repository.py:141`） | 仅 T18/T22 测试；运行时**从未创建** | 审批无法绑定到真实执行 |
| `graph_thread_id` | LangGraph 图现场键 | 默认 `str(execution_id)`（`repository.py:146`） | **运行时从未使用**；全仓库仅测试引用 | `models.py:112` 要求 UNIQUE，且 `models.py:10` 称其是唯一 checkpoint 键 |
| `checkpoint_id` | 具体 checkpoint | LangGraph 返回 | 运行时**从不写回** `AgentExecution.checkpoint_id` | 无法从数据库定位到具体中断点 |

**结论**：数据库里的“图现场标识”是空的，实际图现场挂在业务会话 ID 上。
这三者当前没有一条可验证的对应关系。

## 三、数据库审批记录与图中断状态的关联

| 数据 | 位置 | 关联键 |
|---|---|---|
| 图状态 / interrupt | SQLite checkpoint，`thread_id = chat_thread_id` | — |
| 审批载荷 `pending_reviews` | 图状态（JSON dict） | 内含 `tool_call_id`、`path`、`diff`、`old_hash`；**不含** `approval_id` / `execution_id` |
| 用户决定 `decision_reviews` | 图状态（resume 值） | `decisions[].tool_call_id` |
| Task / Execution / Approval | 业务 SQLite 三张表 | 运行时**零行** |

- 理论上可用的关联键只有 `(execution_id, tool_call_id)`；
- 但运行时既不建 Execution，也不建 Approval，**关联链在源头断开**；
- `ToolNode` 执行时只看 `AIMessage.tool_calls`，不读数据库，因此“审批通过”与“真正执行”之间没有数据库约束。

### 4.1 指南要求重点核对的事项

| 核对项 | 实际 |
|---|---|
| `idempotency_key` 构造 | `sha256(f"{execution_id}:{tool_call_id}")`，**不含** args_hash（`service.py:63-68`）；参数变化表现为同键不同哈希 → `ApprovalConflict` |
| `tool_execution_status` 合法状态 | `NOT_STARTED / RUNNING / SUCCEEDED / FAILED / UNKNOWN`（`enums.py`） |
| 工具状态迁移规则 | 认领：仅 `APPROVED + NOT_STARTED → RUNNING`（`repository.py:332-351`）；结束：仅 `RUNNING → SUCCEEDED/FAILED/UNKNOWN`（`repository.py:354-384`）；无独立迁移表，非法值抛 `ValueError` |
| T22 是否校验整个 Execution | **是**。`resume_service.py:150-177` 取该 `execution_id` 下全部审批，任一 PENDING → `PENDING_APPROVALS`；任一拒绝/撤销 → `NOT_APPROVED`；任一已执行 → `ALREADY_EXECUTED` |
| 一个 Execution 能否出现多批审批 | **图允许**：批准 → 执行 → 模型再次调用高风险工具 → 再次 interrupt；但 T22 会因第一批已 `SUCCEEDED` 而返回 `ALREADY_EXECUTED` |
| REJECTED / REVOKED 的影响 | 二者都会使 T22 返回 `NOT_APPROVED`，且**永久**影响该 Execution 的后续恢复 |
| 已执行审批的影响 | `tool_execution_status != NOT_STARTED` → `ALREADY_EXECUTED` |
| T19 是否已有 `RUNNING → SUSPENDED` | **已有**，是受保护边（`lifecycle.py:101-105`），只能经 `suspend_after_resume_failure(guarded_ok=True)` 使用；适用范围与前置条件见上 |

## 七、事务、幂等、并发与崩溃恢复现状

| 层 | 现状 | 风险 |
|---|---|---|
| 业务库 | repository 方法内部 `commit()`；Service 组合用 `commit=False` | 与 checkpoint 无法同事务 |
| checkpoint | `AsyncSqliteSaver`，`isolation_level=None`（autocommit） | 与业务库完全独立 |
| 审批创建 | `create_or_get_approval` 内部 `commit()`；SAVEPOINT 防冲突污染 | 与调用方其它写入不能组合事务 |
| 决定提交 | 单行 CAS；幂等/冲突语义完整 | 无 API 调用 |
| 状态迁移 | 条件 UPDATE + 行数判断；配对迁移同事务 | 并发由 CAS 保护 |
| 图恢复 | 无数据库护栏；路由检查是 TOCTOU | 并发恢复未验证 |
| 工具执行 | 无认领、无结束 | 数据库无法阻止重复执行 |
| 崩溃窗口 | 审批行与 interrupt 之间无原子性；当前两者根本没有同时存在过 | 需 ADR-3 明确对账 |

**实测**：同一中断顺序 resume 两次——第二次不报错、不二次执行工具（sentinel 未被覆盖）。
**未实测**：两个并发请求同时 resume。

## 八、T23 架构决策清单与风险（Q1–Q6）

### Q1 绑定键 —— 推荐 A

`(execution_id, tool_call_id)` + 载荷携带 `approval_id` + `args_hash` 复核。

- 批次内 `tool_call_id` 唯一性：LangGraph 每次工具调用生成一个 id；同一 `AIMessage` 内唯一。
- 重试稳定性：同一 checkpoint 中断重放时 `tool_call_id` 不变；`idempotency_key` 因此稳定。
- 跨批次区分：必须由“当前审批批次”范围提供，不能只看 `tool_call_id`。
- `args_hash`：`sha256(canonical_json)`，键排序、无空格、UTF-8，已验证。
- 风险：若供应商复用同一 `tool_call_id`，需靠批次范围与 args_hash 双重校验。

### Q2 Execution 粒度与图现场键 —— 推荐 P1

一次 `/agent` 运行 = 一个 Execution；`execution.graph_thread_id` 成为实际 checkpoint 键。

- 支持一次运行多批审批（前提：T22 按批次校验）。
- 业务会话与图现场解耦。
- 需确认：多 Execution 是否允许并发；活动 Execution 如何判定；旧 checkpoint 如何处理。
- **必须单独批准**：T22 行为变更（增加可选批次范围）。
- 风险：改动面涉及 `stream.py`、`api/agent.py`、`coder.py` 拒绝分支、`resume_service.py`；历史开发 checkpoint 不可达。
- P2（沿用 `chat_thread_id`）只能支持“一次运行一批审批”，且字段语义继续不实；不建议长期化。
- P3（Execution 按批次 + 新 checkpoint 键列）需要 Schema 迁移。

### Q3 审批创建时机 —— 推荐 A

`prevalidate_node` 构建载荷后：先 `create_or_get_approval` 提交，再 `interrupt()`。

- 用户看到审批 UI 时，数据库已有可决策行。
- 失败窗口是“有审批行、无中断”，可通过预检识别。
- 不得把 ORM Session 放进 state；用 runtime 注入 + 短事务。
- 重试由 T18 幂等键兜底。

### Q4 拒绝语义 —— 推荐 A

T20 落 `REJECTED` → T19 `WAITING_APPROVAL → RUNNING` → 用拒绝决定 resume → 不执行工具 → 按现有图逻辑回 `model_node`。

- 必须区分“不执行工具”与“不调用 resume”。
- 同批其他已批准工具也全部不执行（现有整批语义）。
- 已批准未执行的记录保持 `NOT_STARTED`，后续批次校验必须把它们排除。
- 风险：若不做批次范围，旧拒绝会让该 Execution 永久 `NOT_APPROVED`。

### Q5 状态不一致 —— 推荐 A

恢复前双向预检：DB 当前审批批次 ↔ 图 interrupts；不一致 → 明确错误（如 `state_mismatch`），不改任何状态。

- 区分“暂时读不到 checkpoint”与“确认不一致”。
- 不自动 `REVOKED`；`REVOKED` 只用于明确取消流程。
- 日志需同时输出两侧标识，便于诊断。

### Q6 工具认领与结束 —— 推荐 A

只覆盖高风险审批批次：执行前原子认领，失败整批不执行；执行后记 `SUCCEEDED/FAILED/UNKNOWN`。

- 认领 CAS：`APPROVED + NOT_STARTED → RUNNING`。
- 结束 CAS：`RUNNING → 终态`。
- 认领后、执行前崩溃 → 保持 `RUNNING`，恢复时必须人工/明确策略处理，不能自动重放。
- 外部副作用无法由数据库保证“恰好一次”；`UNKNOWN` 禁止自动重试。
- 不扩展成覆盖全部工具的统一执行器。
