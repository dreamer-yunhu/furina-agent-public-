## 2. Q1 · Task / Execution 迁移表

### 选项

- **A（推荐）**：按下表执行

### Task

| 当前 | 目标 | 允许 | 条件 |
|---|---|---|---|
| `QUEUED` | `RUNNING` | ✅ | 主管认领并创建 Execution |
| `QUEUED` | `CANCELLED` | ✅ | 用户取消 |
| `RUNNING` | `WAITING_APPROVAL` | ✅ | 出现待审工具调用 |
| `RUNNING` | `COMPLETED` / `FAILED` / `CANCELLED` | ✅ | 正常结束 / 失败 / 取消 |
| `WAITING_APPROVAL` | `RUNNING` | ✅ | 决定完成，继续执行 |

### Execution

| 当前 | 目标 | 允许 | 条件 |
|---|---|---|---|
| `CREATED` | `RUNNING` / `CANCELLED` | ✅ | 开始执行 / 未启动即取消 |

| 终态 | 任意 | ❌ | `VALIDATION_FAILED` 也是终态；重试=新建 Execution |

## 3. Q2 · `SUSPENDED` 的出口

### 背景

规范明确：**超时只把 Task/Execution 置 `SUSPENDED`，不改审批状态，也不自动批准/拒绝**。所以必须回答：谁、在什么条件下把它带出 `SUSPENDED`。

### 选项

| 选项 | 出口 | 后果 |
|---|---|---|
| **A（推荐）** | 只有 `RUNNING / FAILED / CANCELLED` | 与规范一致；迟到决定走 `SUSPENDED→RUNNING`（校验在 T22） |
| B | 额外允许 `SUSPENDED → WAITING_APPROVAL` | 会造出“重新挂起”路径，需要定义审批请求是否复用；复杂度明显上升 |
| C | 超时自动 `SUSPENDED → FAILED` | **违反规范**（超时不自动终态），不建议 |

### 影响

选 A 时，T19 只提供迁移原语；“能不能恢复”由 T22 判断后调用。

## 4. Q3 · 事务边界

### 背景

审批完成时，通常需要：

```
Execution: WAITING_APPROVAL → RUNNING
Task:      WAITING_APPROVAL → RUNNING
```

两行必须同成同败。但现状每个 repository 方法内部 `commit()`，做不到。

### 选项

| 选项 | 做法 | 改动面 | 风险 |
|---|---|---|---|
| **A（推荐）** | 只给 `transition_task` / `transition_execution` 加 `commit: bool = True` | 2 个函数签名，默认行为不变 | 极小；现有调用不用改 |
| B | 所有 repository 函数都加 `commit` | 8+ 个函数，T18 service 也要跟着改 | 改动大，回归面广 |
| C | 引入 UnitOfWork | 新抽象层 | 当前只有一个使用场景，过度设计 |

### 选 A 后的写法（示意，不是最终代码）

```python
async with session.begin():          # 事务所有权在 service
    ok1 = await transition_execution(..., commit=False)
    ok2 = await transition_task(..., commit=False)
    if not (ok1 and ok2):
        raise LifecycleConflict(...)  # 抛出 → 整个事务回滚
```

### 影响

- 选 A：T19 能保证**数据库内**成对迁移原子；文件副作用仍不保证（T19 明确不解决）
- 选 B：未来 T20 更顺，但本轮要回归更多既有函数
- 选 C：不建议

## 5. Q4 · 如何防止“绕过规则直接写库”

### 背景

指南要求“状态迁移服务不能允许调用方绕过规则”。但 `repository.transition_*` 是公开函数，任何调用方都能直接传任意 `from/to`。

### 选项

| 选项 | 做法 | 效果 | 代价 |
|---|---|---|---|
| **A（推荐）** | repository 内部调用纯函数 `is_legal_*(from, to)`，非法直接拒绝 | **唯一物理入口**，绕不过 | repository 多承担一条“配对是否合法”的判断（不涉及“何时迁移”） |
| B | `transition_*` 改名为 `_transition_*`，只暴露 service | 强制收敛 | 改公开 API，现有测试要改 |
| C | 只靠 service + code review | 最省事 | 物理上仍可绕过，不满足指南的硬要求 |

### 关键区分

- **配对合法性**（A→B 允不允许）→ 放 repository 没问题，是静态规则
- **迁移时机**（现在该不该迁）→ 仍在 service，repository 不碰
