## 5. Windows 进程生命周期

### 5.1 进程树形态

```
Tauri 进程
 └─ Child (Option<Child>, backend.rs:28)      ← 只持有 ①② 两个
     ├─ [打包态] furina-backend.exe (PyInstaller onefile bootloader)
     │    └─ _MEIxxxx 解包后的 python 子进程    ← 真正跑 uvicorn
     └─ [开发态] .venv\Scripts\furina-desktop.exe (pip launcher)
          └─ python.exe                         ← 真正跑 uvicorn
```

两种形态都是"**一层 launcher + 一层 python**"，因此 `taskkill /PID /T /F` 是必需的（`backend.rs:249-258` 已记录为实测踩坑）。

### 5.2 逐项回答任务书 §二-3

| 问题 | 答案 |
|---|---|
| Rust 如何持有子进程句柄 | `BackendProcess(Mutex<Option<Child>>)`；`None` 语义 = "不归我管，退出不杀"（`backend.rs:28`、`150-158`） |
| 开发环境是否存在 uv 中间进程 | **无 uv 进程**。是 pip/uv 生成的 `Scripts/*.exe` launcher + 其派生的 `python.exe`，共两层 |
| 是否存在子进程残留风险 | 是，三类：① Job 分配失败时仅剩 `taskkill /T`（只在正常退出路径）② 端口被占时不接管 → 该进程永远无主 ③ 崩溃时靠 Job 兜底 |
| 如何实现退出监控 | **当前未实现**。`spawn` 之后不 `try_wait`、不订阅退出、不发事件。唯一"监控"是前端每 10s 轮询 `/healthz`（`BackendProvider.tsx:66-84`） |
| 如何优雅关闭 Python | **未实现**。`taskkill /F` 为硬杀，uvicorn lifespan 不执行 → 见 R4 |
| 是否需要 Windows Job Object | **需要，且已实现**。`taskkill /F`、崩溃、任务管理器结束均绕过 `RunEvent::Exit`，只有内核级 `KILL_ON_JOB_CLOSE` 可兜底（`backend.rs:57-109`） |

### 5.3 R4 的证据：没有优雅关闭

```
%LOCALAPPDATA%\com.furina.desktop\backend\data\checkpoints.sqlite-wal   4,120,032 B
C:\furina-agent\data\checkpoints.sqlite-wal                             2,150,672 B
```

WAL 长期不 checkpoint = 进程被硬杀，`close_checkpoint_store()` 从未执行。
SQLite 本身崩溃安全（数据不损坏），但每次启动需重放 WAL，且与"关窗即正常退出"的预期不符。

### 7.2 三个已确认的目录问题

**① `FURINA_DATA_DIR` 是半吊子变量（R3）**

`main.py:153` 尊重该变量，但两个 `default_db_path()` 完全不看它。
后果：设 `FURINA_DATA_DIR=D:\furina` → **锁在 D 盘、数据库仍在 CWD**，单实例语义与数据位置脱节。

**② 安装版的沙箱根指向开发仓库（R6，证据确凿）**

```
%APPDATA%\furina-agent\.env:25   SANDBOX_ROOT=C:/furina-agent/sandbox
打包态启动日志                    沙箱根就绪：C:\furina-agent\sandbox
```

一个"开箱即用"的产品，文件工具的工作区是**作者的源码仓库目录**。换机器会在 `C:\furina-agent\sandbox` 现造目录，用户的文件根本不在那里。

**③ 当前机器上同时存在 4 份数据锚点**

```
C:\furina-agent\data\                                   ← dev 从仓库根启动
C:\furina-agent\apps\desktop\src\furina_desktop\data\   ← 从包目录启动过一次
%LOCALAPPDATA%\com.furina.desktop\backend\data\         ← 安装版
%APPDATA%\furina-agent\.env                             ← 配置与数据分家
```

"同一应用的不同启动方式看到不同历史"即源于此。

### 7.3 统一 `FURINA_DATA_DIR` 方案

```
Rust 侧（唯一权威，backend.rs::spawn）：
  dev      → 仓库根（沿用已有库，避免丢历史）
  release  → app_local_data_dir()          // %LOCALAPPDATA%\com.furina.desktop
  显式设置 FURINA_DATA_DIR 时覆盖以上两者
  一并注入 SANDBOX_ROOT=<data>/workspace   // 不再依赖 .env

Python 侧（唯一入口）：
  furina_desktop/paths.py
      def data_dir() -> Path    # FURINA_DATA_DIR 或 "data"（相对 CWD）
  checkpoints.sqlite / furina.db / furina.lock / logs / sandbox 全部走它
```

**为什么不"全塞进 Rust"**：Python 必须能独立跑（`uv run furina-desktop`、pytest），默认值必须在 Python 侧成立，env 只作覆盖。

## 10. 推荐 BackendManager 模块设计

**不建议推翻重写** —— 现有实现已覆盖约 80%。建议从"函数集合"提升为"带状态机的管理器"，补齐三件缺失能力：**可观测、可等待、可自杀**。

```rust
// src-tauri/src/backend/mod.rs（由 backend.rs 拆分而来）
pub struct BackendManager {
    state: Mutex<BackendState>,
    host: String,             // 与 Python 同源，不再各写一份
    port: u16,
    log_path: PathBuf,
}

pub enum BackendState {
    Stopped,
    Starting { child: Child, since: Instant },
    Ready    { child: Child, pid: u32, since: Instant },
    Failed   { reason: String, at: Instant },
    External { pid: Option<u32> },   // 端口被别人占着，不归我管
}
```

四项必须新增的能力：

| 能力 | 现状 | 目标 |
|---|---|---|
| **① 日志落盘** | 全丢 | `spawn` 时 `.stdout(File::create(data_dir/backend.out.log))`、`.stderr(...)`；Rust 侧日志在 release 也注册（至少写文件） |
| **② 就绪握手** | 仅一次 300ms TCP 探测 | `spawn` 后轮询 `GET /healthz` 至 `status=="ok"`，20s 超时 → `Failed`，用 Tauri event 推给前端 |
| **③ 退出监控** | 无 | 独立线程每 1s `child.try_wait()`；非预期退出 → emit `backend://crashed`（可选：退避重启，上限 3 次） |
| **④ 优雅关闭** | `taskkill /F` | 先 `POST /shutdown`（或 `CTRL_BREAK`），等 3s，再 `taskkill /T /F`；Job Object 仍作最终兜底 |

> **顺序理由**：① 必须最先做。没有它，②③④ 出问题时依然看不见 —— 这正是本次审计卡在"原因待验证"的根本原因。

### 12.1 `GET /healthz`（无需鉴权，仅回环）

现状（`main.py:304-322`）`status` 恒为 `"ok"`，建议改为：

### 12.2 `POST /shutdown`（新增，最小面）

## 13. 进程退出与异常处理矩阵

| 场景 | 现状 | 目标 |
|---|---|---|
| 正常关窗 | `Exit` → `shutdown()` → `taskkill /T /F` | 先 `/shutdown` 优雅退，3s 后兜底强杀 |
| `taskkill /F` 杀应用 | Job Object 生效 ✅ | 保持 |
| 应用崩溃 | Job Object 生效 ✅ | 保持 |
| 后端启动失败 | 静默返回 `None`，前端显示"未连接" | `Failed{reason}` + 事件 + 界面显示真实原因 |
| 后端中途崩溃 | 前端 10s 变红，**不重启** | 事件 + 可选自动重启（退避 + 次数上限） |
| 端口被他人占用 | 视为"已有服务"，不接管 ✅ | 保持；但**加一次 `/healthz` 确认是自己的服务**，否则提示"端口 8001 被其他程序占用" |
| 后端卡死（进程在、不响应） | 前端变红，进程不死 | 健康检查连续 N 次失败 → 主动重启 |
