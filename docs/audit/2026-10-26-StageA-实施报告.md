## 2. 实际实现的主管图

```
START ─▶ intent_node ─▶ validate_intent_node ─┬─(CHAT)────────────▶ chat_graph ─▶ END
                 ▲                            ├─(CODE)────────────▶ coder_graph ─▶ END
                 │                            └─(非法 / 不支持)───▶ route_failed_node ─▶ END
                 └── Command(goto="intent_node") · 携带 intent_error 重试（上限 2 次）
```

- 条件路由用 `Command(goto=...)`，**没有** `add_conditional_edges` 的字符串映射表
  （少一张会漂移的表，代价是路由逻辑与节点耦合 —— 认为值得）。
- 意图模型：`supervisor_llm`（`disable_streaming=True`），只喂本次请求，不喂历史。
- 校验：结构 → 枚举 → 落点；两类失败分开处理（见 §3）。
- 子图仍是"编译好的图当节点"挂载 → namespace 前缀 `chat_graph:` / `coder_graph:` 成立，
  审批恢复预检的 `_iter_snapshots` 仍能取到 `coder_messages`。

## 3. 输入输出契约

### 主管入口（`agent_stream` 构造）

```python
{
  "messages":    [{"role": "user", "content": user_input}],
  "task_input":  user_input,       # 唯一权威输入
  "task_id":     str(run.task_id),
  "execution_id": str(run.execution_id),
}
```

### 意图契约

模型只输出 `{"intent": "CHAT" | "CODE", "reason": "..."}`，落到 `intent_raw`，**不进 messages**。

| 情形 | 处理 | 出口 |
|---|---|---|
| 不是 JSON / 缺字段 / 类型不对 | 回填 `intent_error`，重试 | `intent_node` |
| 重试达上限（2 次） | 失败 | `route_failed_node` |
| JSON 合法但意图不在支持集（如 `RAG`） | **立即**失败，不重试 | `route_failed_node` |
| 合法 `CHAT` | 写 `intent=CHAT`, `route_status=ok` | `chat_graph` |
| 合法 `CODE` | 同上 + `subagent_task = task_input` | `coder_graph` |

### 子图契约

| 子图 | 输入 | 输出 |
|---|---|---|
| `chat_graph` (`ChatState`) | `task_input` | `result` |
| `coder_graph` (`CoderState`) | `subagent_task` / `task_id` / `execution_id` | `result` |

`chat_messages` / `coder_messages` / `pending_reviews` 等内部状态**不出子图**（有断言）。

### 业务态 vs 生命周期

| 层 | 字段 | 谁写 |
|---|---|---|
| 业务结果 | `route_status` / `route_error` / `result` | 图 |
| 图运行现场 | checkpoint（`graph_thread_id`） | LangGraph |
| 数据库状态 | Task / Execution / Approval | **只有** `runtime.finalize_run` |

`stream._stream_graph` 收尾三种语义：`interrupted`（有中断）→ `failed`（`route_status=="failed"`）
→ `completed`。路由失败会发 `error{code:"route_failed"}` 再发 `done{failed}`。
