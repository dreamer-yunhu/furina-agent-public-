## 一、阶段目标

让“高风险工具调用”在 `interrupt()` 之前先落到 `approval_request`，
并把图现场键从业务 `chat_thread_id` 切换到 `execution.graph_thread_id`。

验收口径：一次有效中断对应一个正确的持久化审批批次；重试不产生错误重复记录。

## 三、设计依据与实现结果

### 3.1 `/agent` 创建执行（ADR-2 P1）

- 创建 `AgentTask`（QUEUED→RUNNING）与 `AgentExecution`（CREATED→RUNNING）。
- `graph_thread_id` 默认为 `str(execution_id)`，LangGraph 用它作为
  `configurable.thread_id`。
- 同一业务会话已有活动执行（CREATED/RUNNING/WAITING_APPROVAL/SUSPENDED）时，
  第二个 `/agent` 返回 409 `thread_busy`，携带 `execution_id` 与状态。
- 单进程内用按 `thread_id` 的 `asyncio.Lock` + DB 查询双重保护。

### 3.2 审批创建（ADR-3 A）

`prevalidate_node` 顺序：

1. 构造 `WritePreview`（diff / old_hash / creates_dirs）。
2. `AgentRuntime.ensure_approvals`：
   - 校验 Task/Execution 存在、归属一致、状态对为 RUNNING 或已 WAITING；
   - 对每个高风险调用调用 T18 `create_or_get_approval`；
   - `deadline_at = now + approval_timeout_seconds`；
   - 全部成功后将 Task/Execution 成对迁移到 `WAITING_APPROVAL`。
3. 把 `approval_id` 写回每个 `WritePreview`。
4. 进入 `review_node` 调 `interrupt()`。

失败行为：审批构造或落库失败 → 不进入 `review_node`，回填错误给 `model_node`。
已有审批行在重试时由 T18 幂等键复用；参数变化抛 `ApprovalConflict`，包装为
`ApprovalSetupError`，同样不中断。

### 3.3 中断载荷

`approval_required` 事件里的每个 request 现在包含：

```json
{"tool_call_id": "call_w1", "approval_id": "<uuid>", "path": "...", "diff": "...", ...}
```

`approval_id` 与数据库行一一对应；`tool_call_id` 仍保留用于现有决定匹配。

### 3.4 运行收尾

- 图正常完成且无中断 → Task/Execution `COMPLETED`。
- 图抛异常 → `FAILED`（仅当状态对为 RUNNING）。
- 停在中断 → 不改状态（`WAITING_APPROVAL` 已由 prevalidate 设置）。
- 收尾失败只记录日志，不把已完成的流改成断流。

### 3.5 `/agent/resume`（T23-2 过渡）

- 通过活动 Execution 定位 `graph_thread_id`，不再用业务会话 id 当图键。
- 现有“决定与待审 tool_call_id 对齐”校验保留。
- **过渡实现**：校验通过后调用 `runtime.mark_resumed`，用 T19 把
  `WAITING_APPROVAL/SUSPENDED` 成对迁回 `RUNNING`，再恢复图。

> ⚠️ `mark_resumed` 只做 T19 迁移，**不做 T22 校验**。T23-4 会替换为
> `validate_and_resume`（批次校验 + CAS），并删除这条过渡路径。

1. `graph_thread_id == str(execution_id)`。
2. 安全运行收尾为 `COMPLETED`，无审批行。
3. 高风险调用：图中断 + 审批行 PENDING + Task/Execution `WAITING_APPROVAL`。

HTTP 测试额外断言：审批行与工具状态、任务状态、恢复后 `COMPLETED`。

## 五、故障与风险（必须知晓）

| # | 问题 | 影响 | 计划 |
|---|---|---|---|
| R1 | **恢复仍是过渡路径**：`mark_resumed` 只做 T19，不调用 T22/T20 | 恢复前没有批次校验、参数校验、已执行校验 | T23-4 替换 |
| R2 | **决定未落库**：用户批准/拒绝后，`approval_request` 仍为 `PENDING` | 数据库与“工具已执行”暂时不一致；T22 现在无法通过校验 | T23-3 |
| R3 | **工具执行状态未更新**：`tool_execution_status` 仍 `NOT_STARTED` | `ALREADY_EXECUTED` 不生效；并发/重放保护缺失 | T23-4 |
| R4 | 恢复失败没有补偿 | 图异常时 Task/Execution 直接 `FAILED`；未按“是否已开始执行”分流 | T23-4 / ADR-7 |
| R5 | 崩溃后活动 Execution 可能长期阻塞 | 例如启动后图未跑、状态停在 RUNNING | T23-4 对账 |
| R6 | 旧 `chat_thread_id` checkpoint 不可达 | 开发环境旧挂起会话无法继续 | 已批准：不迁移 |
| R7 | 单进程锁 | 多进程并发不受保护 | 桌面版单实例；明确记录 |
| R8 | `state_mismatch` 预检未实现 | DB 与图不一致时只能靠路由的“是否有中断”判断 | T23-4 / ADR-5 |

> **不建议把 T23-2 单独作为发布版本。** 它是内部里程碑；R1–R3 必须由 T23-3/T23-4 闭环。
