## 0. 为什么现在必须你定

审计确认：**超时机制完全不存在**，`deadline_at` 只是存储字段；运行时也没有审批数据。

T21 要新增一个“会自己动状态”的后台机制。这类东西一旦定错，后面很难靠改一个函数挽回：

1. 扫描方式决定它怎么启动、怎么停、怎么测
2. 竞态策略决定“决定”和“超时”谁说了算
3. 聚合规则决定一个多审批的执行什么时候挂起

## 2. Q1 · 用什么方式检查超时？

| 选项 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A（推荐）** | lifespan 里起一个 `asyncio` 后台循环，每 N 秒 `scan_once()` | 无新依赖；启停可控；核心函数可单测 | 进程内循环，多实例会重复扫（桌面有单实例锁） |
| B | 请求到达时顺手扫（比如 `/agent/resume` 前） | 无后台任务 | 没人请求就不扫；超时语义变成“惰性” |
| C | 外部 cron / Windows 计划任务调 CLI | 与进程解耦 | 桌面应用不该依赖系统计划任务；部署复杂 |

### 影响

- 选 A：新增 `scan_once` + lifespan 启停 + 配置开关
- 选 B：不需要后台任务，但“超时”要等下一次访问才生效，验收里的“到达截止时间能被识别”会变得难以定义
- 选 C：超出桌面版产品形态

## 3. Q2 · 怎样判断“确实需要挂起”？

### 条件清单

| 条件 | 说明 |
|---|---|
| `approval_status == PENDING` | 已有决定的请求不再处理 |
| `deadline_at <= now` | 到达即到期（含等于） |
| `execution.task_id == approval.task_id` | 关联正确 |
| `Task.status == WAITING_APPROVAL` | 只挂起“正在等审批”的任务 |
| `Execution.status == WAITING_APPROVAL` | 同上 |
| Task 非终态 | 终态不可出（迁移表也会拒绝） |

| 选项 | 做法 | 后果 |
|---|---|---|
| **A（推荐）** | 六条全满足才挂起 | 最保守；不一致数据只 skip 并计数 |
| B | 只看 `deadline_at` | 可能把已经在执行/已终态的任务挂起 |
| C | 只要求 Task 满足，Execution 不检查 | 会造出 Task/Execution 状态不一致 |

### 关联错误的处理

选项 A：skip + 计数（`mismatch`），**不尝试修复**。
选项 B：顺手把 Execution 也对齐 —— 越权，且掩盖数据问题。**不建议**。

## 4. Q3 · 重复扫描怎么办？

| 选项 | 做法 | 后果 |
|---|---|---|
| **A（推荐）** | 依赖 `transition_pair` 的 CAS：第二次返回 `CONFLICT`，不做事 | 天然幂等，无需新字段 |
| B | 给审批加 `scanned_at` / `suspended_at` 标记 | 要改 Schema；且标记本身又需要 CAS |
| C | 进程内 Set 去重 | 重启失效；多实例失效；不解决并发 |

### 资源释放的幂等

只在 `(APPLIED, APPLIED)` 时调用 `on_suspended`。重复扫描不会重复释放。

## 5. Q4 · 超时与用户决定同时发生？

### 现实

- T20 决定：CAS 在 `approval_request`
- T21 扫描：CAS 在 `agent_task` / `agent_execution`

**两者可以同时成功**，产生 `APPROVED + SUSPENDED`。

规范已经允许这个中间态：迟到批准保存、不自动恢复，交给 T22。

### 选项

| 选项 | 做法 | 后果 |
|---|---|---|
| **A（推荐）** | 扫描事务内重读 approval，仍 `PENDING` 才迁移；接受剩余窗口 | 结果始终是合法状态；窗口在 PG 上仍可能产生 `SUSPENDED + APPROVED`（合法） |
| B | 对 approval 行加 `SELECT ... FOR UPDATE`，与 T20 串行化 | 能收紧窗口，但把 T20/T21 锁语义绑死；SQLite 上 `FOR UPDATE` 无实际效果 |
| C | 挂起后再检查 approval，若已决定则回滚 | 需要额外事务/补偿，且“回滚已提交的挂起”本身更复杂 |

### 建议

选 A，并在文档里明确：**`SUSPENDED + APPROVED` 是合法中间态，不是错误**，由 T22 恢复校验消化。

## 6. Q5 · Task 与 Execution 怎么保持一致？

| 选项 | 做法 | 后果 |
|---|---|---|
| **A（推荐）** | 复用 `transition_pair`（同事务、同成同败） | 零新代码；失败回滚 |
| B | 分别调 `transition_task` / `transition_execution` | 可能一半成功；违反 T19 事务责任 |
| C | 直接写 SQL | 绕过 T19，明确禁止 |

### 注意

`transition_pair` 要求传入**尚未开启事务**的 session；扫描器应为每个候选开一个独立会话。

## 7. Q6 · 时间怎么统一？

| 项 | 选择 |
|---|---|
| 时区 | 统一 UTC；读出的 naive 按 UTC 解释（`as_utc`） |
| 当前时间 | 服务端 `datetime.now(UTC)`，可注入 `now` 供测试 |
| 边界 | `now >= deadline_at` |
| 测试 | 直接传 `now`，不 sleep |

备选：用数据库时间（`CURRENT_TIMESTAMP`）——跨库语义不一致、测试难控，不推荐。

## 8. Q7 · 一个执行有多条待审时，何时挂起？

| 选项 | 规则 | 后果 |
|---|---|---|
| **A（推荐）** | **最早一条到期**就挂起整个 Task/Execution | 只要还有审批没结论，执行本来就动不了 |
| B | 全部到期才挂起 | 一条长期未决的审批不会触发挂起；与“等待超时”直觉不符 |
| C | 按审批逐条挂起 | Task 只有一个状态，无法表达“部分挂起” |

## 9. Q8 · 扫描间隔、批量、开关

| 选项 | 间隔 | 批量 | 后果 |
|---|---|---|---|
| **A（推荐）** | 30s | 50 条/次 | 桌面单机够用；延迟可接受 |
| B | 5s | 10 条 | 更及时，但空转与写锁竞争更多 |
| C | 5min | 500 条 | 延迟大；一次事务过重 |

建议做成配置项（默认 30s，`0` = 关闭），便于测试与线上排查。

## 10. Q9 · “释放调度资源”怎么落地？

项目里**没有任务调度器**（审计 §六）。

| 选项 | 做法 | 后果 |
|---|---|---|
| **A（推荐）** | 提供 `on_suspended(task_id, execution_id)` 钩子，默认只记日志 | 现在不做假动作；将来有调度器在这里接 |
| B | 现在造一个调度器/队列 | 为一个钩子引入大基础设施，越界 |
| C | 不做钩子 | 将来接调度器时要改扫描器内部 |

## 11. Q10 · T21 是否顺带把运行时接线做了？

| 选项 | 范围 | 后果 |
|---|---|---|
| **A（推荐）** | 只做扫描能力 + 测试 | 与 T23 边界清晰；但线上暂时不会自动挂起 |
| B | 顺带把 interrupt → approval 行接线 | 与 T23 重叠；且会牵扯 T18/T20 的调用链 |

> 选 A 时，验收口径是“扫描器对种子数据正确工作”，不是“线上自动挂起”。

## 12. Q11 · 状态不一致的候选怎么处理？

| 选项 | 做法 | 后果 |
