# ADR-1：审批与工具调用的绑定

## 背景与现有代码证据

- `ApprovalRequest` 已有 `execution_id`、`tool_call_id`、`args_json`、`args_hash`、`idempotency_key`（`models.py`）。
- T18 的幂等键是 `sha256(f"{execution_id}:{tool_call_id}")`，**不含** `args_hash`（`service.py:63-68`）。
- 中断载荷 `ReviewRequest.requests[]` 只含 `tool_call_id / path / diff / old_hash`，不含 `approval_id`（`coder.py:prevalidate_node`）。
- 运行时从未创建审批行，绑定链当前不存在。

## 需要解决的问题

1. 一条审批记录必须能唯一追溯到一次具体工具调用。
2. 同一工具多次调用、甚至参数相同，不能串批。
3. 决定必须能回指数据库行，而不是只凭 `tool_call_id`。
4. 参数快照变化必须被检出。

## 候选方案

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A（推荐） | `(execution_id, tool_call_id)` 为稳定键；载荷增加 `approval_id`；`args_hash` 复核 | 不改 Schema；复用 T18；决定可精确定位 | `tool_call_id` 的跨批次唯一性依赖批次范围 |
| B | 新增 `checkpoint_id` / `tool_call_index` 列 | 关联最强 | Schema + 迁移；当前取不到稳定 index |
| C | 只按工具名或 `args_hash` 匹配 | 无 | **禁止**，同参数多次调用会串批 |

## 决策

采用 **A**。

**数据契约**

- `ReviewRequest.requests[]` 每项新增：
  - `approval_id: str`（UUID 文本）
  - 保留 `tool_call_id`、`path`、`diff`、`old_hash`
- 决定项：`{approval_id, action, reason?}`；`tool_call_id` 仍保留用于与图状态对齐。
- 不新增数据库字段。

**不变量**

1. 一个 `(execution_id, tool_call_id)` 最多一条审批（由 `idempotency_key` UNIQUE 保证）。
2. 决定只能作用于“当前 interrupt 批次”中的审批。
3. 恢复前必须重新计算 `args_hash`，与审批行比对；不一致拒绝。
4. 不得仅凭工具名或 `args_hash` 关联。

**批次定义**：一次 `interrupt()` 对应的全部 `approval_id` 集合。
批次身份由“当前图中断里的 `approval_id` 集合”确定，不新增字段。

## 影响的接口与文件

- `agent/contracts.py`：`ReviewRequest` / `ReviewDecision` 增加 `approval_id`
- `agent/nodes/coder.py`：`prevalidate_node` 写入 `approval_id`
- `agent/dependencies.py`：按 `approval_id` 对齐
- `agent/stream.py`：决定匹配改为按 `approval_id`
- `api/contracts.py`：新增决定请求模型

## 失败模式与测试

| 场景 | 期望 |
|---|---|
| `approval_id` 不属于当前 execution | 拒绝，409 |
| `approval_id` 不在当前 interrupt 中 | 拒绝，409 `state_mismatch` |
| 同批 `tool_call_id` 重复 | 创建阶段拒绝（不应发生） |
| 参数被篡改 | `ARGS_MISMATCH`，不执行 |
| 重试同一创建请求 | 返回原行，不新增 |

测试类型：真实数据库集成 + 真实图中断；不是 Mock。

## 兼容性与迁移风险

- 旧版本 checkpoint 中没有 `approval_id`：P1 切换图键后旧现场不再可达，不兼容属预期。
- 不改表，无数据迁移。

# ADR-2：Execution 粒度与图现场键

## 背景与现有代码证据

- `models.py:10`：`graph_thread_id` 是唯一传给 `configurable.thread_id` 的值；业务 `thread_id` 只做分组。
- `models.py:112`：`graph_thread_id` UNIQUE。
- `repository.py:146`：默认 `graph_thread_id = str(execution_id)`。
- `stream.py:_config`：实际传的是 `chat_thread_id`。
- 运行时从未创建 Task / Execution。
- 历史 checkpoint 均以 `chat_thread_id` 为键。

## 需要解决的问题

1. 数据库与图现场必须使用同一个键。
2. 一次运行可能先后产生多批审批。
3. `/agent` 如何判断会话已有活动/挂起执行。
4. `/agent/resume` 如何从持久化记录定位图现场。
5. 旧 checkpoint 如何处置。

## 候选方案

| 方案 | Execution 粒度 | 图键 | 多批审批 | Schema |
|---|---|---|---|---|
| **P1（推荐）** | 一次 `/agent` 运行 | `execution.graph_thread_id` | 支持（T22 按批次） | 不改 |
| P2 | 一次运行 | 仍用 `chat_thread_id` | 不支持 | 不改 |
| P3 | 一批审批 | 新增 `checkpoint_thread_id` | 支持 | 改表 + 迁移 |

## 决策

采用 **P1**，并补充以下规则：

1. **一次 `/agent` 请求创建一个 Task 和一个 Execution**：
   - Task：`QUEUED → RUNNING`
   - Execution：`CREATED → RUNNING`
   - `graph_thread_id = str(execution.id)`
2. LangGraph 的 `configurable.thread_id` 使用 `execution.graph_thread_id`。
3. **同一业务会话同一时刻只允许一个活动 Execution**：
   - 活动 = `CREATED / RUNNING / WAITING_APPROVAL / SUSPENDED`
   - 单进程内用按 `thread_id` 的 `asyncio.Lock` + 数据库查询双重保护；
   - 多进程并发不支持，明确记录为限制（桌面版单进程）。
4. `/agent` 的“是否挂起”改为查活动 Execution，不再读 `chat_thread_id` 的 checkpoint。
5. `/agent/resume` 通过 `approval_id` → Approval → Execution 定位图键；
   `chat_thread_id` 只用于归属校验，不作为图键。
6. `checkpoint_id` 在 interrupt 后与运行结束时回写 `AgentExecution.checkpoint_id`。
7. 一处运行结束时：成功 → Task/Execution `COMPLETED`；失败 → `FAILED`（带明确原因）。
8. 历史以 `chat_thread_id` 为键的 checkpoint **不迁移、不兼容**；文档记录，必要时由开发环境自行清理。

## 影响的接口与文件

- `api/agent.py`：创建 Task/Execution；活动执行检查；resume 定位
- `agent/stream.py`：`_config` 改为接收图键；输入不再负责建执行
- `agent/runtime.py`（新增）：活动执行查询、按线程锁、执行收尾
- `agent/build.py`：不变
- 测试：新增“同会话第二个 `/agent` 被 409”“resume 从 approval 定位图键”

## 失败模式与测试

| 场景 | 期望 |
|---|---|
| 同会话已有活动 Execution | 新 `/agent` 409，返回 active execution id |
| 两个并发 `/agent` | 只有一个创建成功（单进程锁 + DB 检查） |
| Execution 已创建但图未启动 | 启动/下次请求时识别并收尾（ADR-7） |
| resume 用别人会话的 approval | 404/403，不泄漏存在性 |
| 旧 chat 键 checkpoint | 不再被读取，不静默回退 |

## 兼容性与迁移风险

- 现有开发库中的挂起会话无法继续；这是 P1 的明确代价。
- 不改 Schema；但要求 `/agent` 与 `/resume` 的请求/响应契约调整。
- 多进程部署需额外的数据库级互斥，T23 不解决。

# ADR-3：审批创建、幂等与中断一致性

## 背景与现有代码证据

- `prevalidate_node` 构建 `ReviewRequest` 后直接 `goto="review_node"`；`review_node` 调 `interrupt()`。
- T18 `create_or_get_approval` 已实现幂等：SAVEPOINT + flush；冲突按身份逐项比对；内部 `commit()`。
- 配置中没有“审批超时”字段；`ApprovalRequest.deadline_at` 目前没有运行时来源。
- 数据库提交与 checkpoint 保存不可能原子。

## 需要解决的问题

1. 审批行必须在用户看到审批 UI 前存在。
2. 重试不能产生重复行。
3. 多步之间的崩溃窗口必须有明确行为。
4. `deadline_at` 从哪来。

## 决策

采用 **A：先落库 → 再迁移 → 再中断**。

**执行顺序（`prevalidate_node` 内）**

1. 构造每个高风险工具的审批载荷（含 diff / old_hash）。
2. 调用 `create_or_get_approval`：
   - `deadline_at = now + approval_timeout_seconds`
   - 新增配置 `approval_timeout_seconds`，默认 `3600`
3. 全部成功 → `transition_pair(WAITING_APPROVAL)`。
4. 返回 `Command(goto="review_node", update={"pending_reviews": ...})`。
5. `review_node` 调 `interrupt()`，checkpoint 保存。

任一前置步骤失败：**不进入 `review_node`**，不向用户展示审批；回填错误给 `model_node`，保持任务可继续。

**失败窗口矩阵**

| 崩溃点 | 数据库 | 图 | 处理 |
|---|---|---|---|
| 审批提交后、状态迁移前 | 审批 PENDING；Task/Execution 仍 RUNNING | 无 interrupt | 重试 `prevalidate` 复用同一批审批（幂等键）；不展示 UI |
| 状态迁移后、interrupt 前 | WAITING_APPROVAL + PENDING | checkpoint 下一节点为 `review_node`，无 interrupt | 运行时对账：驱动图到 `review_node` 重新触发 interrupt；失败则按 ADR-7 收尾 |
| interrupt 保存后 | WAITING_APPROVAL + PENDING | interrupt 存在 | 正常等待决定 |
| 用户看到 UI 后进程崩溃 | 不变 | checkpoint 持久化 | 重启后正常恢复 |

**边界**

- 不声称数据库事务覆盖 checkpoint。
- `create_or_get_approval` 内部提交，不与状态迁移同事务；状态迁移失败时审批行保留，靠幂等重试复用。
- Execution 终态时，该 Execution 下仍 PENDING 且从未进入 interrupt 的审批，统一标记 `REVOKED`，`decision_reason="run_ended_without_interrupt"`（明确取消流程，不是基础设施兜底）。

## 影响的接口与文件

- `coder.py:prevalidate_node`
- `agent/runtime.py`：短事务、审批创建、状态迁移
- `furina_core/config.py`：新增 `approval_timeout_seconds`
- `stream.py`：事件里的审批项带 `approval_id`
- 测试：崩溃点模拟（在步骤之间抛异常）

## 失败模式与测试

| 场景 | 期望 |
|---|---|
| 同一批次重试 | 审批行数不增；返回相同 id |
| 参数变化后重试 | `ApprovalConflict`，不创建、不中断 |
| 状态迁移失败 | 不调用 `interrupt`；任务仍 RUNNING |
| 迁移后进程崩溃 | 对账可恢复或明确收尾，不产生可点击但无中断的审批 |
| 超时配置缺失/非法 | 使用默认值并记录 |

## 兼容性与迁移风险

- 新增配置项，不改表。
- 审批创建从“无调用方”变为节点内调用，需要 runtime 注入；不得把 Session 放进 state。

# ADR-4：拒绝语义与后续图行为

## 背景与现有代码证据

- `handle_review_fn`：任一拒绝 → 回填 `ToolMessage` → `goto="model_node"`，整批不执行（`dependencies.py:283-300`）。
- 全批准 → `goto="tools_node"`（`dependencies.py:331`）。
- interrupt 只有执行 `Command(resume=...)` 后才会被消费。
- T22 当前要求所有审批 `APPROVED`，否则 `NOT_APPROVED`；直接用于拒绝恢复会失败。

## 需要解决的问题

1. 拒绝必须清除 interrupt，否则会话永久挂起。
2. 拒绝不得执行任何被拒绝的工具；当前整批语义下，同批已批准工具也不执行。
3. 拒绝后的 Task/Execution 状态。
4. 拒绝后是否继续由模型生成替代方案。

## 候选方案

| 方案 | 状态 | 图 | 结果 |
|---|---|---|---|
| **A（推荐）** | `WAITING_APPROVAL → RUNNING` | resume 拒绝决定 → 回 `model_node` | 保留 ReAct 语义 |
| B | `→ CANCELLED` | 不 resume | interrupt 永久残留，不可行 |
| C | `→ CANCELLED` | resume 拒绝决定，但改为 `END` | 语义保守，用户需重新发消息 |

## 决策

采用 **A**。

**流程**

1. T20 持久化 `REJECTED`（同批可混合批准/拒绝）。
2. T22 以“拒绝模式”校验当前批次：
   - 无 PENDING
   - 无任何工具已开始（全部 `NOT_STARTED`）
   - 至少一条 `REJECTED`
   - 允许同批存在 `APPROVED + NOT_STARTED`
3. T19 `transition_pair → RUNNING`。
4. 运行时 `Command(resume=决定)`。
5. `handle_review_fn` 走拒绝分支：整批不执行，回 `model_node`。
6. 模型可继续生成替代方案；本轮结束时按 ADR-2 收尾。

**关键约束**

- “拒绝后不恢复” = **不恢复工具执行**，不是“不调用 resume”。
- 同批已批准但未执行的审批保持 `APPROVED + NOT_STARTED`，作为审计记录保留；
  后续批次校验必须按 `approval_id` 范围排除它们，否则会误触发 `ALREADY_EXECUTED`。
- 拒绝不导致 Task/Execution `CANCELLED`；取消是独立流程（`REVOKED` + `CANCELLED`），T23 不实现。

## 影响的接口与文件

- `furina_core/task/resume_service.py`：增加拒绝模式（见 ADR-7）
- `api/agent.py`：决定为 REJECTED 时走拒绝恢复
- `agent/dependencies.py`：保持现有拒绝分支，不改为 `END`
- 测试：拒绝后 interrupt 清空、文件未写、模型收到拒绝消息

## 失败模式与测试

| 场景 | 期望 |
|---|---|
| 全拒绝 | 不执行任何工具；interrupt 清除 |
| 混合决定 | 整批不执行；批准项保持未执行 |
| 拒绝后 resume 失败 | 无工具已开始 → 可挂起重试；否则按 ADR-7 失败分流 |
| 重复提交拒绝 | T20 返回 IDEMPOTENT；不重复恢复 |
| 拒绝后模型再次请求审批 | 新批次独立创建，不被旧拒绝影响 |

## 兼容性与迁移风险

- T22 增加拒绝模式属于已验收服务变更，需单独批准。
- 旧拒绝记录不会被清理；靠批次范围隔离。

# ADR-5：数据库审批与图中断状态核验

## 背景与现有代码证据

- `/agent/resume` 只检查“图中是否有 interrupt”和“决定 id 是否对齐”（`api/agent.py:71-85`）。
- 没有任何数据库与 checkpoint 的交叉校验。
- T22 校验数据库内部一致性，但不读 checkpoint。
- `ValidationFailureCode.CHECKPOINT_MISMATCH` 已存在但无调用方。

## 需要解决的问题

1. 防止“数据库说可恢复、图里没有中断”或反之。
2. 防止决定绑定到别的批次/别的执行。
3. 区分“checkpoint 暂时不可读”和“确认不一致”。
4. 不一致时不得自动修改审批状态。

## 决策

采用 **A：双向预检，失败即拒绝，不自动改状态**。

**预检算法（恢复前）**

1. 由 `approval_id` 加载审批行，确认同一 `execution_id`、同一 `task_id`。
2. 通过 `execution.graph_thread_id` 读取图快照。
3. 取当前 interrupts 中的 `approval_id` 集合。
4. 与请求中的 `approval_id` 集合做**精确相等**比较：
   - 缺失 → 决定不完整
   - 多余 → 伪造/串批
5. 校验 interrupt 载荷中的 `tool_call_id` 与审批行一致。
6. 从图状态 `AIMessage.tool_calls` 重新计算 `args_hash`，与审批行比对。
7. 校验 `Task/Execution` 状态对属于 T22 可恢复集合。

**错误映射**

| 情况 | 错误 | HTTP |
|---|---|---|
| 审批/执行/任务不存在或不属于当前用户 | `not_found` | 404 |
| 决定与当前批次不一致 | `state_mismatch` | 409 |
| 参数快照不一致 | `args_mismatch` | 409 |
| checkpoint 读取异常/暂时不可用 | `checkpoint_unavailable` | 503 |
| 已有相反决定 | `decision_conflict` | 409 |
| 审批已执行或结果未知 | `already_executed` | 409 |

**约束**

- 不自动把审批置 `REVOKED`。
- 不把“读不到 checkpoint”当成“没有 checkpoint”。
- 差异日志同时输出：`execution_id`、`graph_thread_id`、DB 审批集合、图中断集合。

## 影响的接口与文件

- `agent/runtime.py`：预检函数
- `api/agent.py`：错误映射
- `agent/stream.py`：现有 `check_decision_matches` 改为按 `approval_id`
- 测试：真实 SQLite checkpoint + 真实审批行

## 失败模式与测试

- 删除 checkpoint 文件后恢复 → 503，不改变任何审批。
- 手工改审批 `args_hash` → 409。
- DB 有审批、图无中断 → 409 `state_mismatch`。
- 图有中断、DB 无审批 → 409，不自动建行。
- 两个执行相同 `tool_call_id` → 靠 `execution_id + approval_id` 区分。

## 兼容性与迁移风险

- 旧 checkpoint 无 `approval_id`，P1 下本就不兼容。
- 不新增字段。

# ADR-6：工具执行认领、结果记录与不确定状态

## 背景与现有代码证据

- `ToolNode` 直接执行整批 `tool_calls`（`coder.py:70`）。
- `claim_tool_execution` / `finish_tool_execution` 已实现但运行时零调用（`repository.py:332-384`）。
- 认领：仅 `APPROVED + NOT_STARTED → RUNNING`；结束：仅 `RUNNING → SUCCEEDED/FAILED/UNKNOWN`。
- T22 依赖 `tool_execution_status` 全为 `NOT_STARTED` 才允许恢复。

## 需要解决的问题

1. 两个并发恢复不能同时取得同一工具执行权。
2. 执行前崩溃、执行后未落库如何表达。
3. 结果不确定时禁止自动重放。
4. 不扩展为覆盖全部工具的统一执行器。

## 决策

采用 **A：只覆盖高风险审批批次，整批原子认领 + 结束记录**。

**执行流程**

1. `execute_node` 全批准后进入专用节点 `guarded_tools_node`。
2. 读取当前批次的 `approval_id` 列表。
3. 在一个事务内批量认领：
   - 条件：`APPROVED + NOT_STARTED`
   - 全部成功才提交；任一失败 → 回滚，整批不执行
4. 调用原 `ToolNode` 执行。
5. 按 `tool_call_id` 映射 `ToolMessage`：
   - 成功 → `SUCCEEDED`
   - 明确错误 → `FAILED`
   - 无法判定 → `UNKNOWN`
6. 任一结束写入失败：不回滚已执行的外部副作用；保留 `RUNNING`，由人工处理。

**崩溃语义**

| 崩溃点 | 状态 | 恢复策略 |
|---|---|---|
| 认领后、执行前 | `RUNNING` | 不自动重放；人工确认后记 `UNKNOWN` 或 `FAILED` |
| 执行中 | `RUNNING` | 同上 |
| 执行成功、结束未落库 | `RUNNING` | 同上；外部副作用可能已发生 |
| 结束写入 `UNKNOWN` | `UNKNOWN` | 永久禁止自动重放；只能人工处理 |

**约束**

- 认领失败 → 不执行任何工具，返回明确错误。
- 数据库认领只约束数据库执行权，不保证外部副作用“恰好一次”。
- 支持外部幂等键的工具可优先使用其能力，但不能替代认领。
- 安全工具（非高风险）保持现有 `ToolNode` 路径，不在本 ADR 范围。

## 影响的接口与文件

- `furina_core/task/repository.py` 或 service：新增批量认领函数（单事务）
- `agent/dependencies.py` / `coder.py`：新增 `guarded_tools_node`
- `agent/runtime.py`：结果映射与异常处理
- 测试：并发认领、认领后崩溃、UNKNOWN 阻止重放

## 失败模式与测试

| 场景 | 期望 |
|---|---|
| 两个恢复同时认领同一批 | 一个成功，另一个整批失败且不执行 |
| 批内一条已被认领 | 整批回滚，不执行 |
| 工具抛异常 | `FAILED`，ToolMessage 回填 |
| 进程在认领后崩溃 | 状态保持 `RUNNING`，下次恢复拒绝自动执行 |
| `UNKNOWN` 后再次恢复 | 拒绝，提示人工处理 |

## 兼容性与迁移风险

- 不改表；新增批量认领函数。
- `ToolMessage` 是否提供可靠的成功/失败标记需在实现时验证；无法判定时一律 `UNKNOWN`，不猜。
- 统一执行器留到后续任务。

# ADR-7：恢复流程、状态迁移与异常补偿

## 背景与现有代码证据

- T22 只接受“全批准 + 全未执行”，成功后 `transition_pair → RUNNING`（`resume_service.py:150-223`）。
- T19 已有受保护边 `RUNNING → SUSPENDED`，只能经 `suspend_after_resume_failure`（`lifecycle_service.py`）。
- `/agent/resume` 当前不调用 T22，也不处理数据库。
- 图恢复失败没有补偿逻辑。

## 需要解决的问题

1. T22 校验、T19 迁移、图恢复的先后顺序。
2. T22/T19 失败时不得调用图。
3. 图恢复失败后的状态。
4. 工具已开始/结果未知时不得盲目重放。
5. 拒绝恢复如何走 T22。

## 决策

**批准恢复顺序**

1. 双向预检（ADR-5）。
2. T22 校验**当前批次**并成对迁移 `WAITING_APPROVAL/SUSPENDED → RUNNING`。
3. 运行时 `Command(resume=决定)`，图键 = `execution.graph_thread_id`。
4. 成功后继续流式；运行结束时 T19 → `COMPLETED`。

**拒绝恢复顺序**

1. 双向预检。
2. T22 **拒绝模式**：无 PENDING、无已开始、至少一条 REJECTED；成对迁移 → RUNNING。
3. 图 resume，走拒绝分支，不执行工具。
4. 同批准恢复的收尾逻辑。

**失败补偿矩阵**

| 失败点 | 行为 |
|---|---|
| 预检失败 | 不调用 T22；不调用图；返回明确错误 |
| T22 失败 | 不调用图；状态不变（T22 自身保证） |
| T19 迁移失败 | 不调用图；返回冲突 |
| 图恢复失败，且该批审批全部 `NOT_STARTED` | `suspend_after_resume_failure` → `SUSPENDED`；允许后续重试 |
| 图恢复失败，且任一审批已开始/结果未知 | **不**调用 `suspend_after_resume_failure`；Task/Execution → `FAILED`，原因 `graph_resume_failed_after_tool_started`；审批执行状态保留，禁止自动重放 |
| 图恢复调用结果不确定（超时/连接中断） | 先重新读取 checkpoint 与审批状态；能判定未开始 → 可挂起；已开始 → 按上一行 |
| checkpoint 不存在/不可读 | 503 `checkpoint_unavailable`；若确认缺失，Task/Execution → `FAILED`，原因 `checkpoint_missing` |

**并发与重复**

- T22 的 `transition_pair` CAS 保证只有一个请求能从 `WAITING_APPROVAL/SUSPENDED` 抢到 `RUNNING`。
- 抢不到 → `ILLEGAL_STATE` → 409；不调用图。
- T20 的幂等/冲突保证重复决定不会产生二次迁移。
- 顺序重复 resume 已实测不会二次执行工具；并发依赖 T22 CAS + 认领 CAS。

**超时与迟到决定**

- T21 只把 Task/Execution 置 `SUSPENDED`，审批保持 `PENDING`。
- 迟到批准允许恢复（`SUSPENDED` 是 T22 可恢复状态之一）。
- 不因 `deadline_at` 过期而拒绝决定。

**进程崩溃后的对账**

启动时或下一次请求时：
1. 找到非终态 Execution。
2. 读取 checkpoint：
   - 有 interrupt → 正常运行/等待；
   - 无 interrupt 且下一节点为 `review_node` → 尝试触发中断（ADR-3）；
   - 无 checkpoint / 无法推进 → `FAILED` + 明确原因，清理 PENDING 审批（`REVOKED`，原因 `run_ended_without_interrupt`）。
3. 不把“基础设施异常”写成“业务失败”以外的语义：`failure_reason` 必须区分
   `graph_resume_failed_after_tool_started` / `checkpoint_missing` / `graph_crashed_before_start`。

## 影响的接口与文件

- `furina_core/task/resume_service.py`：批次范围 + 拒绝模式（向后兼容）
- `api/agent.py`：恢复编排
- `agent/runtime.py`：图恢复、异常分类、对账
- `agent/stream.py`：恢复流
- 测试：故障注入、并发恢复、checkpoint 删除、迟到批准

## 失败模式与测试

必须覆盖 T23-5 的 16 项，并明确标注类型。
其中“图恢复失败”要分别测“未开始”和“已开始”两条分支。

## 兼容性与迁移风险

- T22 是已验收服务，改动必须保持旧签名行为不变（新增可选参数）。
- 补偿逻辑会把部分基础设施故障落在 `FAILED`；通过 `failure_reason` 区分，不伪装成业务失败。
- 不新增状态枚举。

# ADR-8：运行时适配层与模块职责边界

## 背景与现有代码证据

- 目前 `stream.py` 同时负责 SSE、图调用、决定匹配。
- `api/agent.py` 只做归属校验和图状态检查。
- 图节点直接调用工具，无数据库访问。
- core 已明确禁止依赖 LangGraph（`smoke_public_api` 有 banned 检查）。

## 需要解决的问题

1. 业务服务不得依赖 LangGraph。
2. 图节点需要数据库能力，但不能把 Session 放进 state。
3. API 层不得重复实现审批状态机。
4. 图定位、恢复异常处理应有唯一入口。

## 决策

采用如下分层：

| 层 | 职责 | 禁止 |
|---|---|---|
| `furina_core.task.*` | 业务规则、校验、状态迁移、CAS | 导入 LangGraph；直接处理 HTTP |
| `apps/desktop/.../agent/runtime.py`（新增） | session factory、活动 Execution、图键、interrupt 检查、resume 调用、异常分类、对账 | 实现审批状态机（必须调用 T18–T22） |
| `apps/desktop/.../agent/nodes/*` | 构图、工具调用、审批载荷 | 持有长期 ORM Session；直接写审批状态 |
| `apps/desktop/.../api/*` | 认证、归属、请求编排、HTTP 错误映射 | 直接改审批/任务状态；直接操作 checkpoint |
| `furina_core.task.repository` | 数据访问与事务边界 | 业务判断 |

**运行时适配对象**

- 持有 `async_sessionmaker`，由 lifespan 注入。
- 对节点暴露短事务方法：`create_approvals(...)`、`mark_waiting(...)`、`claim_batch(...)`、`finish_batch(...)`。
- 对 API 暴露：`find_active_execution(thread_id)`、`locate_by_approval(approval_id)`、`preflight(...)`、`resume_graph(...)`。
- 不进入 `CoderState` / `SupervisorState`。

**新增/调整接口**

| 接口 | 说明 |
|---|---|
| `POST /agent/decisions` | 批量决定；请求只含 `approval_id/action/reason`，`task_id/execution_id` 由数据库反查 |
| `POST /agent/resume` | 请求含 `chat_thread_id` + 决定；内部按 `approval_id` 定位执行 |
| `GET /agent/approvals?thread_id=` | 可选，用于 UI 恢复；不属于 T23 必需 |
| `approval_timeout_seconds` | 新配置，默认 3600 |

**归属校验**

- 由 `approval_id → task_id → thread_id → user` 反查，不信任客户端传入的 `task_id/execution_id`。
- 所有资源不存在与越权统一 404，避免泄漏。

## 影响的接口与文件

- 新增：`agent/runtime.py`
- 修改：`api/agent.py`、`api/contracts.py`、`agent/stream.py`、`agent/nodes/coder.py`、`agent/dependencies.py`
- 新增测试：真实集成脚本

## 失败模式与测试

| 场景 | 期望 |
|---|---|
| core 导入 LangGraph | `smoke_public_api` 失败 |
| 节点里把 Session 放进 state | 代码审查阻断；序列化测试 |
| API 直接改审批状态 | 代码审查阻断 |
| 越权访问 approval | 404 |
| 决定接口重复提交 | T20 幂等结果 |

## 兼容性与迁移风险

- 新增模块，不破坏现有导入路径。
- `stream.py` 的公开函数签名可能调整；测试需同步。
- 不引入新依赖。
