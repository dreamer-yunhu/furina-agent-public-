# T23-0 判断上下文

> 用途：供你决定 T23 的 6 个架构选择。
> 依据：`docs/audit/2026-10-24-T23-0-审计报告.md` + 本轮补充核对。

## 〇、一句话结论

T23 不是“把几个服务接上”那么简单：现有三处设计假设互相冲突，
必须先定 **Execution 的粒度** 和 **拒绝语义**，否则接得越多，错得越深。

---

## 一、先看三个硬约束（它们决定了后面的选项）

### H1｜`graph_thread_id` 的语义与运行时相反

- `models.py:10` 写明：`graph_thread_id` 是**唯一**传给 `configurable.thread_id` 的值，
  业务 `thread_id` 只做分组，“绝不直接当 checkpoint key”。
- `models.py:112` 又规定 `graph_thread_id` **UNIQUE**：一个 Execution 对应一个图现场。
- 但运行时 `stream.py:_config()` 实际传的是业务 `chat_thread_id`；
  `graph_thread_id` 从未被使用（全仓库只有测试引用）。

**后果**：只要一个会话里有第二次 Execution，`graph_thread_id` 就不能再等于 chat id（UNIQUE 冲突）；
而如果它等于 execution_id，数据库记录的“图现场键”就与实际 checkpoint 键不一致。

### H2｜T22 假设“一个 Execution 只有一批审批”

`resume_service.py:150-177` 会把该 Execution 下**所有**审批一起校验：

- 任一审批仍 `PENDING` → `PENDING_APPROVALS`
- 任一审批为 `REJECTED/REVOKED` → `NOT_APPROVED`
- 任一审批 `tool_execution_status != NOT_STARTED` → `ALREADY_EXECUTED`

但 ReAct 循环在同一轮里可以产生**多批**高风险调用（批准→执行→模型再调用→再审批）：

- 第二批恢复时，第一批已是 `APPROVED + SUCCEEDED` → 命中 `ALREADY_EXECUTED`；
- 若第一批被拒绝，之后永远命中 `NOT_APPROVED`。

**后果**：按现状接线，一次用户请求最多只能有**一批**审批；
除非扩大 Execution 粒度，或让 T22 按“当前批次”校验。

### H3｜“拒绝后不恢复”在当前图里会把会话永久卡死

- 拒绝只有在 `Command(resume=拒绝决定)` 之后才会走 `handle_review_fn` 的拒绝分支
  （`dependencies.py:283-300`），把中断清掉并回到 `model_node`。
- 如果拒绝后**完全不调用 resume**：checkpoint 里的 interrupt 永远在；
  `/agent` 会被 `thread_suspended` 挡住（`stream.py:210-219`），`/agent/resume` 也没有入口清除它。

**后果**：指南里的“用户拒绝后不恢复”，必须定义成
**“不恢复工具执行”**，而不是“不调用 resume 接口”。

## 二、六个决策

### Q1｜审批与工具调用用什么键绑定？

| 选项 | 做法 | 优点 | 代价/风险 |
|---|---|---|---|
| **A（推荐）** | `(execution_id, tool_call_id)` 作为稳定键；中断载荷里加 `approval_id`；`args_hash` 复核参数 | 不改 Schema；`idempotency_key` 已含 execution_id；批次内 `tool_call_id` 唯一 | 跨批次同名工具只能靠批次范围区分；`tool_call_id` 由模型/供应商生成，理论上不保证全局唯一 |
| B | 新增 `checkpoint_id` / `tool_call_index` 列 | 绑定最强 | Schema + 迁移；当前无法从 checkpoint 稳定取 index |
| C | 只按工具名或 args_hash 匹配 | 无 | **禁止**：同参数多次调用会串批 |

**推荐 A**。理由：T18 的 `idempotency_key` 已经是
`execution_id + tool_call_id + args_hash` 的派生值，链路里最稳的键已经在库中。

**若采纳 A**：图内契约（`ReviewRequest.requests[]`）增加 `approval_id` 字段；
不改数据库表。

---

### Q2｜Execution 是“一次请求”还是“一批审批”？

这是本轮最重要的选择，直接决定 T22 要不要改。

| 方案 | Execution 粒度 | 图现场键 | T22 | 多批审批 | Schema |
|---|---|---|---|---|---|
| **P1（推荐）** | 一次 `/agent` 运行 | `execution.graph_thread_id`（本轮切换） | 增加可选参数 `approval_ids`，只校验当前批次 | 支持 | 不改 |
| P2（最小） | 一次运行 | 仍用 `chat_thread_id` | 不改，校验整个 Execution | **不支持**（第二批必被 `ALREADY_EXECUTED` 挡住） | 不改 |
| P3（最干净但最贵） | 一批审批 | 新增 `checkpoint_thread_id` 列，与 `graph_thread_id` 分离 | 不改 | 支持 | 改表 + 迁移 |

**推荐 P1**，具体含义：

1. 每次 `POST /agent` 创建 Task + Execution，`graph_thread_id = str(execution.id)`；
2. LangGraph 的 `configurable.thread_id` 改为 `execution.graph_thread_id`——回到 `models.py` 的设计原意；
3. `/agent` 的“线程是否挂起”改为查数据库里该 thread 的活动 Execution，而不是猜 checkpoint 键；
4. `/resume` 从审批/Execution 反查图现场，不再只信客户端传来的 `chat_thread_id`；
5. T22 增加**向后兼容**的可选参数（审批 id 或 tool_call_id 列表），只校验当前中断批次。

**代价（必须提前知道）**：

- 改动面包含 `stream.py`、`api/agent.py`、`coder.py` 的拒绝分支、`resume_service.py`；
- 历史上以 `chat_thread_id` 为键的 checkpoint 将不再可达（仅开发数据，建议不迁移，明确记录）；
- 多轮上下文本来就被 `prepare_node` 每轮清空，因此功能上无退化；
- T22 属于已验收服务，改它需要你单独批准（本轮只讨论，不实施）。

**若你坚持最小改动选 P2**：功能上要接受“一次请求只允许一批高风险审批”，
并且 `graph_thread_id` 字段继续名不副实。我不建议把它当成长期方案。

---

### Q3｜审批记录在哪一步创建？

| 选项 | 位置 | 顺序 | 崩溃窗口 |
|---|---|---|---|
| **A（推荐）** | `prevalidate_node` 构造完审批载荷后 | **先写 DB（提交）→ 再 `interrupt()`** | 有审批行、无中断（可对账） |
| B | `stream.py` 收到 `approval_required` 事件后 | checkpoint 已保存 → 再写 DB | 有中断、无审批行（用户已经看到审批 UI，最危险） |
| C | `/agent` 请求开始时预建 | 不知道 tool_calls | 不可行 |

**推荐 A**。理由：用户看到审批 UI 时，数据库里必须已经有可决策的行；
反过来“有行无中断”可以被检测并拒绝恢复，而“有中断无行”会让用户对着一个无法落库的审批操作。

**实现约束**：图节点是 desktop 层，可以调用 `furina_core.task.service`；
但不允许把 ORM Session 放进 state。建议用一个轻量的 runtime 适配对象持有
`async_sessionmaker`，在 lifespan 注入，节点内短事务使用。core 仍不依赖 LangGraph。

**幂等**：直接复用 T18 `create_or_get_approval`，重试 `prevalidate_node` 不会重复建行。

---

### Q4｜用户拒绝时，Task/Execution 怎么走？

| 选项 | 数据库 | 图 | 后果 |
|---|---|---|---|
| **A（推荐）** | T20 落 `REJECTED`；T19 `WAITING_APPROVAL → RUNNING` | 用拒绝决定 resume，清中断，回 `model_node`，**不执行任何工具** | 保持现有 ReAct 语义；模型可提出替代方案；需要 Q2 的批次校验，否则旧拒绝会挡住以后批次 |
| B | `WAITING_APPROVAL → CANCELLED` | 不 resume | interrupt 永久残留，该会话无法再发消息（H3）——不可行，除非另做“丢弃 checkpoint” |
| C | `WAITING_APPROVAL → CANCELLED` | resume 拒绝决定，但拒绝分支改为 `END` | 语义最保守，但用户必须重新发消息；需要改 `handle_review_fn` |

**推荐 A**（配合 P1）。
注意：当前 `handle_review_fn` 是**整批**语义——只要有一条拒绝，整批都不执行；
DB 里同批的 `APPROVED` 行会保持 `NOT_STARTED`。P1 的批次校验会把它们排除在后续恢复之外，
不会误触发 `ALREADY_EXECUTED`。

**若你选 P2**：拒绝后该 Execution 内永远存在 `REJECTED`，之后任何恢复都会 `NOT_APPROVED`；
等于“一次拒绝 = 该请求报废”。这也是我不推荐 P2 的原因之一。

---

### Q5｜孤儿审批与“有行无中断”怎么处理？

| 选项 | 做法 | 风险 |
|---|---|---|
| **A（推荐）** | 恢复前做双向预检：DB 批次 ↔ 图 interrupts；不一致直接 409 `state_mismatch`，**不改任何状态**，日志里列出两边差异 | 需要人工/后续对账；但绝不误伤 |
| B | 检测到无中断就把审批置 `REVOKED` | 误判成本高（checkpoint 暂时不可读也会被当成孤儿） |
| C | 新增 `INVALIDATED` 状态 | 枚举/CHECK 变更，本轮不必要 |

**推荐 A**。现有 `ApprovalStatus.REVOKED` 已存在（`enums.py:83`），
留给“用户/系统明确取消”流程，不拿它兜底基础设施异常。

---

### Q6｜工具执行要不要“认领/结束”？

| 选项 | 做法 | 结果 |
|---|---|---|
| **A（推荐）** | 只包高风险批次：执行前逐条 `claim_tool_execution`，执行后 `finish_tool_execution(SUCCEEDED/FAILED/UNKNOWN)` | `ALREADY_EXECUTED` 真正生效；并发恢复有 DB 护栏 |
| B | 做完整统一执行器（所有工具） | 超出 T23，范围膨胀 |
| C | 不做 | `tool_execution_status` 永远 `NOT_STARTED`；T22 的重复执行保护形同虚设 |

**推荐 A**。任一审批认领失败（已被别人认领）→ **整批不执行**，
返回明确错误，不重放。执行结果不确定时记 `UNKNOWN`，不记 `FAILED`。

## 三、如果全部按建议，T23 的实际影响面

| 文件 | 变化 |
|---|---|
| `agent/nodes/coder.py` | `prevalidate_node` 创建审批行；`review_node` 载荷带 `approval_id`；拒绝分支按 Q4 处理 |
| `agent/dependencies.py` | 高风险批次执行前认领、执行后结束 |
| `agent/stream.py` | checkpoint key 改用 `execution.graph_thread_id`；resume 改为从 DB 定位 Execution |
| `api/agent.py` | 创建 Task/Execution；新增决定接口；resume 走 T22；错误码映射 |
| `api/contracts.py` | 新增决定请求模型 |
| `furina_core/task/resume_service.py` | 可选参数：只校验当前审批批次（**需单独批准**） |

| 测试 | 新增真实集成：图中断 + DB 审批 + 决定 + 恢复 + 故障注入 |

**不改**：数据库表结构、迁移、依赖、T19 状态机、审批枚举。

## 六、我不建议的选项（红线）

- 只按工具名 / args_hash 匹配审批（Q1-C）
- 让数据库状态和 checkpoint 键继续“各说各话”，却宣称已绑定（P2 长期化）
- 拒绝后完全不 resume，把会话永久留在 interrupt（Q4-B）
- 无中断时自动把审批改成 `REVOKED`（Q5-B）
- 不认领就执行高风险工具（Q6-C）
