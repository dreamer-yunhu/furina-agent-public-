## 二、逐项分析

### Q1 · 职责范围

**代码事实**
- `furina_core` 依赖里**没有** langgraph（`packages/core/pyproject.toml`），core 不应依赖图。
- `transition_pair` 支持 `WAITING_APPROVAL/SUSPENDED → RUNNING`，且同事务、CAS（`lifecycle_service.py:99-160`）。

**方案**
- A 仅校验：返回结果，调用方迁移。
- **B 校验 + 迁移**：DB 内原子，图留给桌面层。
- C 校验 + 迁移 + 调图：破坏分层。

**取舍**
- A：职责最纯，但“校验通过→迁移”的窗口交给每个调用方，容易漏。
- B：一个服务内完成校验与迁移，调用方只需处理结果；图仍是外部副作用。
- C：core 引入 LangGraph，测试与依赖都变重。

**推荐 B**。理由：T19 已经提供成对 CAS；T20/T21 都用“服务返回结果”的风格。

**事务/并发/失败**：校验只读；迁移用 `transition_pair` 自带事务；任一侧失败整体回滚；并发由 CAS 保证最多一次 APPLIED。

**影响**：T23 负责“迁移成功后调图”；T24 处理校验失败后的重委派。

**未解决**：图恢复失败的补偿（见 Q11）。

---

### Q2 · 允许从哪些状态恢复

**事实**：迁移表允许 `WAITING_APPROVAL→RUNNING` 与 `SUSPENDED→RUNNING`（`lifecycle.py` 两张表）。

**方案**：A 两者都允许 / B 只 SUSPENDED / C 只 WAITING。

**取舍**：
- 正常批准：任务还在 `WAITING_APPROVAL`（T20 不改状态）。
- 迟到批准：任务可能已被 T21 挂起（`SUSPENDED`）。
- B/C 都会让其中一条正常路径无法恢复。

**推荐 A**。

**事务/并发**：两状态共用同一 CAS 调用；`from_status` 由服务根据当前状态选择，**不能相信调用方传入**。

**影响**：T21 挂起后仍可恢复；T23 无需分支。

---

### Q3 · 同一 Execution 下存在未决审批

**事实**：一个 Execution 允许 N 条审批（`approval.execution_id` 有索引无唯一约束，`models.py:152-157`）；`list_approvals(execution_id=...)` 可查（`repository.py:238-260`）。

**方案**：A 有 PENDING 就拒绝 / B 只恢复已批准的那条。

**取舍**：B 会让执行带着未决操作继续跑，属于越权；A 与 TODO 的“批内无 pending”一致。

**推荐 A**。批次定义 = **同一 `execution_id` 下的全部审批行**。

**事务/并发**：C3 是只读快照；在迁移前再读一次以缩小窗口，但不能消除“校验后新增审批”的窗口（新审批只会在新 Execution 中产生，风险低）。

**影响**：T23 必须按 execution 建批。

---

### Q4 · 工具身份与参数快照

**事实**
- DB 有 `tool_name`、`args_json`、`args_hash`（`models.py:159-162`）。
- 审批行与 checkpoint 的 tool_call **没有绑定字段**；`get_pending_tool_call_ids` 只读图状态（`stream.py:69-86`）。
- T18 的 `canonical_args_json` / `compute_args_hash` 可复用（`service.py:49-60`）。

**方案**
- **A 只做 DB 内部一致性**：`tool_name` 非空；`args_hash` 为 64 位 hex；`args_json` 可解析；重算哈希与 `args_hash` 一致。
- B 解析 checkpoint 比对：当前无可靠绑定，无法实现。
- C 不做：违背“快照校验”要求。

**推荐 A**，并明确标注：**图侧绑定校验未实现，属 T23**。

**失败语义**：DB 不一致 → `ARGS_MISMATCH`（复用 `ValidationFailureCode`）。

**影响**：T23 需要把审批行与 tool_call 绑定（增加字段或约定），才能补全 C7。

---

### Q5 · `old_hash` 不匹配

**事实**：`old_hash` 在 desktop 的 `build_write_review` 生成（`dependencies.py:110-160`），在 `verify_preview_unchanged` 执行前比对（`:222-240`）；**DB 的 `old_hash` 运行时无人写入**。

**方案**：A 拒绝恢复 / B 自动重批 / C 忽略。

**推荐 A**。拒绝后：状态不变（Q6），由 T18/T23 重新发起审批；**T22 不自动创建审批、不建新 Task**。

**失败语义**：`OLD_HASH_MISMATCH`。

**影响**：T23 创建审批时必须把 `target_path`/`old_hash` 写入 DB，否则 C8 无意义。

---

### Q6 · 校验失败后的状态

**方案**：A 不改状态 / B Execution→`VALIDATION_FAILED` / C Task→`FAILED`。

**取舍**：B/C 把“校验失败”与“执行失败”混为一谈；且 `VALIDATION_FAILED` 是终态，重试要新建 Execution（T24 未实现）。

**推荐 A**。T22 只返回 `ResumeResult`，状态迁移由调用方/T24 决定。

**影响**：`AgentExecution.validation_failure_reason` 仍无人写（Q10=A）。

---

### Q7 · 结果表达

**事实**：T19 用 `TransitionOutcome`，T20 用 `DecisionOutcome + DecisionResult`，`ValidationFailureCode` 已定义未使用。

**方案**：A `ResumeOutcome + ResumeResult` / B 领域异常 / C bool。

**推荐 A**，风格与 T19/T20 一致；`ResumeResult.failure_code` 复用 `ValidationFailureCode`。

**枚举**：`RESUMED / NOT_FOUND / SCOPE_MISMATCH / NOT_APPROVED / PENDING_APPROVALS / ILLEGAL_STATE / ALREADY_EXECUTED / OLD_HASH_MISMATCH / ARGS_MISMATCH`。

---

### Q8 · 并发恢复

**事实**：`transition_pair` 是 CAS + 同事务；两独立 Session 并发时只有一个能 `APPLIED`（T19 测试已验证同类行为）。

**方案**：A DB CAS / B 先查再迁 / C 加锁。

**推荐 A**。B 有窗口；C 过度设计。

**约定**：只有 `(APPLIED, APPLIED)` 才返回 `RESUMED` 并允许调用方恢复图。

**未验证**：跨进程、PostgreSQL。

---

### Q9 · 是否接运行时

**事实**：运行时无审批行；`submit_decision` 零调用方；`/agent/resume` 不碰 DB。

**方案**：A 只做服务 / B 顺带把路由接上 DB。

**推荐 A**。B 接上也无数据可校验，还会与 T23 的“interrupt → 审批行”绑定重复。

**实际影响**：T22 的验证只能基于种子数据；`/agent/resume` 行为**本轮不变**。

---

### Q10 · 校验失败的持久化

**方案**：A 返回 `failure_code` / B 写 `validation_failure_reason` / C 新增审计表。

**推荐 A**。B 会引入“谁写、何时清”的生命周期问题；C 需要 Schema 变更。

**影响**：失败原因只在本次调用可见；T24 若需要审计，再单独设计。

### Q11（补充）· DB 迁移成功后图恢复失败怎么办

**决策：B（已确认）** —— 为 T19 增加**受约束的** `RUNNING → SUSPENDED`，使数据库迁移成功但图恢复失败时具备安全恢复路径。

**事实**：DB 与 LangGraph checkpoint 不是同一事务；T19 迁移表没有 `RUNNING→SUSPENDED`。

**为什么选 B 而不是 A**
- A（置 `FAILED`）会把一次基础设施故障变成任务终态，必须由 T24 重委派；
- B 保留“可重试的挂起”，但必须加约束，否则会引入 `RUNNING↔SUSPENDED` 的自由振荡。

**约束（设计要点，详细方案见 T19 变更 ADR）**
1. 只允许 `RUNNING → SUSPENDED`；终态不可出，`SUSPENDED` 不新增状态。
2. 必须走**专用入口**（暂名 `suspend_after_resume_failure`），不接受通用调用方直接迁。
3. 入口前置条件：Task 与 Execution 都为 `RUNNING`；该 Execution 下**所有审批的 `tool_execution_status == NOT_STARTED`**。任一已开始/结果未知 → 拒绝（不可安全重试，应走 FAILED）。
4. 不自动重试、不自动循环；每次由 T23 显式触发。
5. `SUSPENDED` 因此有两种来源：审批超时（T21）与恢复失败（T23）。二者对 T22 的恢复校验是同一套规则。
6. 挂起原因是否持久化：现有模型无字段；T19 ADR 需在“不新增 Schema（仅返回值/日志）”与“新增列（需 Alembic）”之间定夺。

**事务/并发**：迁移仍走 `transition_pair` 的 CAS + 同事务；同一任务第二次 `RUNNING→SUSPENDED` 会 `CONFLICT`，不会重复生效。

**影响**：T21 不受影响（它只走 `WAITING_APPROVAL→SUSPENDED`）；T22 的校验无需区分来源；T23 实现“图恢复失败 → 调用专用入口”。

**前置**：必须先完成并确认 `2026-10-24-T19-1-ADR-新增RUNNING到SUSPENDED迁移.md`，不得直接改已批准的迁移表。

**仍未解决**：是否限制重试次数；挂起原因是否需要可查询。

### Q12（补充）· `old_hash` 为 None 的语义

**事实**：新文件的 `WritePreview.old_hash` 为 None（`dependencies.py:135`）；DB 允许 NULL。

**方案**
- **A（推荐）**：`target_path` 为 None → 跳过 C8（非写类操作）；`target_path` 有值且 `old_hash` 为 None → 目标文件不存在则放行（新建），存在则 `OLD_HASH_MISMATCH`（审批期间被创建）。
- B 一律跳过：等于放弃 C8。
- C 一律拒绝：新文件永远无法恢复。

**推荐 A**。

**实现依赖**：core 有 `PathJail`（`sandbox.py:107`）可做路径边界；文件哈希在 core 需新增一个小 helper（desktop 的 `sha256_text` 不能直接依赖）。建议 `validate_and_resume(..., workspace_root: str | Path | None = None)`，None 时取 `settings.sandbox_root`。

**需确认**：是否允许在该签名上增加可选参数（候选签名只写了 `now`）。

## 三、事务、并发与失败语义汇总

| 阶段 | 事务 | 失败处理 |
|---|---|---|
| 校验（读 approval/task/execution/file） | 只读 | 返回 outcome，不写 |
| 成对迁移 | `transition_pair` 内部事务 | 任一侧失败整体回滚 |
| 图恢复 | 不在 T22 | 见 Q11 |

- 不使用“先查后写”作为并发保证；写只走 CAS。
- 文件校验与真正执行之间仍有 TOCTOU 窗口（T14 已窄化），T22 不宣称消除。
- 数据库故障以异常抛出，不映射成 outcome。
