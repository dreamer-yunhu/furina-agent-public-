# ADR：T21 审批超时扫描与挂起

> 状态：**已确认并实施**（2026-10-24；实现与偏差见 §11 与 PROGRESS）
> 日期：2026-10-24 ｜ 前置：T21-0 审计 + 用户批准 Q1–Q11 全部推荐项
> 范围：扫描能力与启停；不含 T20/T22/T23

---

## 1. 背景与问题

- `deadline_at` 已存在且有索引，但**无人读取**（T21-0 F5）。
- 没有扫描器、调度器、后台任务（F6）。
- 审批等待一旦开始，任务会永远停在 `WAITING_APPROVAL`。
- T19 已支持 `WAITING_APPROVAL → SUSPENDED` 的成对迁移（F9–F12），T21 只需编排。

**目标**：到期后把符合条件的 Task/Execution 成对置为 `SUSPENDED`，释放“活动调度”语义，**不改审批状态、不自动批准/拒绝/恢复**。

---

## 2. 决策驱动因素

1. 不引入新调度基础设施（桌面单进程、已有单实例锁）。
2. 不绕过 T19 生命周期服务。
3. 不新增 Schema/依赖。
4. 必须可单测：时间可注入，不依赖 sleep。
5. 必须容错：单条失败不终止整轮；循环异常不静默退出。
6. 必须诚实：没有调度器就不假装释放资源。

---

## 3. 已确认的决定（Q1–Q11）

| # | 决定 |
|---|---|
| Q1 | **lifespan 启动 `asyncio` 后台循环**；核心逻辑独立为 `scan_once()` |
| Q2 | **六条全满足**才挂起；不一致/关联错误一律 skip + 计数 |
| Q3 | **依赖 CAS**（`transition_pair`）；不加标记字段，不用进程内 Set 去重 |
| Q4 | 扫描事务内**重读 approval 仍为 PENDING**；接受 `SUSPENDED + APPROVED` 为合法中间态 |
| Q5 | **复用 `transition_pair`**；每条候选独立 Session + 事务 |
| Q6 | **UTC + `as_utc`**；`now >= deadline_at`；测试注入 `now` |
| Q7 | **最早一条到期即挂起整个 Task/Execution**；同轮按 execution 去重 |
| Q8 | 间隔 **30s**、批量 **50**、配置 **0 = 关闭** |
| Q9 | 提供 `on_suspended(task_id, execution_id)` 钩子，**默认只记日志** |
| Q10 | **只做扫描能力**，不接 interrupt → approval 的运行时链路 |
| Q11 | 不一致候选 **skip + 计数**，不修复 |

---

## 4. 备选方案与放弃理由

| 议题 | 备选 | 放弃原因 |
|---|---|---|
| 扫描方式 | 请求时惰性扫描 / 外部 cron | 超时语义依赖访问；桌面不应依赖系统计划任务 |
| 并发控制 | 对 approval 行 `FOR UPDATE` | 把 T20/T21 锁语义绑死；SQLite 上无实际效果 |
| 去重 | 新增 `scanned_at` 字段 | 改 Schema；标记本身又要 CAS |
| 聚合 | 全部到期才挂起 | 一条长期未决的审批会让执行永远不挂起 |
| 资源释放 | 现造调度器/队列 | 为一个钩子引入大基础设施 |
| 时间来源 | 数据库时间 | 跨库语义不一致，测试难控 |

## 5. 接口契约（T21-2 实现）

### 5.1 查询（新增只读函数）

```python
# task/repository.py
async def list_due_pending_approvals(
    session: AsyncSession, *, now: datetime, limit: int
) -> Sequence[ApprovalRequest]:
    # JOIN agent_execution / agent_task
    # WHERE approval_status='PENDING' AND deadline_at <= :now
    #   AND NOT (task.status='SUSPENDED' AND execution.status='SUSPENDED')
    # ORDER BY deadline_at ASC, id ASC LIMIT :limit
```

- `now` 必须已经是 `as_utc()` 后的值（调用方负责）。
- **已实测**：SQLite 下 aware `now` 直接比较正确（UTC）；PG 未验证。
- **t21-2 实施时发现的必要修正**：超时不改 `approval_status`，已挂起的审批会永远满足
  `PENDING + 到期`。若不排除“Task 与 Execution 都已 SUSPENDED”的对，
  有 `limit` 的扫描会被它们占满，后面的候选永远轮不到（饥饿）。
  因此查询在 SQL 层排除这一种正常完成态；其它不一致状态仍返回给 Service 计数。

### 5.2 扫描核心

```python
@dataclass(frozen=True)
class ScanReport:
    candidates: int                 # 本轮取到的待审候选数
    suspended: int                  # 成功挂起数
    not_due: int                    # 重读后发现已不满足时间条件
    already_decided: int            # approval 已非 PENDING
    task_terminal: int              # Task 已终态
    task_not_waiting: int           # Task 不是 WAITING_APPROVAL
    execution_not_waiting: int      # Execution 不是 WAITING_APPROVAL
    association_mismatch: int       # 关联错误或关联记录缺失
    pair_conflict: int              # 成对迁移未 APPLIED（含并发被抢）
    deduped: int                    # 同一 execution 的重复候选
    callback_errors: int            # on_suspended 抛出的异常数
    errors: int                     # 单条处理抛出的异常数

async def scan_once(
    session_factory, *, now: datetime | None = None, limit: int = 50
) -> ScanReport: ...
```

### 5.3 单条候选流程

```
1. 独立 session + session.begin()
2. 重读 approval；不存在 → mismatch/errors（按 Q11 计数）
3. approval_status != PENDING → already_decided
4. as_utc(deadline_at) > now → not_due
5. 读 execution；不存在 → mismatch
6. execution.task_id != approval.task_id → mismatch
7. 读 task；不存在 → mismatch；status 终态 → terminal
8. task.status != WAITING_APPROVAL → wrong_task_status
9. execution.status != WAITING_APPROVAL → wrong_execution_status
10. transition_pair(...WAITING_APPROVAL → SUSPENDED...)
11. 仅 (APPLIED, APPLIED) → 提交后调用 on_suspended；否则 pair_conflict
```

> 重读与迁移分属两个 session：先读后判，再交给 `transition_pair`（内部自带事务）。
> 两者之间的窗口即为 §6 声明的剩余竞态窗口。

> 第 2 步的“重读”只缩小窗口，**不消除**并发窗口（见 §7）。

### 5.4 回调

```python
async def on_suspended(task_id: uuid.UUID, execution_id: uuid.UUID) -> None:
    """默认实现只记日志。将来有调度器时在这里释放资源。"""
```

- 只在**事务提交成功后**调用。
- 回调异常：记录日志 + 计数，**不回滚已提交状态**。
- 重复扫描不会重复调用（只有 APPLIED 才触发）。

### 5.5 后台循环

```python
async def run_timeout_scanner(app, *, session_factory, interval_seconds):
    if interval_seconds <= 0:
        return
    while True:
        try:
            await scan_once(session_factory, limit=settings.approval_scan_batch_size)
        except asyncio.CancelledError:
            raise
        except Exception:
            logger.exception("超时扫描失败，将在下轮重试")
        await asyncio.sleep(interval_seconds)
```

- lifespan：图组装成功后 `asyncio.create_task(...)`，句柄存 `app.state.timeout_scanner_task`。
- 关闭：`task.cancel()` → `await` 并吞掉 `CancelledError` → 再关闭存储。
- 首轮延迟一个间隔，避免与启动争抢。
- `interval=0` 时不创建任务。

### 5.6 配置

| 名称 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `approval_scan_interval_seconds` | int | 30 | `0` = 关闭后台扫描 |
| `approval_scan_batch_size` | int | 50 | 每轮候选上限 |

按 `config.py` 现有风格：`int(os.getenv(..., "30"))`。

**非法值策略（已采纳）**：
- `interval < 0` → clamp 到 `0`，**打 ERROR 日志**（不静默）
- `batch <= 0` → 回退到 `50`，**打 ERROR 日志**
- 启动时打印生效值，便于排查

**运行日志与状态**：
- 每轮：有挂起/跳过/错误 → `INFO`；全空 → `DEBUG`（避免 30s 一轮的噪声）
- `/healthz` 新增 `timeout_scanner: "running" | "disabled"`

## 6. 事务与并发语义

| 项 | 约定 |
|---|---|
| 查询 | 独立短会话，只读 |
| 每条候选 | **独立 Session**，`transition_pair` 内部 `session.begin()` |
| 成对失败 | `_PairAborted` → 整体回滚 → `(CONFLICT, CONFLICT)` |
| 回调 | 提交后执行；失败不回滚、不重试（下轮扫描自然幂等） |
| 决定并发 | 决定 CAS 在 approval 行；扫描 CAS 在 task/execution 行；**两者可同时成功** |
| 合法中间态 | `SUSPENDED + APPROVED` 允许存在，交 T22 |
| 重复扫描 | 第二次 `transition_pair` 返回 CONFLICT，不调用回调 |
| 多实例 | 桌面单实例锁保证一个扫描器；多进程未支持 |

**明确声明**：事务内重读 approval **不能彻底消除**“读后决定提交”的窗口；在 PG 的 READ COMMITTED 下仍可能出现 `SUSPENDED + APPROVED`，这是被接受的合法状态。

## 9. 接受的代价与风险

1. **端到端不生效**：没有运行时审批数据，扫描器只对种子数据有效。
2. **竞态窗口残留**：PG 下仍可能 `SUSPENDED + APPROVED`；这是设计接受项，不是缺陷。
3. **回调不是资源释放**：默认只记日志；不得在文档中描述为“已释放资源”。
4. **后台任务是新基础设施**：这是项目第一个常驻协程，需覆盖启停与异常退出。
5. **配置新增**：两个环境变量；不会改 Schema。
6. **SQLite 实测、PG 未验证**：时间比较与并发语义需在 PG 上复验。
