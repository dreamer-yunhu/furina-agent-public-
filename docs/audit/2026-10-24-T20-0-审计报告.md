**关键事实**：这条链路**没有任何数据库写入**。

- 全仓 `decide_approval` 的调用方**只有测试**（`apps/desktop/tests/smoke_task_models.py:210`、`smoke_approval_service.py:242`），业务代码 0 调用。

## 三、相关数据模型与状态枚举

### 3.1 `ApprovalRequest`（`task/models.py:125-198`）

与决定相关的字段：

| 字段 | 类型 | 现有语义 |
|---|---|---|
| `approval_status` | `PENDING/APPROVED/REJECTED/REVOKED` | 决定**内联**在这一行 |
| `decided_by` | `str \| None` | 谁决定的 |
| `decided_at` | `datetime \| None` | **调用方传入**，不是服务端生成 |
| `decision_reason` | `Text \| None` | 拒绝理由 |
| `deadline_at` | `datetime` | 无任何代码读取比较（T21 未实现） |
| `task_id` / `execution_id` | UUID | 审批与任务/执行的关联 |

**没有独立的“决策记录”表**。因此“决策记录写入与审批状态更新同一事务”在当前模型下**退化为同一行的单条原子 UPDATE**。

### 3.2 枚举

- `ApprovalStatus`：`PENDING / APPROVED / REJECTED / REVOKED`（`enums.py:73-87`）
- 终态由 `ApprovalStatus.terminal()` 定义（`enums.py:85-87`），但**无人调用**
- 没有 `EXPIRED`；超时不改审批状态

### 3.3 数据库约束（SQLite DDL 实测）

- `approval_status` / `tool_execution_status` 有 CHECK
- `idempotency_key` UNIQUE
- **没有** decision 表、没有“同一请求多个决定”的唯一约束（当前模型不需要：一行只有一个决定）
- 外键 `task_id`、`execution_id` 都存在，但**没有** `approval.task_id == execution.task_id` 的约束（T18 在 service 层校验创建时一致）

| 函数 | 提交位置 | 事务范围 |

`as_utc()` 已存在（`service.py:71`），可作为服务端时间归一化的唯一入口。

## 五、重复提交与冲突决定的现有行为

`decide_approval`（`repository.py:255-289`）：

```python
UPDATE approval_request
SET approval_status = :decision, decided_by, decided_at, decision_reason
WHERE id = :id AND approval_status = 'PENDING'
```

| 场景 | 现有行为 | 缺陷 |
|---|---|---|
| 首次批准 | 返回 `True` | ✅ |
| 重复提交相同决定 | 返回 `False` | ❌ 调用方无法区分“重复”与“失败” |
| 提交相反决定 | 返回 `False` | ❌ 无法区分“冲突”与“状态不符” |
| 不存在 | 返回 `False` | ❌ 与上面三种同形 |
| 已 `REVOKED` 再决定 | 返回 `False` | 同上 |

**没有任何幂等返回、冲突识别或结果类型**。

## 六、迟到决定与终态任务

| 场景 | 现有行为 | 依据 |
|---|---|---|
| `deadline_at` 已过 | `decide_approval` **完全不检查**，照样写入 | `repository.py:255-289` 无时间判断 |
| 任务已 `COMPLETED/FAILED/CANCELLED` | `decide_approval` **不检查 Task 状态**，仍可写 `APPROVED` | 同上 |
| 决定后是否恢复任务 | **不恢复**（没有联动） | 调用链无 Task/Execution 更新 |
| 图侧迟到 resume | `agent_resume_stream` 只检查 `interrupts` 仍在，不检查 deadline | `stream.py:246` |

**结论**：
- “不无条件恢复”目前是**因为根本没有恢复逻辑**，不是因为做了校验。
- “终态任务不得被迟到批准复活”**没有被显式实现**；虽然不会复活，但会留下一条 `APPROVED` 记录，语义上可能被误读。
- 是否允许在终态任务上写入决定，必须由 T20 明确（见 §十 Q3）。

## 七、并发风险与代码证据

### 7.1 已有保护

- `decide_approval` 的 CAS（`WHERE approval_status='PENDING'`）保证**一行只被决定一次**。
- 已验证：顺序重复调用第二次返回 `False`（`smoke_task_models.py:209-219`）。

### 7.2 风险窗口

1. **读后写**：若 T20 先 `SELECT` 判断“是否已有决定”，再 `UPDATE`，两次提交之间会有窗口。必须以 CAS 结果为准，并在失败后**重读**判定 same/opposite。
2. **同决定判定依赖字段**：`decided_by`、`decision_reason` 是否参与“相同决定”的判断，当前无定义。
3. **跨表不一致**：审批状态与 Task/Execution 状态没有一致性约束，T20 若在决定后迁移任务，必须走 T19 服务并接受其 CAS 语义。
4. **SQLite 限制**：写事务串行化；并发测试可用两个独立 Session，但**不能据此证明 PG/跨进程安全**（T19 已有同样限制）。

## 九、最小实施建议

### 9.1 推荐形态（**不改 Schema**）

新增 `packages/core/src/furina_core/task/decision_service.py`：

```
DecisionOutcome(str, Enum):
    APPLIED        # 首次成功
    IDEMPOTENT     # 相同决定重复提交
    CONFLICT       # 相反决定
    NOT_FOUND      # 审批请求不存在
    SCOPE_MISMATCH # 请求与 task/execution 关联不符
    ILLEGAL_STATE  # 当前状态不允许（含终态任务策略，待拍板）

async def submit_decision(
    session, *, approval_id, task_id, execution_id,
    decision: ApprovalStatus, decided_by: str, reason: str | None = None,
    now: datetime | None = None,
) -> tuple[DecisionOutcome, ApprovalRequest | None]
```

判定顺序：

1. 读审批 → 不存在 `NOT_FOUND`
2. `approval.task_id != task_id or approval.execution_id != execution_id` → `SCOPE_MISMATCH`
3. 已终态：与本次相同 → `IDEMPOTENT`；相反 → `CONFLICT`
4. `PENDING`：按需校验任务终态（Q3）→ 调 `repository.decide_approval(decided_at=as_utc(now or 服务端现在))`
5. CAS 成功 → `APPLIED`；失败 → **重读**：相同 `IDEMPOTENT` / 相反 `CONFLICT`

**明确不做**：
- 不更新 Task/Execution（T22）
- 不执行工具（T23）
- 不读/写 `pending_reviews` / `decision_reviews`（图状态归 T23 统一执行器处理）
- 不检查“是否超过 deadline 就拒绝”（迟到决定允许，Q4/Q5）

### 9.2 是否需要 Schema 变更

**建议不需要**（决策记录内联在 `approval_request`）：

- 优点：零迁移、与 T18 模型一致
- 代价：**没有“每次提交”的审计轨迹**（重复/冲突提交不留痕）；若你要求留下每次提交记录，需要新增 `approval_decision` 表（Q1）

### 9.3 建议修改/新增文件

| 文件 | 动作 |
|---|---|
| `task/decision_service.py` | 新增（核心） |
| `apps/desktop/tests/smoke_decision_service.py` | 新增（12 类场景） |
