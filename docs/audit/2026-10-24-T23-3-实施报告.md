# T23-3 实施报告：审批决定接口

> 依据：ADR-3 / ADR-4 / ADR-8（已批准）
> 范围：决定持久化（T20）与 HTTP 入口；**未实现 T23-4 的 T22 校验、预检、认领**
> 状态：测试全绿；T23-2 的 R2（决定不落库）已关闭

---

## 一、阶段目标

让用户的批准/拒绝通过唯一入口调用 T20 落库，并保证：

- 不信任客户端传入的 task/execution；
- 重复提交同一决定 → 幂等；
- 相反决定 → 冲突；
- 不存在/越权审批 → 404；
- API 不重复实现审批状态机。

## 三、设计依据与实现结果

### 3.1 `POST /agent/decisions`

请求：

```json
{
  "chat_thread_id": "<uuid>",
  "decisions": [
    {"approval_id": "<uuid>", "tool_call_id": "call_w1", "action": "approve", "reason": null}
  ]
}
```

处理顺序：

1. `get_owned_threads` 校验会话归属（404，不泄漏存在性）。
2. 每条决定必须具备 `approval_id` 或 `tool_call_id`，否则 422。
3. 查该会话活动 Execution；没有 → 409。
4. `runtime.submit_decisions`：
   - 校验 Execution 属于该 Task，Task 属于该 `thread_id`；
   - 优先按 `approval_id` 定位；只给 `tool_call_id` 时在该 Execution 内解析；
   - 同时给出时，校验二者指向同一行；
   - 从审批行反查 `task_id` / `execution_id`，**不使用客户端传值**；
   - 逐条调用 T20 `submit_decision`；状态机判定完全由 T20 负责。
5. HTTP 映射：
   - 全部 `APPLIED` / `IDEMPOTENT` → 200，返回逐条结果；
   - 任一 `NOT_FOUND` / `SCOPE_MISMATCH` → 404；
   - 任一 `CONFLICT` / `ILLEGAL_STATE` → 409。

**本接口不恢复图**。决策落库后，图仍停在 interrupt，等待 `/agent/resume`。

### 3.2 `/agent/resume` 的决定持久化

在原有“决定与待审 `tool_call_id` 对齐”校验通过后，先调用同一个
`runtime.submit_decisions`，全部成功才继续恢复；失败则在 HTTP 层返回 404/409，
不进入流式响应。

> 这修掉了 T23-2 的 R2：不会再出现“工具已执行、审批仍 PENDING”。

恢复本身仍是 T23-2 的过渡路径（`mark_resumed` = 仅 T19 迁移）。
T23-4 会替换为 T22 `validate_and_resume`。

### 3.3 幂等/冲突/并发

- 同一决定重复提交：T20 返回 `IDEMPOTENT`，不覆盖 `decided_at`。
- 相反决定：T20 返回 `CONFLICT`，数据库保持首个决定。
- 并发提交：T20 单行 CAS；只有一个写入生效，另一个得到 `CONFLICT` 或 `IDEMPOTENT`。
- 批量中若某条失败：API 返回 404/409，不启动恢复；已成功写入的其他条目保留，
  响应 `results` 逐条给出 outcome。

## 五、故障与风险

| # | 问题 | 影响 | 计划 |
|---|---|---|---|
| R1 | 决定接口不与图中断批次做预检 | 可对“已存在但不在当前 interrupt”的审批落库（仍受 Execution 归属约束） | T23-4 / ADR-5 |
| R2 | `/agent/resume` 仍用 `mark_resumed`（仅 T19） | 恢复前没有 T22 的批次/参数/已执行校验 | T23-4 |
| R3 | `tool_execution_status` 仍 `NOT_STARTED` | `ALREADY_EXECUTED` 未生效 | T23-4 |
| R4 | 批量决定可能部分写入 | 一条冲突时，前面的决定已提交；需按 `results` 重试或人工处理 | 已在响应中逐条暴露；T23-4 可加预检 |
| R5 | 并发决定依赖 T20 CAS | 无跨审批批次原子性 | 接受；每行独立 |
| R6 | 拒绝恢复仍走现有图逻辑（回 `model_node`） | 与 ADR-4 一致；但未接 T22 拒绝模式 | T23-4 |

## 六、下一步建议

**T23-4**：

1. 用 T22 `validate_and_resume` 替换 `mark_resumed`，增加“当前审批批次”范围；
2. 拒绝模式（无 PENDING、无已开始、至少一条 REJECTED）；
3. 双向预检：DB 审批 ↔ 图 interrupts ↔ 参数哈希；
4. 高风险批次整批原子认领 + 结束记录；
5. 图恢复失败的补偿（未开始 → SUSPENDED；已开始 → FAILED，不重放）。
