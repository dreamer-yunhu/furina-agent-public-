## 四、Task 与 Execution 的关联约束

| 约束 | 现状 | 证据 |
|---|---|---|
| 外键 `agent_execution.task_id → agent_task.id` | 有，`ON DELETE CASCADE` | DDL 实测 |
| 外键 `agent_task.parent_task_id → agent_task.id` | 有 | DDL |
| 外键 `agent_task.thread_id → agentthreadid.id` | 有，`ON DELETE CASCADE` | DDL |
| SQLite 外键是否生效 | **仅在显式 `PRAGMA foreign_keys=ON` 时生效**；desktop 引擎在 `database.py:60-64` 开启 | `database.py` |
| Task ↔ Execution 状态一致性约束 | **没有**（无触发器、无 CHECK） | DDL |
| 一个 Task 对应几个 Execution | **N 个**（表结构允许，`list_executions` 按 task 查列表） | `repository.py:138-146` |
| Execution 创建时是否校验 Task 状态 | **否**（只靠外键 exists） | `repository.py:111-129` |

**结论**：归属关系靠外键保证“存在”，不保证“状态合理”。T19 按指南要求**不假定 1:1**，只校验归属与存在性。

## 五、当前事务边界与潜在部分提交

### 5.1 Repository 的提交行为

| 函数 | `add` | `flush` | `commit` | 失败后 session |
|---|---|---|---|---|
| `create_task` | 是 | 隐式 | **是**（内部） | 需 `rollback` |
| `create_execution` | 是 | 隐式 | **是** | 需 `rollback` |
| `transition_task` | — | — | **是** | 需 `rollback` |
| `transition_execution` | — | — | **是** | 需 `rollback` |
| `create_approval` | 是 | 隐式 | **是** | 需 `rollback` |
| `decide_approval` / `claim_*` / `finish_*` | — | — | **是** | 需 `rollback` |

Session 配置：`expire_on_commit=False`（`database.py:67`）。

### 5.2 实测：部分提交确实存在

场景：同一 session 先 `create_task` 成功，再 `create_execution(task_id=不存在)` 触发 `IntegrityError`。

```
task committed: cb3302d1-...
second step failed: IntegrityError
tasks still persisted after failed step2: 1 -> step1-committed
```

第一步已提交，第二步失败**不会**回滚第一步 —— 业务上“创建任务并启动执行”无法整体回滚。

### 5.3 `flush` 与 `commit` 的区别（本项目的实际影响）

- `flush`：把 SQL 发给数据库并拿到约束错误，**不结束事务**；外层仍可回滚。
- `commit`：结束事务并释放锁；失败后 session 进入 `PendingRollbackError` 状态（T18-0 已实测）。
- 因此 **create-or-get 必须用 SAVEPOINT**（T18 已实现），而**多步业务要么共用一个事务，要么接受部分提交**。

### 5.4 建议的事务方案（需拍板）

| 选项 | 做法 | 评价 |
|---|---|---|
| **A（推荐）** | 只给 `transition_task` / `transition_execution` 加 `commit: bool = True` | 改动面最小；现有调用默认行为不变；T19 的成对迁移可共享事务 |
| B | 所有 repository 函数都加 `commit` | 一致性更好，但改动面大，且 T18 service 也要跟着改 |
| C | Service 自己写 SQL / UnitOfWork | 重复实现、抽象过重 |

> 注意：即使选 A，也只能保证**数据库内**原子的；文件写入等外部副作用不在 T19 范围（指南 §二.C 已声明）。

### 7.2 如何防止“绕过规则直接写库”

这是指南的硬要求（“不能允许调用方绕过规则”），但 repository 的迁移函数是公开的。三个选项：

| 选项 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | 在 `repository.transition_*` 内部调用纯函数 `is_legal_*`，非法直接返回 False + 不改库 | repository 承担“合法配对”判断（不是“何时迁移”），与其“只做 CAS”的原注释冲突，但换来唯一入口 |
| B | 把 `transition_*` 改名 `_transition_*`，只暴露 service | 强制收敛，但改公开 API，且测试要改 |
| C | 只靠 service + code review | 最省事，但“绕过”在物理上仍然可能 |

> 我倾向 **A**：规则表是纯函数、无 IO，放在 repository 里只做“这对我允许吗”的判断，
> 不涉及“现在该不该迁”——后者仍归 service。

1. T19-1：确认迁移表（本文二、三节）
