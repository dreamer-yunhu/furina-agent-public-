## 0. 为什么现在必须你定

T22 要做的事只有一句话：**一条已批准的请求，什么时候允许把任务从“等待/挂起”带回运行。**

它横跨三样东西，且都不是 T22 能单独决定的：

1. 数据库状态机（T19 已批准，不能随便加边）
2. 审批记录的权威性（T20 写入、T21 不改）
3. LangGraph 图恢复（不在 core，也不与数据库同事务）

其中 **Q11 是这次审计新发现的硬约束**：数据库迁到 `RUNNING` 后，图恢复失败**没有回退路径**。这一条不拍板，T22 写不下去。

## 12. Q11（补充）· DB 已迁到 RUNNING，图恢复失败怎么办

**这是本次审计发现的最硬约束**：T19 迁移表没有 `RUNNING→SUSPENDED`。

| 选项 | 做法 | 后果 |
|---|---|---|
| **A（推荐）** | 调用方契约：T23 在 resume 失败时把 Task/Execution 置 `FAILED`（`CHECKPOINT_MISMATCH`），由 T24 重委派 | 状态诚实；但一次基础设施故障会把任务打成终态 |
| B | 给 T19 加 `RUNNING→SUSPENDED` | 保留可恢复性；但改已批准的迁移表，需要 T19 变更 + 测试 |
| C | 先 resume 图，成功后再写 DB | 图可能先执行工具而 DB 仍是挂起；崩溃后重复执行风险 |
| D | 留在 RUNNING | 状态与现实不一致，不可接受 |

**选 A 的代价**：任务失败后必须重新走一遍任务创建；但不会出现“永远 RUNNING 的僵尸”。
**选 B 的代价**：`SUSPENDED` 的含义会变成“等待审批 / 等待重试”两用，需要重新定义它的出口。
