## 0. 结论摘要（先看这五条）

1. **审批链路目前跑不通，而且不是"差最后一步"，是入口就断。**
   实测：主管图最小调用直接抛
   `AttributeError: 'CoderState' object has no attribute 'subagent_task'`
   —— coder 子图第一个节点 `prepare_node` 就失败。

2. **即使修好入口，审批门也不在图上。**
   `prevalidate_node` 从未 `add_node`；`pending_reviews` 永远为 `None`；
   `review_node` 拿到 `None` 后 `goto="model_node"`，会形成"模型 → 审批节点 → 模型"的**热循环**（每次都调 LLM）。
   `execute_node` 也是空函数且从未注册，`review_node` 的 `goto="execute_node"` 指向不存在的节点。

3. **当前没有任何审批持久化。** 没有审批表、没有状态枚举、没有幂等键、没有唯一约束、没有执行状态。
   "审批"只存在于 LangGraph checkpoint 里的 `pending_reviews` 快照和 `interrupt()` 载荷中，**不可查询、不可恢复、不可审计**。

4. **设计约束中的"重复提交不重复创建"在当前架构下有真实触发路径。**
   实测（InMemorySaver + 真 `interrupt()`）：**resume 时包含 `interrupt()` 的节点会从头重跑**。
   任何写在 `interrupt()` 之前的"落审批记录"代码都会执行两次。因此数据库唯一约束不是锦上添花，是必需项。

5. **桌面版连数据库会话都没接。** `furina_desktop.main` 只初始化了 checkpoint store，
   **没有设置 `app.state.async_session`**；而 `get_session` 依赖它。
   所以 `POST /agent` 在进入图之前就会 `AttributeError`。web 侧有 PG 会话，但 `agent_stream` 仍是 `NotImplementedError`。

## 6. 推荐的最小修改方案（阶段 2 / 3 预演，尚未实施）

### 6.1 先说结论：不要先写"幂等"或"状态机"，先让链路能跑到审批门

当前有 9 个阻断缺陷，其中 B1-B8 是"不修就到不了 interrupt"。
建议阶段 2 的第一刀是**修通一条最小路径**：

```
POST /agent（或直接 ainvoke）
 → prepare（拿到任务）
 → model（真 LLM）
 → prevalidate（分类；全安全→工具节点；有危险→建审批记录→review）
 → review（interrupt，载荷带 approval_id）
 → resume（只允许待审批记录）
 → execute（统一执行器校验→执行→回填 ToolMessage）
 → model
```

配套测试只断言"图能停在审批门、拒绝后不写文件、批准后文件出现"。
**幂等与并发放阶段 3**，但数据模型从第一天就带 `idempotency_key` 的 unique 约束，
避免阶段 3 再改表。

### 6.2 数据模型（建议放在 `packages/core`）

一行 = **一个工具调用**（不是一个批次）。理由：

- 约束要求"审批请求必须绑定具体工具及关键参数" → 逐条天然满足；
- 前端支持逐条决策（现有 `ItemDecision` 就是逐条）；
- 不需要 `batch` 主表 + `items` 子表，少一层；
- 同一批用 `batch_id` 分组即可（`batch_id` 可确定性生成，也可随机一次后复用）。

```text
approval_request
  id                UUID        PK
  thread_id         UUID/str    必填，索引           -- 归属线程
  batch_id          UUID        必填，索引           -- 同一次 interrupt 分组
  scope             str         "coder"             -- 将来多子代理时区分
  tool_call_id      str         LLM 给出的调用 id
  tool_name         str         必填
  args_json         Text        规范化后的完整参数快照
  args_hash         str         参数快照哈希（防篡改/一致性检查）
  target_path       str|None    沙箱相对路径（文件类工具）
  old_hash          str|None    审批时文件内容哈希（乐观锁）
  idempotency_key   str(64)     **UNIQUE**          -- DB 层幂等
  approval_status   enum        pending/approved/rejected/expired/cancelled
  execution_status  enum        not_started/running/succeeded/failed/unknown
  decided_by        str|None    审批人
  decided_at        datetime|None
  decision_reason   str|None
  execution_started_at / execution_finished_at
  execution_result  Text|None
  created_at / updated_at
```

关键点：

- **`args_json` 是执行时唯一的参数来源**。resume 载荷只允许带 `approval_id + action + reason`，
  绝不允许客户端回传/修改参数。这同时满足"参数被修改"测试项和"执行内容与获批内容一致"。
- `approval_status` 与 `execution_status` 是两个独立列，**不共用一个枚举**。
- `idempotency_key = sha256(canonical_json({thread_id, scope, tool_call_id, tool_name, args}))`。
  规范化：`json.dumps(..., sort_keys=True, ensure_ascii=False, separators=(",", ":"))` 后 utf-8。
  不用 `checkpoint_id` 的理由：`tool_call_id` 在 resume 后仍稳定存在于 state 的 AIMessage 中，
  且同一逻辑请求的重复投递会得到同一个 key；新的一轮对话会生成新 id，不会误伤。

### 6.3 状态机与合法转换

```text
approval_status:
  pending ──approve──▶ approved
  pending ──reject───▶ rejected
  pending ──超时/新消息──▶ expired / cancelled
  approved / rejected / expired / cancelled 为终态，不再变更

execution_status:
  not_started ──执行器抢到锁──▶ running ──成功──▶ succeeded
                                        ├─确定失败──▶ failed
                                        └─结果不明──▶ unknown
```

规则：

- `approved` **只代表授权**，不写入 `execution_status`。
- 只有 `approval_status == approved AND execution_status == not_started` 才能进入 `running`。
- `failed` / `unknown` **不自动重试**；要再执行必须重新走一次审批（新 `tool_call_id` → 新 key）。

### 6.4 数据库层幂等与并发

**创建（修 B-幂等）**

```python
try:
    session.add(row)
    await session.flush()
except IntegrityError:                 # 唯一键冲突 = 并发/重复提交
    await session.rollback()           # PG 事务在冲突后已 abort，必须先回滚
    row = await session.scalar(
        select(ApprovalRequest).where(
            ApprovalRequest.idempotency_key == key
        )
    )
    if row is None:                    # 不是我们认识的冲突 → 继续抛
        raise
```

- **不能**用"先 SELECT 再 INSERT"作为正确性保证（任务书明确禁止）。
- 冲突后要校验查回的记录与本次请求语义一致（thread/tool/args_hash）；
  不一致说明 key 碰撞或逻辑错误，应报 409，而不是静默复用。
- SQLite 与 PG 都支持唯一索引；用 `IntegrityError` 路径可避免写两套方言 upsert。

**决策（修"重复审批决定"与并发审批）**

```sql
UPDATE approval_request
SET approval_status = :action, decided_at = now(), decided_by = :uid, decision_reason = :r
WHERE id = :id AND approval_status = 'pending'
```

- `rowcount == 1` → 成功。
- `rowcount == 0` → 再读一次：
  - 不存在 → 404；
  - 已有状态与本次请求**相同** → 幂等返回 200（重复点击/重试）；
  - 已有状态与本次请求**不同** → 409（例如先批准后拒绝）。
- 这一步是原子的，不依赖应用层锁。

**执行（修"只批准不执行≠成功"与并发执行）**

```sql
UPDATE approval_request
SET execution_status = 'running', execution_started_at = now()
WHERE id = :id
  AND approval_status = 'approved'
  AND execution_status = 'not_started'
```

- `rowcount == 0` → 拒绝执行（未批准、已执行、或执行中）。
- 抢到之后再执行，天然防止同一审批被执行两次。

### 6.5 统一执行器（修约束 2 / 8 / 9）

建议新增**唯一**入口，例如：

```text
execute_approved(approval_id) -> ExecutionResult
  1. 读取 DB 行（参数只从 args_json 来）
  2. 校验 approval_status == approved 且 execution_status == not_started
  3. 校验 args_hash == sha256(args_json)
  4. 校验路径重新 resolve 后仍在 sandbox 内
  5. 文件类：校验 old_hash 与当前文件一致；新建文件校验目标仍不存在
  6. 原子 UPDATE → running
  7. 执行
  8. 写回 succeeded / failed / unknown
```

**结构要求：`ToolNode` 里不能再出现高风险工具。**
否则"批准后走执行器"和"直接走 ToolNode"会形成两条执行路径，审批可被绕过。
建议把 `coder_tools` 拆成 `safe_tools`（给 ToolNode）与 `risky_tools`（只给执行器），
或者在自定义 tools 节点里统一分发。这一步属于"修结构"，不是"修值"。

**结果不确定的定义（文件写）**：写后读回并比对 hash。
- 写成功且读回一致 → `succeeded`
- 写前确定未发生（如路径校验失败）→ `failed`
- 写调用抛异常/读回不一致/超时 → `unknown`，**不重试**，等人工处理

### 6.6 API 最小集合

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/agent/approvals?thread_id=` | 列出待审批/历史（按线程归属校验） |
| POST | `/agent/approvals/{id}/decision` | `{action: approve|reject, reason?}`，只接受 id，不接受参数 |
| POST | `/agent/resume` | 用 thread_id + 决策结果恢复图；需校验 approval 属于该 thread |

`resume` 的实现要点：

- 先校验 thread 归属（复用 `get_owned_threads`）；
- 校验该 thread 当前确实处于 interrupt 状态；
- 校验提交的 `approval_id` 集合与 pending 集合一致；
- 然后 `graph.astream(Command(resume={...}), config={"configurable": {"thread_id": ...}})`。

### 6.7 桌面版必须补的数据库装配（B8）

在 `furina_desktop.main.lifespan` 里：

create_async_engine("sqlite+aiosqlite:///data/furina.db")

## 7. 风险清单

| 风险 | 说明 | 缓解 |
|---|---|---|
| **双份代码漂移** | `backend/` 与 `apps/desktop/` 是同一套 agent 代码 | 明确单一实现目标；另一份标 legacy 并停止修改 |
| **先接线后加约束** | 若先让 `handle_review_fn → tools_node` 跑通，会短暂出现"无审批校验的写盘路径" | 先拆走 ToolNode 里的写工具，再接审批 |
| **resume 载荷被当成可信输入** | 当前设计里 decision 只带 tool_call_id；若将来允许带参数，等于客户端可改参数 | API 层拒绝任何 args 字段；执行参数只取 DB |
| **`sandbox_root` 默认 `.`** | `core/config.py:93` 在环境变量缺失时把 CWD 当沙箱根 | 桌面版启动时强制要求显式配置，缺失即拒绝启动 |
| **SQLite 并发** | 单进程 + 单实例锁降低了风险，但多协程仍可能并发写 | WAL + 条件 UPDATE + 唯一索引；不要依赖 Python 锁 |
| **PG 事务 abort 语义** | 唯一冲突后 PG 事务不可继续，必须在同一 session 里 rollback | 冲突分支固定先 `rollback()` 再查询 |
| **checkpoint 与 DB 不一致** | DB 有 pending，checkpoint 丢了（或反之） | DB 为准；提供按 thread 查询 pending 的恢复入口；孤儿 pending 过期处理 |
| **新消息到达时的旧 pending** | 9.8 铁共识：挂起期间新消息应作废旧 pending，否则可能被隐式放行 | 新 turn 开始时把该 thread 的 pending 置 `cancelled` |
| **无迁移工具** | `create_all` 只建新表，不改旧表 | 本轮只新增表，不改旧表；后续引入 Alembic 再谈 |
| **`interrupt()` 载荷序列化** | Enum 必须是 str 兼容；Pydantic `model_dump(mode="json")` 已处理 | 保持 `str, Enum`；测试里断言 `json.dumps` 可过 |
| **子图 interrupt 冒泡未复验** | 文档 `docs/9.11` 说已验证，但本次因 B1 无法重跑 | 阶段 2 修通后第一件事就是复验 |
