# 审批 V2：Thread → Task → Execution → Approval
## 现有架构审查、字段差异与最小迁移方案

> 日期：2026-10-22
> 依据：用户提供的《芙芙 Agent 审批系统 V1：任务层级、状态管理与超时恢复补充需求》
> 阶段：**仅审查与方案，未修改代码**（遵循该文档 §九）
> 前置材料：
> - `docs/2026-10-22-审批系统V1-阶段1-只读审查.md`
> - `docs/2026-10-22-审批系统V1-总体设计与实施方案.md`

## 0. 结论摘要

1. **现有代码只有 Thread，没有 Task / Execution。**
   `AgentThreadID` 是唯一与“工作线程”对应的持久化实体；审批表尚未实现。
   V2 的四层模型需要新增两张表（Task、Execution），并把 Approval 挂到 Execution 上。

2. **最关键的架构冲突：业务 thread_id 被直接当作 LangGraph 的 thread_id。**
   `api/agent.py` 校验 `chat_thread_id` 后，`stream.py` 直接把它放进
   `configurable.thread_id`。一个 Thread 若有多个 Task/Execution，它们会**共用同一份 checkpoint**，
   直接违反验收场景 #9（同线程多任务不互相误用 checkpoint / 审批记录）。

3. **当前没有调度器，也没有业务数据库会话。**
   - desktop 的 lifespan 只初始化了 checkpoint store，没有 `app.state.async_session`；
   - 没有任何后台任务/超时监控；
   - 没有 Alembic 或其他迁移工具。

4. **当前 Supervisor 图是半成品。**
   `build_graph` 只有 `START → coder_graph → END`，
   主管节点（profile/route/rag/generate/persist）全是 `NotImplementedError`。
   V2 要求“主管创建新业务任务、接收子图结构化结果、决定重新委派”，
   这部分**必须先补一个最小主管节点**，否则 V2 的重新委派无处落地。

5. **状态语义需要按新文档重排。**
   上一版方案里的审批 `EXPIRED / CANCELLED` 不再适用：
   新文档明确 **超时不改变审批状态**，审批状态为
   `PENDING / APPROVED / REJECTED / REVOKED`；
   超时改变的是**任务**状态（`SUSPENDED`）。

6. **V2 不是“加几个字段”的改动**，而是一次中等规模扩展：
   持久化基础设施 + 任务/执行生命周期 + 图与 ID 重新绑定 + 超时监控 + 重委派。
   建议分四个小阶段落地，每阶段可独立验收。

## 1. 现有架构审查

### 1.1 四层实体现状

| 层 | 现有实体 | 位置 | 结论 |
|---|---|---|---|
| Thread | `AgentThreadID` | `packages/core/src/furina_core/models.py:60-76` | ✅ 已有。字段：`id / created_at / updated_at / title / user_id` |
| Task | 无 | — | ❌ 缺失 |
| Execution | 无 | — | ❌ 缺失 |
| ApprovalRequest | 无（仅设计文档） | — | ❌ 缺失 |

补充事实：

- `AgentThreadID.user_id` 外键指向 `user.id`。
- desktop 的 `get_local_user` 返回一个**不落库**的固定 User
  （`apps/desktop/src/furina_desktop/auth.py:57-75`）。
  一旦启用 SQLite 外键，创建 Thread/Task 会因 user 行不存在而失败。
  **V2 必须先把本地用户落库（或显式关闭该外键约束，但不推荐）。**
- web 侧 `Conversation / Message` 是聊天记录，不等于 Task/Execution，
  不能拿来替代。

### 1.2 thread_id 的真实调用链（重点）

```text
客户端 POST /agent
  body.chat_thread_id
    → get_owned_threads(session, thread_id=chat_thread_id)   # 校验 AgentThreadID
    → agent_stream(inform)
        config = {"configurable": {"thread_id": inform.chat_thread_id}}
        graph.astream(..., config)
```

代码位置：

- `apps/desktop/src/furina_desktop/api/agent.py:31-35`
- `apps/desktop/src/furina_desktop/agent/stream.py:33`
- 旧单体同样逻辑：`backend/app/routers/agent.py:25-35`

**结论：当前业务 thread_id 与 LangGraph thread_id 是同一个 UUID。**

这带来三个问题：

1. 同一 Thread 下的多个 Task 会共享 `messages` / `subagent_task` / 中断现场；
2. 两个 Task 同时等待审批时，`aget_state(config)` 无法区分是谁的中断；
3. 重新委派产生新 Task 时，旧 Task 的 checkpoint 仍在新 Task 的 thread 里，
   新执行可能继承旧状态——这正是文档要禁止的“旧授权/旧现场被继承”。

### 1.3 图与状态现状

`SupervisorState`（`agent/state.py`）：

```text
messages, mode, user_name, personal_preference,
rag_result, subagent_task
```

`CoderState`（`agent/state.py`）：

```text
subagent_task, coder_messages,
pending_reviews(dict), decision_reviews(dict)
```

图装配（`agent/build.py:102-108`）：

```text
START → coder_graph → END
```

主管节点全部是 `NotImplementedError`。也就是说：

- **没有“主管创建 Task”的代码路径**；
- **没有“主管接收 coder 结构化结果并重委派”的代码路径**；
- 当前 coder 子图只能接收一个 `subagent_task` 字符串。

### 1.4 审批与执行现状

上一轮已经打通：

```text
model → prevalidate → [tools_node | review_node]
review_node → interrupt → execute_node → tools_node / model_node
```

但仍有明确的临时边界：

- `execute_node` 只校验决定完整性，不查数据库；
- 批准后直接 `goto="tools_node"`，**高风险工具仍由 ToolNode 直接执行**；
- 没有统一执行器；
- `pending_reviews` / `decision_reviews` 只是 checkpoint 里的运行时快照。

### 1.5 持久化现状

| 项 | desktop | web / 旧单体 |
|---|---|---|
| 主业务库 | ❌ 未接（`app.state.async_session` 未设置） | PostgreSQL + asyncpg |
| 建表 | 无 | `SQLModel.metadata.create_all` |
| checkpoint | SQLite（`checkpoints` + `writes`） | PG（`AsyncPostgresSaver`，三张表） |
| 迁移工具 | 无 | 无（无 Alembic） |
| 后台任务 | 无 | 无 |

### 1.6 超时/调度现状

- 没有任何 `asyncio.create_task` / 后台循环 / 调度器；
- 没有 `deadline_at` 字段；
- 没有“挂起后释放调度资源”的概念。

## 2. 字段差异清单

### 2.1 Thread

| 字段 | 现状 | 处理 |
|---|---|---|
| `id` | 有 | 保留，作为业务 thread_id |
| `title` | 有 | 保留 |
| `user_id` | 有（FK user.id） | 保留；desktop 需先落库本地用户 |
| `created_at/updated_at` | 有 | 保留 |
| `graph_thread_id` | 无 | **不放在 Thread**；放到 Execution |

### 2.2 Task（新增）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | UUID PK | `task_id` |
| `thread_id` | UUID FK → `agentthreadid.id` | 所属工作线程 |
| `instruction` | Text | 主管下发的正式任务指示 |
| `status` | str | 见 §3.1 |
| `parent_task_id` | UUID nullable FK → self | 重委派来源 |
| `failure_reason` | Text nullable | 校验失败/终止原因 |
| `redelegation_key` | str(64) nullable **UNIQUE** | 防止同一失败事件重复创建新任务 |
| `created_at/updated_at` | datetime(tz) | UTC |

> `redelegation_key = sha256(parent_task_id | source_execution_id | failure_code)`。
> 只在“由失败触发的重委派”任务上非空；初始任务为 NULL。
> 唯一约束保证事件重放/并发时最多创建一个子任务。
> 注意：SQLite / PG 对多个 NULL 的唯一约束都允许（NULL 不参与唯一比较），
> 所以初始任务不会互相冲突。

### 2.3 Execution（新增）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | UUID PK | `execution_id` |
| `task_id` | UUID FK → task.id | 所属业务任务 |
| `status` | str | 见 §3.2 |
| `graph_thread_id` | str(64) **UNIQUE** | 传给 LangGraph 的 `configurable.thread_id` |
| `checkpoint_id` | str(128) nullable | 中断时的 checkpoint id，用于恢复现场校验 |
| `validation_failure_reason` | Text nullable | 恢复前校验失败原因 |
| `created_at` | datetime(tz) | |
| `finished_at` | datetime(tz) nullable | |

**关键建议：`graph_thread_id` 使用 `execution_id`（或其确定性派生值），不再复用业务 thread_id。**
理由：

- 每次 Task/Execution 有独立 checkpoint，天然满足验收 #9；
- 重委派产生新 Execution → 新 checkpoint，旧状态不会被继承；
- resume 时用 `execution.graph_thread_id` 取现场，不会串任务；
- 客户端不再直接指定图的 thread key，减少越权/误用。

代价：同一业务 Thread 的跨任务对话上下文不会自动出现在图状态里。
若需要，必须由主管在创建新 Task 时把摘要/历史显式写进 `SupervisorState.messages`。
这是一条需要确认的取舍（见 §12 Q1）。

## 3. 状态机

### 3.1 业务任务状态（Task）

```text
QUEUED ──调度器认领──▶ RUNNING
QUEUED ──取消────────▶ CANCELLED

RUNNING ──创建审批────▶ WAITING_APPROVAL
RUNNING ──完成────────▶ COMPLETED
RUNNING ──失败────────▶ FAILED
RUNNING ──取消────────▶ CANCELLED

WAITING_APPROVAL ──决定+恢复校验通过──▶ RUNNING
WAITING_APPROVAL ──deadline 到期────────▶ SUSPENDED
WAITING_APPROVAL ──取消────────────────▶ CANCELLED

SUSPENDED ──迟到决定+恢复校验通过──▶ RUNNING
SUSPENDED ──恢复校验失败───────────▶ FAILED
SUSPENDED ──取消───────────────────▶ CANCELLED

COMPLETED / FAILED / CANCELLED 为终态
```

规则：

- 用户拒绝审批 **不是任务失败**：任务回到 `RUNNING`，coder 收到拒绝消息后重新规划。
- 恢复前校验失败 → 任务 `FAILED`，`failure_reason` 记录失败码；
  随后由主管创建新任务（见 §6）。
- 超时只改任务状态，不改审批状态。
- “任务是否仍有效”= 状态不是终态，且没有被替换。

### 3.2 内部执行状态（Execution）

```text
CREATED ──开始执行──▶ RUNNING
RUNNING ──创建审批──▶ WAITING_APPROVAL
RUNNING ──完成──────▶ COMPLETED
RUNNING ──失败──────▶ FAILED
RUNNING ──取消──────▶ CANCELLED

WAITING_APPROVAL ──恢复校验通过──▶ RUNNING
WAITING_APPROVAL ──超时──────────▶ SUSPENDED
WAITING_APPROVAL ──取消──────────▶ CANCELLED

SUSPENDED ──迟到批准+校验通过──▶ RUNNING
SUSPENDED ──校验失败──────────▶ VALIDATION_FAILED
SUSPENDED ──取消──────────────▶ CANCELLED

COMPLETED / FAILED / VALIDATION_FAILED / CANCELLED 为终态
```

> 命名说明：文档只要求“至少能表达运行中、等待审批、挂起、校验失败、已完成、失败”。
> 这里用 `CREATED` 表达“执行记录已建但尚未开始”，避免和审批的执行状态 `NOT_STARTED` 混淆。

### 3.3 审批状态（Approval）

```text
PENDING ──approve──▶ APPROVED
PENDING ──reject───▶ REJECTED
PENDING ──revoke───▶ REVOKED

APPROVED / REJECTED / REVOKED 为终态
```

铁律：

- **超时不改变审批状态**，`PENDING` 可以一直保持到用户决定。
- 只有 `PENDING` 能接受首次决定；重复决定返回已有结果或 409。
- `REVOKED` 仅用于明确撤销（如任务取消时主动撤销待审批）。
  若现有权限模型不支持，V2 可先只在“任务取消”路径使用。
- 终态不能通过普通重复请求逆转。

### 3.4 工具执行状态（Tool Execution）

```text
NOT_STARTED ──执行器认领──▶ RUNNING
RUNNING ──成功──────────▶ SUCCEEDED
RUNNING ──确定失败──────▶ FAILED
RUNNING ──结果不确定────▶ UNKNOWN
```

- `APPROVED` ≠ `SUCCEEDED`。
- `UNKNOWN` 禁止自动重试；先查实际资源状态，必要时人工核实。
- 执行失败不改变已经作出的审批决定。

## 4. 超时挂起与迟到批准

### 4.1 时间来源

- 所有 `deadline_at` / `decided_at` / 状态时间用**服务端 UTC**。
- 不信任客户端时间。
- 不在 LangGraph 节点里 `sleep`（文档明确禁止）。

### 4.2 超时监控器

应用层 lifespan 启动一个后台协程：

```text
每 N 秒（建议 5s）执行一次：
  now = UTC now
  SELECT 到期的 PENDING 审批
  对每个审批：
    UPDATE agent_task
       SET status='SUSPENDED'
     WHERE id = :task_id AND status='WAITING_APPROVAL'
    UPDATE agent_execution
       SET status='SUSPENDED'
     WHERE id = :execution_id AND status='WAITING_APPROVAL'
    -- 不改 approval_status
```

要点：

- 单条 SQL + 事务，避免部分更新；
- 任务/执行的状态迁移都是条件 UPDATE，重复扫描不会重复挂起；
- 进程重启后重新扫描，不依赖内存计时器；
- desktop 有单实例锁，天然只有一个监控器；
- web 若多 worker，需要 DB 级锁或只让一个 worker 跑监控（V1 可先单 worker）。

### 4.3 决定与超时的竞争

决定接口必须比较**服务端时间**与 `deadline_at`：

```text
事务：
  UPDATE approval
     SET approval_status=:decision, decided_at=:now, decided_by=:who
   WHERE id=:id AND approval_status='PENDING'

  if rowcount == 0: 读当前状态 → 幂等/冲突判定

  if now <= deadline_at:
      -- 按时决定：任务从 WAITING_APPROVAL → RUNNING（等待 resume 调用）
      UPDATE task SET status='RUNNING'
       WHERE id=:task_id AND status='WAITING_APPROVAL'
  else:
      -- 迟到决定：只记录决定，不把任务从 SUSPENDED 拉起来
      UPDATE task SET status='SUSPENDED'
       WHERE id=:task_id AND status='WAITING_APPROVAL'
      -- 若监控器还没跑，这里顺手完成挂起
```

这样无论监控器和决定谁先到，最终语义一致：

- 按时批准 → 任务可恢复；
- 迟到批准 → 任务保持 `SUSPENDED`，必须走恢复校验。

### 4.4 迟到批准

```text
用户迟到批准
  → approval_status = APPROVED（PENDING→APPROVED 原子迁移）
  → 任务仍 SUSPENDED
  → 用户/前端调用 POST /agent/tasks/{task_id}/resume
  → 恢复前校验（§5）
      ├─ 通过 → 任务/执行 SUSPENDED→RUNNING → Command(resume=...) → 执行
      └─ 失败 → 任务 FAILED，执行 VALIDATION_FAILED → 结构化结果交主管（§6）
```

迟到批准**不能直接触发执行**。

## 5. 恢复前校验（统一执行入口）

`resume_and_execute(task_id, execution_id, approval_id)` 至少检查：

| # | 检查 | 数据来源 |
|---|---|---|
| 1 | `approval.task_id == task_id` 且 `approval.execution_id == execution_id` | Approval |
| 2 | `approval_status == APPROVED`，审批人合法 | Approval |
| 3 | `tool_name` 与 `args_hash` 与批准快照一致 | Approval + 当前调用 |
| 4 | 文件/资源当前 hash 与 `old_hash` 一致；新建文件仍不存在 | 文件系统 |
| 5 | 任务状态不是 `CANCELLED/FAILED/COMPLETED`，未被替代 | Task |
| 6 | `tool_execution_status == NOT_STARTED`（未执行/不在执行中） | Approval |
| 7 | 当前 LangGraph checkpoint 存在，且对应 `execution.graph_thread_id`；中断仍在 | Execution + saver |
| 8 | 决定时间/截止时间语义正确（迟到批准已识别） | Approval |

通过后：

```sql
-- 原子认领
UPDATE approval
SET tool_execution_status='RUNNING', execution_started_at=:now
WHERE id=:approval_id
  AND approval_status='APPROVED'
  AND tool_execution_status='NOT_STARTED'
```

`rowcount=0` → 拒绝执行（已执行/执行中/未批准）。
执行完成后写 `SUCCEEDED/FAILED/UNKNOWN`。

### 5.1 幂等键

审批：

```text
idempotency_key = sha256(
  canonical_json({execution_id, tool_call_id, tool_name, args})
)
```

- 包含 `execution_id`：新执行必然产生新审批，不会继承旧授权；
- 同一执行内重复投递 → 同 key；
- 用户真的想再执行一次 → 新 `tool_call_id` / 新 execution。

任务重委派：

```text
redelegation_key = sha256({parent_task_id, source_execution_id, failure_code})
UNIQUE
```

- 同一失败事件重放/并发 → 最多创建一个子任务；
- `NULL` 允许（初始任务不参与唯一比较）。

## 6. 校验失败后的重新委派

### 6.1 结构化结果

Coder 不再“校验失败就继续/重放”，而是返回明确结果：

```json
{
  "task_id": "...",
  "execution_id": "...",
  "outcome": "VALIDATION_FAILED",
  "failure_code": "ARGS_MISMATCH | OLD_HASH_MISMATCH | TASK_INVALID | ALREADY_EXECUTED | CHECKPOINT_MISMATCH",
  "failure_reason": "人类可读原因",
  "needs_replan": true
}
```

同时：

- 执行状态 `VALIDATION_FAILED`；
- 任务状态 `FAILED`，写 `failure_reason`；
- 旧审批记录保留（不改、不删、不重放）。

### 6.2 主管重委派

```text
Supervisor 收到结构化结果
  → 创建新 Task：
       parent_task_id = 旧 task_id
       instruction = 主管重新规划后的新指示
       status = QUEUED
       redelegation_key = hash(...)
  → Coder 接收新 Task
  → 创建新 Execution（新 execution_id / 新 graph_thread_id）
  → 重新生成操作计划 / 参数快照 / 新 approval_id
  → 新审批请求（新 idempotency_key）
```

规则：

- 新任务不得复制旧审批授权；
- 新任务不得只复制旧参数“假装重新审批”；
- 旧任务/执行/审批全部保留；
- `redelegation_key` 唯一约束防止重复建任务；
- 建议设置最大重委派次数（如 3 次），超过则任务 `FAILED` 并上报用户（需确认）。

### 6.3 主管节点缺口

当前 `SupervisorState` 图没有主管逻辑。V2 至少需要：

```text
START → supervisor_node
          ├─ 首次进入：创建 Task + Execution → 路由到 coder
          ├─ coder 返回结构化成功：更新 Task=COMPLETED → END
          └─ coder 返回 VALIDATION_FAILED：创建子 Task → 路由到 coder
```

主管节点需要访问数据库。建议：

- 在图装配时注入一个 `TaskService`（持有 session factory），
  不要把 ORM session 放进 state；
- 或者通过 `config["configurable"]["services"]` 传入运行时依赖；
- 不要用模块级全局 session。

## 7. 数据库迁移方案

### 7.1 目标

V2 只**新增表**（Task、Execution、Approval），不改现有表结构：

- `agentthreadid` 保留；
- `user` 保留（desktop 需 seed 本地用户）；
- 新表通过 FK 关联。

因此 **V2 不需要 ALTER TABLE**。

### 7.2 desktop（优先）

```text
storage/database.py（新增）
  create_async_engine("sqlite+aiosqlite:///data/furina.db")
  PRAGMA foreign_keys=ON（通过 connect 事件）
  async_sessionmaker → app.state.async_session
  SQLModel.metadata.create_all

main.py lifespan 顺序：
  1) 建业务库 + create_all
  2) seed 本地用户（固定 LOCAL_USER_ID）
  3) 建 checkpoint store
  4) build_graph(store, services)
  5) 启动超时监控协程
  关闭时逆序
```

现有 `auth.py` 的本地用户不落库，必须先修正，否则 Thread/Task 的 FK 会失败。

### 7.3 web / 旧单体

- PostgreSQL 已有 `create_all`；新表会被自动创建。
- 但 `create_all` 不会修改已有表；V2 不涉及修改，所以可接受。
- 若未来要加列，必须引入 Alembic。**V2 建议先不引入 Alembic**，
  但在文档里明确“下一次改列前必须引入”。

### 7.4 迁移步骤（桌面）

```text
1. 备份 data/furina.db（如果已存在）
2. 启动应用 → create_all 自动建新表
3. 验证：
   - agent_task / agent_execution / approval_request 三张表存在
   - FK 指向 agentthreadid / user
   - idempotency_key / redelegation_key 唯一索引存在
4. 如果已有旧审批表（当前没有），先做数据迁移再删旧表；
   本仓库目前不存在旧审批表，无需迁移。
```

### 7.5 回滚

- 新表独立，回滚 = 停用新代码 + 保留新表（不删数据）。
- 不做破坏性 DROP；旧数据保留。

## 11. 验收场景测试计划

> 原则：真 SQLite 文件、真图、真工具；只 stub LLM（需要网络）。
> 超时用“把 deadline_at 设为过去 + 手动触发一次监控 tick”，**不 sleep**。

| # | 场景 | 测试步骤 | 断言 |
|---|---|---|---|
| 1 | 正常审批通过后执行成功 | 建 Task/Execution → 发起审批 → approve → resume → 执行 | 文件存在；approval=APPROVED；tool_execution=SUCCEEDED；task=COMPLETED |
| 2 | 审批超时挂起，其他任务可调度 | deadline 设为过去 → 监控 tick → 再建一个 Task | 任务 A=SUSPENDED；审批仍 PENDING；任务 B=QUEUED/RUNNING |
| 3 | 迟到批准经校验后恢复 | 超时挂起 → approve（now>deadline）→ resume | 任务保持 SUSPENDED 直到 resume；校验通过后 RUNNING；文件写入 |
| 4 | 文件版本/参数不一致，不执行旧操作 | 审批后修改文件/args_json → resume | 校验失败；文件未被覆盖；execution=VALIDATION_FAILED |
| 5 | 校验失败创建新任务/执行/审批 | 触发 #4 → 主管处理 | 新 task.parent_task_id=旧 task；新 execution_id；新 approval_id；旧记录保留 |
| 6 | 新任务不继承旧授权 | 检查新 approval | 新 idempotency_key；approval=PENDING；不能复用旧 approval_id |
| 7 | 重复审批决定不重复恢复 | 同一 approve 调两次 | 第二次返回已有结果/200；只恢复一次；tool_execution 只成功一次 |
| 8 | 重复失败事件不重复建任务 | 同一失败事件重放两次 | redelegation_key 唯一；只创建一个子任务 |
| 9 | 同线程多任务不串 checkpoint | 同 thread 建两个 Task/Execution，各自 interrupt | graph_thread_id 不同；resume A 不影响 B；审批不交叉 |
| 10 | 执行异常/不确定不盲目重试 | 模拟“已写入但抛异常” | tool_execution=UNKNOWN；再次 resume 被拒；不自动重试 |
| 11 | 任一高风险路径无法绕过统一入口 | 直接调用 ToolNode / 直接 invoke 工具 | ToolNode 名单不含高风险工具；只能经 execute_approved |

补充：

- 并发审批：`asyncio.gather` 两个决定 → 一个成功、一个幂等/409；
- 并发超时与批准：服务端时间判定，最终任务状态唯一；
- 重启恢复：进程重启后监控器能重新扫描到期审批。
